I added `set -e` to `scripts/check.sh` and replaced the record. Just adding `-e` wasn't enough, so I also restructured the loop.

**Why adding `-e` alone would break things:** I tested it, and the check exited 1 on an ordinary commit with one small staged file. Two problems caused this:
- The line `[ "$kb" -gt "$limit_kb" ] && echo …` was the last command in the loop. When the last file was small, that test returned false, so the loop returned 1 and `-e` aborted the whole check.
- The loop ran inside `big=$(...)`, and bash doesn't apply `-e` inside `$(...)`. An error partway through the loop was hidden whenever a later file passed. The usual fix, `inherit_errexit`, doesn't exist in `/bin/bash` 3.2, which is what macOS ships.

**Changes to `scripts/check.sh`:**
- `set -euo pipefail`.
- The file loop now runs in the main shell (`while read … done <<< "$staged"`), so `-e` covers every command in it.
- The size test is now an `if` instead of `[ … ] && …`.
- I removed `2>/dev/null` from `git diff --cached`, so when the check aborts on a git error, the reason is printed.
- Large files still only produce a warning and exit 0. Only failures inside the check itself exit non-zero.

**Test results (in a throwaway repo):**

| Case | Result |
|---|---|
| Nothing staged / one small file | exit 0 |
| A large file (name with a space) followed by a small one | warning, exit 0 |
| Staged-then-deleted file (the 2026-09-10 incident) | skipped, exit 0 |
| Unreadable staged file with other files after it | "Permission denied", exit 1 |
| Run outside a git repo | exit 129 |
