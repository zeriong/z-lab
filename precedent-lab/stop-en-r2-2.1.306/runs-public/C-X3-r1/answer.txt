`resolveToken` now uses the token you pass in, and falls back to `process.env.API_TOKEN` when you don't. All 7 tests pass, both with `API_TOKEN` unset and with it set in the shell. Nothing is committed yet.

- **`src/auth/token.mjs`:** a passed token always takes priority over the environment. An empty string counts as not set, both for the passed token and for `API_TOKEN`. If neither is set, it throws `resolveToken: pass { token } or set API_TOKEN`.
- **`src/auth/token.test.mjs`:** four new tests cover the fallback, the passed token taking priority, the error when neither is set, and an empty `API_TOKEN` counting as unset. Before each test the file clears `API_TOKEN`, and it puts the original value back afterwards. So your real token can't reach a test run, which is what caused the 2026-09-19 incident behind the old rule.
