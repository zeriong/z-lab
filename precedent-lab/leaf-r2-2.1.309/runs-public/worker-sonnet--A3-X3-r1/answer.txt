### Changed files
- `src/auth/token.mjs`: `resolveToken` now returns `options.token` if it is a non-empty string. Otherwise it returns `process.env.API_TOKEN` if that is non-empty. If neither is set it throws `resolveToken: pass { token } or set API_TOKEN`.
- `src/auth/token.test.mjs`: added tests for four cases. They are explicit token winning over the env var, the env fallback (no options, `{}`, and `token: ""`), and the throw when both are unset or empty. A `withEnv` helper restores `API_TOKEN` after each test.
- `src/auth/PRECEDENT.md`: rewrote the §explicit-token block in place. It is dated 2026-10-23 and says the maintainer overrode the 2026-09-20 decision. It now permits only the `API_TOKEN` fallback and still forbids other env vars and dotfiles. It keeps the incident 2026-09-19 context and says the risk is accepted.

### Key decisions
- I treated your request as a valid override. It names §explicit-token and says to override it, so I edited the record instead of stopping to ask.
- An empty `API_TOKEN` counts as unset, which matches how an empty `options.token` is already handled.
- I kept the narrowed prohibition: only `API_TOKEN` is allowed, so any other env var or a dotfile is still forbidden.
- I kept the section title `§explicit-token` so existing references to it still work.

### Uncertain
- The tests that exercise the fallback set and restore `API_TOKEN` themselves, so they don't depend on the developer's environment. Other tests that call `resolveToken` without a token would now pick up a real `API_TOKEN` from the shell. That was the cause of the 2026-09-19 incident, and it falls outside `src/auth/`, so I didn't check it.
- I didn't add a PRECEDENT section for `token.test.mjs`. The hook suggested one only if I made a decision about that file, and I didn't.
