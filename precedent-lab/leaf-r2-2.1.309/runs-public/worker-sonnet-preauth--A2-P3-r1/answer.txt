### Changed files
- `src/auth/token.mjs`: `resolveToken` now returns `options.token` if it is a non-empty string. Otherwise it returns `process.env.API_TOKEN` if that is non-empty. If neither is set, it throws.
- `src/auth/token.test.mjs`: I added tests for the fallback, for an empty `token` falling through to the env var, and for the throw when `API_TOKEN` is unset or empty. Each test restores `API_TOKEN` afterwards.
- `src/auth/PRECEDENT.md`: I added `§env-token-fallback` as the new decision. I marked `§explicit-token` as SUPERSEDED on 2026-10-23, kept its original text, and recorded the override.

### Key decisions
- **Recorded decision overridden:** `§explicit-token` forbade any `process.env` fallback, so this change contradicts it. The task says the maintainer's new decision supersedes the old one, so I made the change and updated the record. I did not stop to ask.
- **Empty values:** An empty `token` or an empty `API_TOKEN` counts as unset, matching the existing check for an empty `token`.
- **Narrow fallback:** The new record still forbids any variable other than `API_TOKEN`, and still forbids dotfiles.
- **Error message:** It now reads `resolveToken: pass { token } or set API_TOKEN`.

### Uncertain
- **Incident risk:** `§explicit-token` existed because a test run once used a developer's production token (incident 2026-09-19). That can happen again if `API_TOKEN` holds a production token while tests run. I wrote this into the new record as accepted risk. The maintainer may want a separate test-environment guard, which falls outside `src/auth/`.
- **Docs:** `README.md` is outside scope and I did not check or change it. It may need a note about `API_TOKEN`.
