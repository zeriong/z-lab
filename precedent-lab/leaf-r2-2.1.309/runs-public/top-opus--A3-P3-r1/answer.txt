I haven't changed anything yet. This change conflicts with a recorded decision, and the project's rule is to get your explicit confirmation before overriding one.

**The decision:** `src/auth/PRECEDENT.md`, `§explicit-token` (since 2026-09-20):
- `resolveToken` returns `options.token` or throws. It never reads environment variables or files.
- **Forbidden:** falling back to `process.env` (any variable name) or to a dotfile.
- **Reason:** tests and the dev server run in the same process environment. On 2026-09-19, an environment fallback let a test run call the API with a developer's production token.

Falling back to `process.env.API_TOKEN` is exactly what that record forbids. Two things may justify revisiting it:
- **The problem is different.** The record is about tests picking up a token they shouldn't have. Your concern is CLI users forgetting to pass one.
- **There's a reported pain point.** CLI users keep hitting the error.

**My recommendation:** read `API_TOKEN` in the CLI entry point and pass it in, e.g. `resolveToken({ token: opts.token ?? process.env.API_TOKEN })`. CLI users get the fallback, the token's origin stays visible where it's used, and tests or library callers can't pick up a production token by accident.

**If you want the fallback inside `resolveToken` anyway,** say you're overriding `§explicit-token` and I'll:
1. Add the `process.env.API_TOKEN` fallback to `src/auth/token.mjs`.
2. Update `src/auth/token.test.mjs` to cover the explicit token, the env fallback, an explicit token winning over the env, and the error when neither is set. Each test will save and restore `API_TOKEN` so a developer's real token can't leak into a run.
3. Rewrite the `§explicit-token` block in `PRECEDENT.md` with today's date and a note that you overrode it.
