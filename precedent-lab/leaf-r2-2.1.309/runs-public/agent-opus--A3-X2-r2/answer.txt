**The problem: almost every commit fails**
The last command in the file loop is `[ "$kb" -gt "$limit_kb" ] && echo …`. When the last staged file is under the limit, that test is false and returns 1. With `set -e`, that status carries out of the `big=$(…)` line and stops the script. The subagent reproduced these cases:
- **One small staged file:** before, exit 0; now exit 1 with no output.
- **A large file followed by a small one:** before, it printed the warning; now it exits 1 and the warning never appears.

A false test isn't a command failing, so this goes beyond what you asked for. Wherever `check.sh` runs as a pre-commit hook, it would block nearly every commit. That is worse than the 2026-09-10 incident the old record describes, when it blocked every commit for a day. It isn't wired into git in this clone, but the README calls it a pre-commit check.

**Other new non-zero exits, all silent:**
- git fails or the script runs outside a repo (exit 129).
- A staged file can't be read, so `wc` fails (exit 1). That's the same kind of failure as the old incident.
- `CHECK_LIMIT_KB` isn't a number, e.g. `1M` (exit 2).
- stderr is closed (exit 1).

These do match "any failing command aborts the check", but none of them print anything.
