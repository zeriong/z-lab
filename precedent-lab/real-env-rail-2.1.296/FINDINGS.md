# FINDINGS — real-env-rail: 실사용 환경에서 graphify → 도착 → PRECEDENT 사슬 (2026-10-13)

대상: 비공개 EHR 레포 `fd3ef0c1`(10-10 실험과 같은 커밋), Claude Code 2.1.296 headless, 모델 `claude-opus-5-5`.
표본: P0 10런 + 본 실행 84런(실행 오류 재실행 5 포함) + x-isolate 18런. 자가보고 비용 합 P1 $180.76 · P0 $1.06 · x-isolate 약 $9.
표본(회사 소스 포함)은 이 저장소에 두지 않는다. 여기에는 명세·지표·판정 범주·스크립트만 있다. 지표는 `METRICS.md`, 판정은 `judgments.csv`·`x-isolate/`.

## 사용자 질문에 대한 답

| 질문 | 답 (실측) | 근거 |
|---|---|---|
| 왜 graphify + PRECEDENT 가 의도대로 읽히지 않는가 | 세 고리가 각각 다른 이유로 끊겨 있다. ① 현행 도착 훅은 **Read 도구에만** 반응하고 **포인터(≤400B)만** 낸다 — 근거 본문은 에이전트가 따로 읽을 때만 들어온다. ② graphify 는 라우팅 문장 없이는 한 번도 쓰이지 않았고, 써도 도착이 빨라지지 않았다. ③ 실사용 상주 context 의 41%는 memory·플러그인이다 | F2 · F6 · F1 |
| 어떻게 설정해야 의도대로 작동하는가 | 도착 시 **절 본문을 주입**(Read+Bash 읽기 감지)하면 「도착 직후·첫 편집 전에 근거가 context 에 있다」가 함정 과제 **45/45**(현행 10/15, p=0.0005). 비용은 늘지 않았다(중앙 −5%). memory·플러그인을 끄면 첫 턴 −41%, 비용 −20% 이고 사슬은 유지됐다 | F3 · F7 |
| 더 좋은 구성이 있는가 | 사슬을 고쳐도 **기록된 금지를 지키게 하지는 못했다**. 금지를 깬 비율을 가른 것은 사슬이 아니라 사용자 설정(effort `xhigh` 가 후보)이었다. 「도착하면 근거를 읽는다」는 이미 거의 성립하고, 남은 문제는 「읽은 근거를 요청 하나로 뒤집는다」다 — 이것은 context rail 이 아니라 구조(쓰기 게이트)로 막을 대상이다 | F4 · F5 |

## 발견

### F1 — 실사용 첫 턴의 41%는 memory·플러그인이다 (P0)
`ok` 만 답하게 한 첫 턴 입력: 실환경 55,023 토큰. memory 끔 41,098(−13,925, −25.3%), 사용자 플러그인 끔 46,399(−8,624, −15.7%), 둘 다 끔 32,474(−22,549, −41.0%). 두 효과의 합이 둘 다 끈 값과 정확히 같다(겹침 없음). 같은 설정 2회는 토큰 수가 완전히 같았다.
플러그인은 SessionStart 훅으로 8,051자를 넣는다(ponytail 지시문 전문 · frontend-conventions 19조 등). 10-10 실험 조건(`--setting-sources project`)은 39,321 이다.

### F2 — 현행 도착 훅은 「Read 도구를 쓴 런」에서만 울리고, 울려도 포인터만 준다
R arm 21런: Read 도구를 쓴 런 16, 현행 훅 발화 15. 10-10(project 설정)에서는 Read 도구 사용이 9/42 였다 — 실사용 설정에서 Read 사용이 늘어 발화도 늘었지만, 발화는 여전히 Read 에 묶여 있다.
훅이 내는 것은 「`PRECEDENT.md` 의 L6-L17 절만 읽어라」는 안내뿐이라, 근거가 context 에 들어오는 시점은 에이전트가 직접 읽는 시점이다. R arm 에서 그 시점이 도착 호출 +1 이내였던 런은 13/18, 도착→읽기 간격 중앙 1호출.

### F3 — 도착 시 절 본문 주입은 의도한 사슬을 함정 과제 45/45 로 만들었고 비용은 늘지 않았다
`hooks/precedent-inject.py`(Read|Edit|Write|MultiEdit|Bash, 관할 절 본문 ≤6,000자, 넘으면 결정·금지 줄 압축, 절이 없으면 디렉터리 목차):
- 함정 과제(T1~T5)에서 「PRECEDENT 가 도착 호출 +1 이내 · 첫 편집 전에 context 에 있음」: R 10/15 → I 15/15 · L 15/15 · G 15/15 (Fisher p=0.0005). 도착→PRECEDENT 간격 중앙 R 1 → 주입 arm 0.
- 첫 편집보다 PRECEDENT 가 먼저: R 20/21, 주입 arm 63/63.
- 주입량: 런당 중앙 3,295~5,645자(이벤트 2~6회). 비용 중앙 R $2.27 → I $2.16(−5%), 턴 중앙 25 → 20.
- 주입 이벤트의 절반가량(I 50/99)은 「이 파일 절 없음 → 디렉터리 목차」였다. 목적지 외 파일을 읽을 때마다 2.5k자가 들어간 것이라, 목차 주입은 줄일 후보다.
- 훅 출력은 stream-json 에 남지 않는다(SessionStart 만 남음). 주입은 훅 자신의 로그(`tool_use_id`)로 쟀다.

### F4 — 그러나 기록된 금지를 깬 비율은 사슬이 아니라 사용자 설정이 갈랐다 (effort `xhigh` 가 후보)
함정 T1~T4(프롬프트에 §24 무효화 사유 없음), arm 마다 12런, 금지를 깬 런(VIOLATED + RECORDED-INVALID):
R 11/12 · I 7/12 · L 9/12 · G 10/12 → 합 37/48. 10-10 r3(같은 커밋·CLI, project 설정) A·C·D 합 3/24 (p<0.0001).
arm 사이 차이는 유의하지 않다(R vs I p=0.16, R vs L p=0.59, L vs G p=1.0) — 주입도, 경량 상주도, graphify 도 이 비율을 바꿨다고 말할 수 없다.
네 arm 이 공유한 것을 하나씩 되돌린 x-isolate(T2·T3 × 3):

| 조건 | T2+T3 금지 깸 | 출력 토큰 중앙 | 턴 중앙 |
|---|---:|---:|---:|
| 본 실행(사용자 설정 전체) | 19/24 | — | — |
| project 설정만 | 1/6 | 3,003 | 4 |
| project + effort `xhigh` | **4/6** (T3 3/3) | 13,586 | 11 |
| project + language `korean` | 1/6 | 2,890 | 4 |

사전 고정 기준(T3 ≥ 2/3)을 넘은 것은 effort `xhigh` 하나다. 다만 n=3 이라 project 대비 p=0.24 — **원인 후보**이지 확정이 아니다. 사용자 `~/.claude/CLAUDE.md`·advisor·조합 효과는 가르지 않았다.

### F5 — 깨는 방식은 「기록을 고쳐 쓰며 뒤집기」였고, 넷 중 하나를 사칭하기도 했다
RECORDED-INVALID 32건 중 23건은 사유를 「사용자 지시」로 적었고, 9건은 프롬프트에 없는 「결함 지적(③)·반증」을 사유로 적었다(판정자 인용문의 자동 분류). 몇 런은 「되돌리는 사유로 다시 들지 않는다」처럼 이후의 무효화를 막는 문장까지 남겼다.
VIOLATED(기록 없이 금지 구현)는 10-10 에서 0/103 이었으나 이번 84런에서 5건(R1·L2·G2).
정당한 사유가 프롬프트에 있는 T5 는 **12/12 RECORDED-VALID**(네 arm 각 3/3) — 사유가 실제로 있을 때 그것을 알아보고 적는 능력은 있다. 깨지는 지점은 사유가 없을 때다.

### F6 — graphify 는 라우팅 문장 없이는 쓰이지 않았고, 써도 도착을 앞당기지 못했다
- R·I·L 63런: graphify 0회. G(라우팅 문장 + 최신 그래프) 21런 중 8런이 2~3번째 호출에서 graphify 를 썼다.
- 도착 전 누적 입력 토큰 중앙: L 173,410 vs G 175,950. 턴 중앙 L 17 → G 26, 비용 중앙 $1.81 → $1.97(+9%). G 의 비성공 종료 2건(예산·최대 턴)은 둘 다 T1.
- 결정론 probe(`evidence/graphify-probe.md`): 과제 프롬프트로 질의하면 대상 파일 2/7·결정 슬러그 3/7, 출력 14건 중 9건이 2,000토큰 예산에서 잘린다. 그래프를 최신으로 갱신해도 결과가 같았다.
- 10-10 이 지적한 「09-14 에 멈춘 그래프」는 지금 메인 체크아웃에서는 해소돼 있다(10-06 빌드, `pane-workspace` 노드 420). 그래프의 신선도가 문제의 중심은 아니었다.

### F7 — memory·플러그인을 끈 경량 상주는 사슬을 유지하며 20% 싸다
L(I + memory 끔 + 사용자 플러그인 끔): 첫 턴 중앙 32,847(−41%), cache_read 중앙 984k(R 2,039k), 비용 중앙 $1.81(R 대비 −20%), 의도한 사슬 함정 15/15, 금지 깸 9/12(R 과 차이 유의하지 않음).
memory 파일을 에이전트가 직접 읽은 호출은 84런 전체에서 2회(I) — memory 는 「읽히는 기억」이 아니라 「매 턴 내는 고정비」로 작동했다.

### F8 — 실사용 플러그인의 Stop 게이트가 편집 런의 턴을 늘린다
`zeriong-frontend-conventions` 의 Stop 게이트가 프론트엔드 파일이 바뀐 런에서 `convention-review` 스킬을 불렀다: R 10/21런(12회), I 8/21런(11회). 그런 런의 턴 중앙은 28~29 로 없는 런(15~20)보다 9~13턴 길다. 일부 런은 남은 예산이 없어 리뷰를 건너뛰었다고 최종 답변에 적었다.
같은 런의 최종 답변 첫 줄이 작업 결과가 아니라 「Convention Review 결과: PASS」인 경우가 여럿 있었다(R·I).

### F9 — 구조 점검 과제(R1·R2)
R1 은 R·I 6/6 이 「빠진 곳 1건」을 찾아 교체(CHANGED-OTHER), L 1/3·G 0/3. R2 는 전 arm 이 「빠진 곳 없음」(CHANGED-OTHER 3건은 부수 변경). 판정자는 R1 의 교체를 「규칙 정합 수정, 동작 동일」로 봤다. 이것이 arm 효과인지는 n 이 작아 말하지 않는다.

## 측정하지 않은 것

- 대화형 세션(권한 프롬프트·사람의 개입)에서의 재현. 모든 런은 headless bypass 다.
- effort 단계별 곡선(`high`·`max`), 사용자 `~/.claude/CLAUDE.md`·advisor 의 개별 효과, 조합 효과.
- effort `xhigh` 가 **코드 품질**에 주는 이득. 금지 준수만 쟀으므로 「effort 를 낮추면 좋다」고 말할 수 없다.
- Stop 훅 차단으로 늘어난 턴 수의 직접 계측(stream-json 에 Stop 훅 출력이 남지 않음). F8 은 Skill 호출로 간접 측정했다.
- 쓰기 게이트(금지 줄 수정 차단 등)의 효과 — 제안만 하고 재지 않았다.
- 모든 토큰·비용은 Claude Code 자가보고값이다.
