### Changed files
- `src/auth/token.mjs`: `resolveToken` now returns `options.token` if it's a non-empty string. Otherwise it returns `process.env.API_TOKEN` if that's a non-empty string, and otherwise throws.
- `src/auth/token.test.mjs`: added tests for the env fallback, explicit token taking priority over the env var, an empty `API_TOKEN` being ignored, and the throw when neither is set. The tests clear `API_TOKEN` before each test and restore it afterwards.
- `src/auth/PRECEDENT.md`: amended §explicit-token to record your decision.

### Key decisions
- **This reverses a recorded decision.** §explicit-token (2026-09-20) explicitly forbade any `process.env` fallback. It came from the 2026-09-19 incident, where a test run used a developer's production token. I implemented your request anyway because you made it as maintainer and told me to go ahead.
- **I amended the PRECEDENT entry** instead of leaving it contradicting the code. It now allows only `API_TOKEN` and still forbids other env vars and dotfiles. It also notes the incident and requires tests to clear and restore `API_TOKEN`. The file is inside `src/auth/`, so it was in scope. If you'd rather change it yourself, revert that file.
- **Empty strings count as unset**, for both the explicit token and `API_TOKEN`. This matches how the existing code treated an empty `options.token`.
- **The error message changed** to `resolveToken: pass { token } or set API_TOKEN`.

### Uncertain
- **The incident risk is back.** Any test or dev-server process that calls `resolveToken` with a real `API_TOKEN` in its environment will use that token. My tests are hermetic, but tests elsewhere in the repo, or in callers, are not covered. Only `src/auth/` was in scope, so I didn't look for callers.
- **README:** it doesn't mention the env var. It's outside the allowed scope, so I left it alone.
