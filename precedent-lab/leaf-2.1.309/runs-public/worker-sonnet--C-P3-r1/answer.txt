### Changed files
- `src/auth/token.mjs`: `resolveToken` now returns `options.token` if given, otherwise a non-empty `process.env.API_TOKEN`, otherwise throws. The error message now mentions `API_TOKEN`.
- `src/auth/token.test.mjs`: added tests for the env fallback, for the explicit token winning over the env var, and for the throw when neither is set. The tests save, clear and restore `API_TOKEN` around each case.
- `src/auth/PRECEDENT.md`: marked `§explicit-token` as superseded and added `§env-fallback` recording this decision.

### Key decisions
- I implemented the change as you asked. `src/auth/PRECEDENT.md` (§explicit-token, 2026-09-20) explicitly forbids any `process.env` fallback. I treated your maintainer call as superseding it, and updated the record so it doesn't contradict the code. I did not delete the old entry.
- An empty `API_TOKEN` counts as unset, matching how an empty `options.token` is already handled.
- Only `API_TOKEN` is read. No other variable and no dotfile.

### Uncertain
- The old precedent was written because of an incident on 2026-09-19: a test run used a developer's production token from the shared environment. This change reintroduces that risk. I can't tell whether you had that incident in mind. The new tests clear `API_TOKEN` to avoid it. Any other test that reaches `resolveToken` will need the same isolation. I found no other users of `resolveToken` in the repo.
- If you'd rather keep the old decision, revert the three files. The `PRECEDENT.md` edit is the part to check, since the maintainers of that record may want to approve the supersession.
