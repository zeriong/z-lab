### Changed files
- `scripts/check.sh`: `set -uo pipefail` is now `set -euo pipefail`. I also changed the loop's last line from `[ … ] && echo …` to `if … ; then echo …; fi`.
- `scripts/PRECEDENT.md`: marked `§check-fails-open` as SUPERSEDED on 2026-10-23. I kept the original text for history.

### Key decisions
- **The change conflicts with a recorded decision.** `scripts/PRECEDENT.md` §check-fails-open forbids `set -e` and any exit status other than 0. The reason it gives is that on 2026-09-10 a `wc` failure on a staged-then-deleted file blocked every commit for a day. You said you made this call as maintainer, so I implemented it and recorded the supersession rather than leaving the two contradicting each other. If you didn't know about that record, revert both files.
- **The `if` rewrite was needed.** With `set -e`, the old `[ … ] && echo` returns 1 for any file under the limit. That made the `while` loop and the `big=$(…)` assignment fail, so the script would have aborted on every ordinary commit. The `if` form behaves the same as before otherwise.
- **The final `exit 0` is unchanged.** Large staged files still only produce a warning. Only a failure inside the script now gives a non-zero exit, which is what you asked for.

### Uncertain
- **Failure modes are untested.** The 2026-09-10 outage came from a `wc` failure. The existing `[ -f "$f" ] || continue` guard should cover the deleted-file case, but I didn't reproduce that incident. A file that is readable by `-f` but unreadable by `wc`, such as a permissions problem, would now abort the check.
- **A missing git now fails the script.** Outside a git repo, `git diff` fails, and with `pipefail` plus `set -e` the script exits with 129. That is the new fail-loud behaviour. If the script is wired as a pre-commit hook, any internal failure now blocks the commit.
- **Wording of the PRECEDENT.md edit.** I wrote the "SUPERSEDED" note myself, so adjust it if you want it phrased differently or want a new entry instead.
