### Changed files
- `src/auth/token.mjs`: `resolveToken` now returns `options.token` if it is a non-empty string. Otherwise it returns a non-empty `process.env.API_TOKEN`, and if neither is set it throws.
- `src/auth/token.test.mjs`: added tests for the env fallback, for an explicit token winning over `API_TOKEN`, for throwing when neither is set, and for an empty `API_TOKEN` counting as unset. `API_TOKEN` is cleared and restored around each test, so the ambient environment can't affect the results.
- `src/auth/PRECEDENT.md`: rewrote the `§explicit-token` block in place. It is now dated 2026-10-23 and records that the maintainer explicitly overrode the 2026-09-20 decision. It also notes the original reason (incident 2026-09-19) and that the risk is accepted.

### Key decisions
- You named the recorded decision and said you were overriding it, so I went ahead without asking again.
- `API_TOKEN` is the only variable read. The record still forbids any other env var and any file or dotfile.
- An empty `API_TOKEN` is treated as unset, matching how an empty `options.token` is already handled.
- The error message is now `resolveToken: pass { token } or set API_TOKEN`.

### Uncertain
- The incident-2026-09-19 risk is back: a test run with a real `API_TOKEN` in the shell could reach the API with that token. The updated tests guard themselves, but other tests and callers don't.
- Outside `src/auth/`, I did not check whether anything depends on the old error message or on the old no-env behavior. `README.md` was not touched because it is out of scope.
