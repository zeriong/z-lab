## 발견

### R1 — 기록하라는 규칙이 없는 프로젝트에서는 훅 없이 거의 기록하지 않았다
- 훅 없는 arm 은 기록 없는 경로 0/9, 절이 있는 파일 2/9 를 기록했다.
- 같은 fixture 에 0.2.0 을 붙이면 절이 있는 파일이 8/9 가 됐다.
  - 0.2.0 이 주는 것은 절 본문 주입, 변경 확인 문구, Edit 알림(「새 결정이면 같은 변경에 블록으로 더하라」) 셋이다.
  - 셋 중 무엇이 차이를 냈는지는 가르지 않았다.
- E7 의 「기록 작동 미충족」(훅 없는 대조도 8/9)이 회사 상주 기록 규칙 때문에 생긴 천장이라는 해석과 이번 결과는 맞는다. 다만 그 규칙의 효과를 직접 잰 것은 아니다.

### R2 — 0.3.0 의 기록 없음 안내가 기록 없는 경로를 0.2.0 의 3/9 에서 8/9 로 올렸다
- 기록한 8런은 모두 대상과 같은 디렉터리에 `PRECEDENT.md` 를 만들었고, `## <파일>` 절과 한정어 없는 `- Decision:` 줄을 썼다.
- 0.2.0 의 3/9 는 안내 없이 다른 폴더의 기록을 읽고 그 형식을 따른 경우다. 카나리에서도 같은 모습이 보였다.
- 결정이 필요 없는 편집(Q)에서는 세 arm 모두 기록을 만들지 않았다(0/6). 안내가 군더더기 기록을 늘리지 않았다.

### R3 — 남은 미기록은 셸로 파일을 쓴 경우다
- v030 의 미기록 3런(N1 2런, U3 1런)은 모두 대상 파일을 `cat > file <<EOF` · `cat >> file <<EOF` 로 썼다.
- 훅은 셸 명령을 읽기일 때만 도착으로 본다. 그래서 세 런 모두 Edit 알림과 기록 없음 안내를 받지 못했다(0회).
- Write 도구로 쓴 런은 모두 기록했다.
- 따라서 이것은 안내의 실패가 아니라 전달 경로의 빈틈이다.
  - 후보: 관할 파일에 대한 셸 쓰기(`>`·`>>`·`tee`·`sed -i`)를 Edit 처럼 취급한다.
  - 바꾸면 새로 잰다(제9조).
