# 오프라인 노트 앱 저장 방식 결정

- 사고 프레임: constraint-first / 문체: opus
- 결정: 현재 범위에서는 **JSON 파일**을 사용한다. SQLite로 바꿀 조건은 아래에 명시한다.

## 제약부터 확인

저장소 선택에서 익숙한 데이터베이스를 먼저 고르기 쉽다. 여기서는 제약이 실제로 요구하는 기능부터 확인한다.

| 제약 | 영향을 받는 차원 | 결정에 미친 영향 |
|---|---|---|
| 로컬 사용자 한 명, 오프라인 | 실행 위치·접속 의존성 | 서버 운영과 호스팅 DB를 제외한다. |
| 동기화·동시 쓰기 없음 | 쓰기 주체·시점 | 충돌 병합이나 복수 작성자 조정을 설계하지 않는다. |
| 노트 필드는 `title`, `body` | 데이터 형태 | 관계형 모델을 필수로 두지 않는다. |
| 이번 산출물은 결정 문서 | 작업 범위 | 코드·설치·빌드 절차를 추가하지 않는다. |

제약의 교집합은 비어 있지 않다. JSON과 SQLite 모두 로컬에서 해당 필드를 저장할 수 있으므로, 제약만으로 어느 후보도 탈락하지 않는다. 호스팅 DB는 모순을 해결할 후보가 아니라 이미 제외된 범위 밖 요구다.

따라서 요구를 완화하거나 구조를 강제로 뒤집을 이유는 없다. 대신 “노트를 저장하려면 데이터베이스가 필수”라는 전제를 채택하지 않는다. 동시 쓰기를 위한 설계를 생략하는 것은 승인된 범위의 구체화이며, 저장 실패로 노트를 잃어도 된다는 완화가 아니다. 이 구분 때문에 JSON을 선택하면서도 실패 처리를 확인 대상으로 남긴다.

## 목표와 선택 근거

사람이 구현할 작은 앱의 저장 방식을 정한다. JSON에는 `title`과 `body`를 가진 노트 목록을 저장한다. 별도 저장 엔진 연결과 스키마 관리 없이 내용을 확인할 수 있다는 점을 우선한다.

대신 전체 파일 읽기·다시 쓰기 비용, 파일 교체와 오류 복구 처리는 앱이 맡는다. SQLite의 트랜잭션과 쿼리 기능을 당장 도입하지 않는 선택이며, 그런 기능이 불필요하다고 영구 판단하는 것은 아니다.

## 가정과 틀릴 때의 대응

- **전체 노트 목록을 읽고 다시 저장하는 방식이 실제 사용량에서 수용 가능하다.** 구현 담당자는 사용자가 예상하는 최대 사용량의 표본으로 읽기·저장을 측정하고 사용자가 수용하는지 확인한다. 맞지 않으면 노트 수 제한을 임의로 추가하지 말고 SQLite로 선택을 바꾼다. 현재 노트 수나 지연 기준은 주어지지 않았다.
- **선택한 런타임에서 파일 저장 실패를 처리하는 부담이 수용 가능하다.** 가장 이른 확인은 런타임의 파일 교체 기능과 실패 동작을 조사하는 것이다. 어렵다면 SQLite의 해당 런타임 지원과 트랜잭션 사용 비용을 비교해 전환한다. 파일 교체만으로 전원 장애 내구성이 보장된다고 가정하지 않는다.
- 복잡한 검색·정렬·부분 갱신은 현재 선택의 필수 요건이 아니라고 가정한다. 요구가 확인되면 SQLite를 다시 평가한다.

## 대안과 재검토 조건

| 후보 | 현재 판단 | 판단을 바꿀 조건 |
|---|---|---|
| JSON 파일 | 채택. 단순한 노트 목록에 맞고 내용 확인이 쉽다. 전체 다시 쓰기와 복구 부담을 감수한다. | 사용량 검증 실패, 파일 저장 안전성 구현 부담 증가, 쿼리 요구 등장 시 SQLite로 재검토한다. |
| SQLite | 보류. 트랜잭션·부분 갱신·쿼리가 유용하지만 현재는 엔진 연결과 스키마 관리 부담을 정당화할 요구가 확인되지 않았다. | 위 부담보다 저장 안전성이나 조회·갱신 기능의 이득이 커지면 채택한다. |
| 호스팅 DB | 제외. 사용자 결정과 로컬 오프라인 범위에 어긋난다. | 사용자가 로컬 전용 제약과 기존 제외 결정을 명시적으로 바꿀 때만 다시 논의한다. |

## 적용과 검증

아래는 구현 시 확인할 결정의 조건이며, 이번 작업에서 앱을 구현하라는 지시가 아니다.

| 조치 | 선행 조건 | 확인 방법과 연결된 제약 |
|---|---|---|
| 데이터 표현을 확인한다. | 독립적으로 수행 가능 | 빈 문자열·줄바꿈·한글이 포함된 `title`과 `body`를 저장 후 읽어 원문과 비교한다. 필드 보존 요건을 확인한다. |
| 전체 파일 처리 비용을 확인한다. | 예상 사용량 표본 확보 | 구현 담당자가 표본의 읽기·저장을 측정하고 사용자와 수용 여부를 판단한다. 작은 앱이라는 선택 근거를 검증한다. |
| 저장 실패 처리를 정한다. | 런타임·운영체제 결정 | 원본에 직접 덮어쓰는 방식을 피하고, 임시 파일 작성 후 교체와 실패 시 복구 경로를 확인한다. 단일 작성자라는 범위를 데이터 손실 허용으로 확대하지 않는다. |

## 위험과 미해결 사항

- 잘못된 JSON이나 저장 오류를 빈 노트 목록으로 취급해 덮어쓰지 않는다. 오류를 알리고 원본을 보존하는 동작을 구현 시 확인한다.
- 디스크 부족·앱 종료·전원 장애는 서로 다른 실패다. 요구 내구성 수준을 확인한 뒤 해당 실패 검증을 정한다. 이번 문서는 장애 시 무손실을 보증하지 않는다.
- 구현 언어·런타임·운영체제, 총량, 검색 요구, 내구성 수준은 미정이다. 현재 선택을 막지는 않지만 위 가정의 확인에 필요하다.
- 읽은 `source.txt`와 패킷의 요구 설명 사이에 충돌은 없다.

## 완료 기준과 구현자 계약

이번 결정 문서는 검토자가 JSON 채택 여부, 각 후보의 근거와 재검토 조건, 가정이 틀릴 때의 대응을 본문에서 모두 찾을 수 있으면 완료다. 분량 기준은 1500단어 미만이며 사용자 요구에서 도출되었다. 작성자가 공백으로 나눈 단어 수를 세어 확인한다.

후속 구현에서는 담당자가 위 데이터 표본을 저장하고 다시 읽어 모든 `title`·`body` 값이 일치하는지 비교한다. 실패하면 저장 동작을 수정한 뒤 다시 검증한다. 이 확인만으로 성능이나 내구성 검증을 대신하지 않는다.

구현자는 JSON 파일을 기본 선택으로 삼고, 적용 표의 가정 검증 결과에 따라 SQLite 전환을 판단한다. 런타임이 미정이므로 의존성 버전이나 실행 명령을 임의로 고정하지 않는다. 코드 구현과 실행 검증은 이번 산출물의 완료 조건이 아니다.

## Frame deviations & habit regressions

- 「목표와 선택 근거」에서 단순한 구성을 선호해 JSON으로 수렴했다. 가장 약한 근거는 미확인 사용량이다. 「가정과 틀릴 때의 대응」에 표본 검증과 SQLite 전환을 명시했지만 실제 측정은 남아 있다.
- 검토자라면 「적용과 검증」의 파일 교체·복구 부담이 SQLite 연결보다 정말 작은지 먼저 확인할 것이다. 런타임이 없어 이 비용 비교는 확정하지 못했다. 그 불확실성을 제품의 내구성 요구 완화로 처리하지 않았다.
