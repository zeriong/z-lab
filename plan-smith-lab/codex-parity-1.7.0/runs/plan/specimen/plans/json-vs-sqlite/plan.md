# JSON·SQLite 선택 계획

## 완료 기준
- A: 네트워크 없이 제목·본문을 저장하고 재시작하면 내용이 일치한다.
- B: 사람 구현자가 대상 환경에서 저장·읽기 절차와 의존성을 검증한다.

적격성: A 실패는 저장 설계를, B 실패는 구현 방식을 재선택하게 한다. A는 서버 필수 방식을, B는 미지원 방식을 배제한다.

## 목표·가정
프레임 backward / 스타일 opus. SQLite부터 고르는 습관 대신 완료 기준에서 출발한다.

**자료는 메모리에 들어가고 일괄 저장·읽기로 충분하다고 가정한다.** 틀리면 JSON을 재검토한다. 정상 저장 후 보존이 기준이며, 장애 내구성·언어·런타임·OS·자료량·검색은 미정이다.

## 접근·핵심 경로
교차: 로컬 저장은 A·B를 지원하지만, 파일 교체 실패는 A와 충돌한다. 안전성은 환경에 의존하므로 B 확인 후 A를 검증한다.

- 환경 확인(독립, B): 구현자가 예상 자료량과 JSON·SQLite 지원을 확인한다. 가정이 깨지면 SQLite를 먼저 평가한다.
- 저장 설계(환경 확인 후, A·B): 기본 지원되면 JSON을 잠정 선택한다. 임시 파일 작성 후 교체 절차·실패 처리를 검토한다.
- 검증(저장 설계 후, A·B): 향후 구현에서 사람이 한글·빈 본문 자료를 저장·재시작하여 원본과 대조하고, 갱신 실패 시 기존 파일 보존을 확인한다.

비앵커 요구도 구조를 바꾸지는 못하지만 범위에 남고 구현에 반영한다. 단일 사용자·동시성 없음·동기화 없음은 저장 설계에 반영한다. 명시 요구의 보류는 없다.

## 대안·위험·완료 계약
SQLite는 잠정 보류한다. 전체 갱신 부담·교체 안전성 미확인·검색 또는 트랜잭션 요구가 재검토 조건이다. 호스팅 DB는 사용자 거절로 제외하며 방침 변경 시만 재논의한다.

완료: 선택·가정·재검토 조건이 문서에 명시된다. 구현자는 위 검증 절차를 따른다. 런타임·버전·명령은 환경 미정으로 고정하지 않는다.

## Frame deviations & habit regressions
‘저장 설계’의 JSON 선호가 가장 약하다. 두 방식 모두 기준을 충족할 수 있어 단순성 관행이 개입했다. 검토자는 ‘환경 확인’에서 구현·유지보수 부담을 비교해야 한다. 유지보수는 측정하기 어려워 앵커에서 빠졌다.
