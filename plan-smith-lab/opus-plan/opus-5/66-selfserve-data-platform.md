# 사내 데이터 플랫폼 셀프서브 쿼리 인터페이스

- 추론 프레임: api-first
- 한 줄 요약: 분석가가 이미 치고 있는 SQL 10줄과 그 응답 봉투를 계약으로 동결하고, 조인 권한·개인정보 컬럼·스캔 비용 같은 애매한 케이스를 예외가 아니라 **정규 응답 행**으로 계약에 박제한 뒤, 내부 구조는 그 10줄이 참이 되는 방향으로만 설계한다.

## 프레임이 요구하는 시작점 — 분석가가 실제로 치는 10줄

반사적 습관은 시맨틱 레이어·지표 카탈로그를 먼저 세우는 것이다. 계약은 그것을 금지한다 — 분석가가 이미 가진 호출 지점(SQL 텍스트, 시트 임포트)을 전부 폐기시키기 때문이다.

```sql
-- 계약 v1 = 가설. 식별자는 자리표시자이며 0단계 채굴의 상위 질의 테이블·조인쌍으로 교체된다.
 1 SELECT dt, SUM(gmv) FROM mart.orders_daily WHERE dt >= '2026-07-01' GROUP BY dt;
 2 SELECT * FROM mart.orders_daily WHERE dt = '2026-07-30' LIMIT 100;
 3 SELECT o.dt, SUM(o.gmv) FROM mart.orders_daily o JOIN hr.employees e USING (user_id) GROUP BY 1;
 4 SELECT u.email, SUM(o.gmv) FROM mart.users u JOIN mart.orders_daily o USING (user_id) GROUP BY 1;
 5 SELECT u.email, COUNT(*) FROM mart.users u GROUP BY 1 HAVING COUNT(*) < 3;
 6 SELECT SUM(gmv) FROM mart.orders_daily;                       -- 파티션 필터 없음
 7 =QUERY("gmv_by_channel", {"from":"2026-07-01","to":"2026-07-31"})   -- 시트 셀 호출
 8 SELECT dt, SUM(gmv) FROM mart.orders_daily AS OF '2026-07-30T09:00Z' GROUP BY dt;
 9 SELECT a.email, b.plan FROM mart.users a JOIN crm.accounts b ON a.email = b.email;
10 DELETE FROM mart.orders_daily WHERE dt = '2026-07-30';
```

응답 봉투(계약의 기대 출력 절반). 결과 그리드 = 요청 표현식의 컬럼 + 항상 붙는 메타 컬럼
`_query_id · _as_of · _status(ok|masked|refused) · _reason_code · _next_action · _suppressed_groups · _scanned_bytes`

각 줄의 판정:

| 줄 | 판정 | 계약 조항 |
|---|---|---|
| 1·2 | `ok / NONE` | 2번은 미리보기 경로 — 비용 게이트의 정식 탈출구 |
| 3 | `refused / JOIN_GRANT` | 권한 부족이 **숫자를 바꾸는** 실패 → 거절. 조인을 조용히 좁혀 작아진 GMV를 주지 않는다 |
| 4 | `masked / PII_MASKED` | 표시만 가리는 실패 → 마스킹. `***masked***` 센티널, 합계는 그대로 |
| 5 | `masked / K_SUPPRESSED` + `_suppressed_groups=N` | 가명은 **컬럼 내에서만 안정** → 그룹화 가능. 단 그룹 크기 < k인 행은 억제하고 억제 건수를 보고 |
| 6 | `refused / SCAN_BUDGET` | 사전 추정 단계에서 거절, 스캔 0바이트. `_next_action`에 파티션 필터 리라이트 제안 |
| 7 | `ok / NONE` | 저장 질의를 이름+파라미터로 호출. 시트가 유일 호출 지점인 분석가의 계약면 |
| 8 | `ok / NONE` | 같은 `_as_of`로 재실행하면 바이트 동일 결과 — 숫자 재현성 |
| 9 | `refused / MASKED_JOIN_KEY` | 가명은 **테이블 간에는 불안정**(솔트가 컬럼 단위) → 마스킹 컬럼을 조인 키로 쓰면 거절. 5번의 그룹화 허용과 재식별 차단을 한 조항으로 양립시킨다 |
| 10 | `refused / READ_ONLY` | 읽기 전용 계약 |

**거절도 HTTP 오류가 아니라 1행 그리드로 반환된다** — 시트 임포트 경로가 오류를 조용히 삼키고 셀을 비워두기 때문. 이 한 줄이 API 형태(오류 코드 중심)를 데이터 형태(정규 응답 행)로 뒤집는다.

7번(시트 셀 호출)의 봉투 착지: 데이터 범위 **첫 행 위에 `_status · _reason_code · _next_action` 3필드 헤더 블록**이 붙고, 나머지 4개 메타는 두 번째 이름 범위 `_meta`로 분리된다. 거절은 데이터가 0행이어도 헤더 블록으로 반드시 눈에 보이며, 시트 사용자가 메타 7컬럼을 항상 지고 다니지 않는다. 두 경로의 등가성은 `t_sheet_cell_visibility`가 검사한다.

계약이 고정하는 것: 메타 컬럼의 존재와 이름, `_reason_code` 값 집합(아래 레지스트리 전량 — 열거되지 않은 값은 계약 위반), 센티널 문자열, 가명의 안정 범위(컬럼 내 안정/테이블 간 불안정), 요청 표현식의 컬럼명, **`_next_action`이 구체적 다음 행동(승인 요청 대상 또는 리라이트 예시)을 지목한다는 요건**.
자유로 남기는 것: `_next_action`의 문면, `ORDER BY` 없을 때의 행 순서, 실행 엔진, 하위호환 메타 컬럼 추가. → 행 순서를 계약에서 뺀 결과 **엔진 교체가 파괴적 변경이 아니게** 되고, 문면을 뺀 결과 거절 메시지 개선이 파괴적 변경으로 읽히지 않는다. 문면은 자유지만 "지목 대상이 있어야 한다"는 요건은 고정이므로, 판정 기준 3은 문장 다듬기로는 움직이지 않는다.

`_reason_code` 레지스트리 (동결. 값 7개 — S1 규칙대로 각 값이 `_next_action` 지목 대상 1개와 테스트 1개를 갖는다):

| `_reason_code` | `_status` | `_next_action`의 지목 대상 | 테스트 |
|---|---|---|---|
| `NONE` | `ok` | 없음 — `ok` 행의 `_reason_code`는 빈 문자열이 아니라 문자열 `NONE`이고 `_next_action`은 빈 문자열로 고정 | `t_reason_code_none_on_ok` |
| `JOIN_GRANT` | `refused` | 해당 테이블의 권한 승인자(카탈로그 소유자 필드) | `t_refusal_not_narrowing` |
| `SCAN_BUDGET` | `refused` | 파티션 필터를 넣은 리라이트 예시 SQL, 또는 2번 미리보기 경로 | `t_cost_gate_zero_bytes` |
| `MASKED_JOIN_KEY` | `refused` | 원본 조인 키 사용 승인 대상 — 해당 컬럼의 개인정보 담당자(카탈로그 PII 소유자) + 승인 시 사용할 대체 조인 키(`user_id`) | `t_masked_join_key_refused` |
| `READ_ONLY` | `refused` | 쓰기 요청 접수 채널 — 데이터팀 적재 변경 요청 큐(`_query_id` 첨부) | `t_read_only_refused` |
| `PII_MASKED` | `masked` | 마스킹 해제 요청 대상 — 해당 컬럼의 개인정보 담당자 | `t_pseudonym_scope` |
| `K_SUPPRESSED` | `masked` | 억제를 피하는 리라이트 — 그룹 키를 상위 차원으로 올리는 예시 | `t_kanon_suppression_count` |

계약이 SQL 텍스트로 표현할 수 없는 조항(발생 시점·상호작용·문면 대비 필드)은 산문 문서로 새지 않도록 같은 코퍼스의 **이름 붙은 테스트**로 묶는다: `t_refusal_not_narrowing`, `t_sheet_cell_visibility`, `t_cost_gate_zero_bytes`, `t_masked_join_key_refused`, `t_kanon_suppression_count`, `t_as_of_byte_identical`, `t_pseudonym_scope`, `t_read_only_refused`, `t_reason_code_none_on_ok`. (9개 = 레지스트리 7개 + 경로 등가성 1개 + 재현성 1개.)

## 문제 정의 / 목표

분석가의 질의가 데이터팀 사람을 거쳐야 하고(권한·개인정보 판단이 사람 판단으로 남아 있어서), 그 판단이 매번 달라져 같은 지표가 다른 숫자로 유통된다. 목표는 도구를 늘리는 것이 아니라 **애매한 케이스의 판정을 지금 문서에서 결정해 계약에 박아, 실행 시점에 판단이 필요 없게** 만드는 것이다. 성공은 "셀프서브 비율"이 아니라 "조용히 틀린 숫자 0건"이다.

## 명시적 가정

| 가정 | 틀렸을 경우의 영향 |
|---|---|
| **요청의 다수가 이미 SQL 텍스트 형태로 도착한다** | 계약의 단위가 틀린 것 → 전면 재범위. 최저비용 확인: 0단계에서 요청 100건을 SQL/시트수식/산문으로 하루 태깅. 폴백: 계약 단위를 7번 줄(시트 저장 질의 호출)로 옮기고 봉투 계약은 위의 헤더 블록 형태로 그대로 유지 |
| 개인정보 컬럼이 카탈로그에 태깅돼 있거나 태깅 가능하다 | 마스킹 자동화 불가 → 미태깅 컬럼은 기본 거부로 전환, 태깅 작업이 S1의 선행 조건이 된다 |
| 권한이 테이블 단위로 부여돼 있다 | 행 단위 권한이면 3번의 "숫자를 바꾸는 실패" 판정이 행 수준까지 확장돼야 하고 마스킹/거절 이분법이 깨진다 |
| 질의 엔진이 실행 전 스캔량 추정을 제공한다 | 6번이 사후 킬로 바뀜 → 소각 바이트 예산 + 강제 종료로 대체(스캔 0바이트 보장은 포기) |
| 시트 임포트 경로가 응답 본문을 셀로 렌더한다 | 거절-as-데이터의 근거가 사라짐 → 별도 알림 채널 필요, `t_sheet_cell_visibility`가 실패 게이트로 작동 |

## 접근 및 단계

| 단계 | 선행 | 내용 | 검증 |
|---|---|---|---|
| S0 채굴 | 독립 | 요청 채널 90일 + BI 질의 로그를 긁어 요청 형태 3분류, 상위 질의 테이블·조인쌍·거절 사유 분포 산출 | **게이트(기본 분기 포함)**: 표본의 무수정 파싱률 ≥ 80%면 계약 v1 유지. 미달 시 실패가 dialect 기능에 몰리면 원문 통과(passthrough) 확장, 산문 요청에 몰리면 계약 단위를 7번 줄로 이동(봉투 불변). 표본 = 90일 전량, 상한 192건 |
| S1 계약 v2 동결 | S0 | 10줄을 고정 데이터셋 + 기대 봉투 픽스처로 전환, 사유 코드/센티널 레지스트리와 이름 붙은 테스트 9개 등록 | 구현 전 전부 red. 사유 코드는 각각 `_next_action` 문자열 1개와 테스트 1개를 가진다 — 없는 코드는 삭제 |
| S2 거절/마스킹 판정 규칙 | S0(실제 조인쌍) + S1 | "숫자를 바꾸는 실패 = 거절 / 표시만 가리는 실패 = 마스킹"을 상위 20개 실제 조인쌍에 적용해 표로 확정 | 플랫폼 1명 + 분석가 1명이 독립 분류해 20건 중 불일치 ≤ 2건, "상황에 따라" 판정 0건. 불일치는 규칙 문장을 고쳐 재분류 |
| S3 비용 게이트 | S1 (S2와 병렬) | 사전 추정 → 예산 초과 시 스캔 0바이트 거절 + 리라이트 제안 | `t_cost_gate_zero_bytes` 통과 + 채굴 코퍼스에서 추정/실측 오차 기록 |
| S4 호출 지점 어댑터 | S1·S2 | 시트 임포트(헤더 블록 + `_meta` 범위), 저장 질의 이름 호출 | 실제 시트에서 `t_sheet_cell_visibility` — 3번 거절이 셀에 보이는지 |
| S5 섀도 파일럿 | S2·S3·S4 | 분석가 5명 2주(판정 기준 3의 거절 30건에서 역산 — 아래 수치 태그. 판정 기준 1의 diff는 섀도 러너가 채굴 표본을 재생하므로 인원과 무관하다). 채굴 표본을 구/신 경로 동시 실행해 diff | 조용한 숫자 불일치 0건 + 적대 과제(아래) |
| S6 코퍼스 운영 규칙 | S1 | 예시 상한 24건(분기 리뷰 2시간 ÷ 건당 5분), 사유 코드당 예시 ≤ 3(24 ÷ 레지스트리 7값 = 3.4 → 내림), 90일 로그 히트 0이면 은퇴 | 의도적 파괴 변경 1건 리허설 — 계약 변경이 테스트를 red로 만드는지 |

## 대안과 기각 사유

- **자연어→SQL 인터페이스를 계약면으로**: 같은 문장이 다른 SQL을 낳으면 숫자 재현성이 없고, 거절/마스킹 경로가 프롬프트 문면으로 흐려진다. 부활 조건: S0에서 산문 요청이 60% 이상이고 동일 문장→동일 SQL 재현율이 표본에서 95% 이상 측정되면, NL을 계약 **위**가 아니라 **아래**(SQL 생성기)에 둔다.
- **시맨틱 레이어/지표 카탈로그 선행**: 계약 대상이 분석가의 세계가 아니라 우리 모델링 취향이 된다. 부활 조건: 동일 지표를 다르게 계산한 사건이 한 분기에 2건 이상 관측되면 계약의 하위 뷰로 도입.
- **기존 BI 툴의 권한 UI만 개선**: 애매한 케이스가 여전히 사람 판단으로 남는다. 부활 조건: S0의 거절 사유 분포에서 90% 이상이 모호성 없는 단순 권한 누락일 때.

## 리스크 & 완화

| 범주 | 완화 |
|---|---|
| 재식별 | 가명 솔트를 컬럼 단위로 → 9번 거절. 5번 k 미달 그룹 억제 |
| 규제·감사 | 개인정보 접근·마스킹 해제 요청을 `_query_id` 단위로 보존, k 초기값과 마스킹 정책은 S1 전 법무 검토 |
| 비용 | S3 사전 게이트 + 2번 미리보기 경로 + 동시 실행 수 상한 |
| 조직(권한 승인) | 거절의 `_next_action`이 막다른 길이 되지 않게 grant 요청 처리 중위 시간을 파일럿에서 실측하고, 초과 시 거절 코드에 임시 승인자 지정 |
| 오독·신뢰 | 조용한 축소 금지(3번), `_as_of` 필수 노출(8번) |
| 운영 부담 | S6 코퍼스 상한·은퇴 규칙 |
| 성능·신선도 | `_as_of` 지연을 봉투에 노출, 지연 초과 시 `masked`가 아닌 경고 행 |
| 마이그레이션 | 기존 저장 질의는 S5 섀도 diff를 통과한 것만 이전, 실패분은 원문 유지 |
| 학습 곡선 | 거절 메시지가 곧 문서 — `_next_action`이 다음 행동을 문장으로 지시 |
| 계약 경화 | 자유 목록(문면·행 순서·엔진) 명시로 개선이 파괴 변경으로 읽히는 것을 차단 |

## "완료"의 판정 기준

1. **채굴 표본에서 무작위 30건을 구 경로와 신 경로에 동시 실행 → 집계 숫자가 완전히 일치하거나, 불일치 건은 전부 `refused`/`masked` 표시를 동반한다(경고 없는 불일치 0건).** 측정: 플랫폼팀이 섀도 러너 diff 리포트로, 파일럿 2주간 매일.
2. 적대 과제: 분석가 2명에게 "마스킹된 이메일을 재식별하거나 권한 없는 조인의 숫자를 얻어내라"는 과제를 주고 **1인당 시도 10회, 파일럿 2주 안에 소진**한다. 모든 시도는 `_query_id`로 로그에 남고, 성공 건수는 공격자 크레딧으로 기록한다. 성공 1건 이상 → S2 규칙 수정 후 파일럿 연장. 시도 20회가 소진되지 않으면 "성공 0건"은 결과로 세지 않는다. (적대 검증 장치는 failure-first 프레임에서 차용.)
3. 파일럿 중 발생한 거절 30건 중 분석가가 사람에게 되묻지 않고 `_next_action`만으로 다음 행동을 완료한 비율 ≥ 70%. 측정: 요청 채널에서 해당 `_query_id` 언급 여부를 카운트.
4. 이름 붙은 테스트 9개가 CI에서 green이고, 계약 변경 리허설 1건이 red를 발생시켰다.

수치 태그:

- **임의 초기값** — 무수정 파싱률 80%·불일치 ≤ 2/20·자력 해결률 70%·시도 10회/인. 대체 시점은 각각 S0 종료일·첫 분류 실측·파일럿 종료일·첫 적대 과제 소진일(측정자 플랫폼팀).
- **임의 초기값(추가)** — 판정 1의 무작위 30건: 대체 시점 S0 종료일, 채굴된 질의 유형 분포로 층화 표본 크기를 재산정(측정자 플랫폼팀). 판정 3의 거절 30건: 대체 시점 파일럿 1주차 종료일, 실제 거절 발생량으로 재조정(측정자 플랫폼팀) — 이 값이 바뀌면 아래 파일럿 규모도 같이 바뀐다. 가정 표의 요청 100건: 1인 1일 태깅 가용량의 대략치이며(태깅은 분류만이라 검수의 건당 5분보다 빠르지만 그 요율이 미측정이라 도출로 승격하지 않는다), 대체 시점은 S0 1일차 종료 — 실측 태깅 속도로 재산정(측정자 플랫폼팀).
- **도출** — 표본 상한 192건 = 검수 2인 × 1일(검수 가용 8시간 = 480분) ÷ 건당 5분. (반올림하지 않는다 — 200으로 올리면 초과 8건이 예산 밖 40분이 된다.) 코퍼스 상한 24건 = 분기 리뷰 2시간(120분) ÷ 건당 5분. 사유 코드당 예시 ≤ 3 = 24건 ÷ 레지스트리 7값 = 3.4 → 내림 3. 파일럿 규모 5명 2주 = 판정 3의 거절 30건 ÷ 분석가 1인당 주 3건 거절 발생 = 10 인·주 → 5명 × 2주. (판정 1의 diff 30건은 인원이 아니라 섀도 러너가 만들므로 규모의 근거가 아니다. 분모 "주 3건"은 S0 거절 사유 분포의 1인당 빈도로 S0 종료 시 실측 대체되며, 실측이 더 낮으면 인원이 아니라 기간을 늘린다.)
- **도메인 관행** — k 초기값 5. 법무 검토로 대체된다.
- **의도적 공백** — 스캔 예산 바이트. 산식은 `월 질의 예산 ÷ 월 질의 건수 = 건당 허용 비용 → 바이트 환산`이고, 입력은 재무·플랫폼팀이 S3 착수일에 기입한다.

## 프레임 이탈 / 관성 회귀

- S0→S6이 의존 순서로 정렬돼 있지만 S3(비용 게이트)만 S2와 병렬임을 표시했다. 나머지는 실제로 직렬이며, 사다리처럼 읽히는 것은 계약 동결이 모든 하위 작업의 선행이기 때문이다 — 상승 서사가 아니라 단일 병목이다.
- 파일럿(S5)은 이 스타일의 안전한 기본값이다. 다만 파일럿이 "규모를 늘리는 단계"가 아니라 판정 기준 1의 diff를 얻기 위한 계측 장치로만 쓰이는지는 실행 시점에 다시 확인해야 한다.
- 가장 약한 절: 리스크 표의 "성능·신선도" 행. 지연 초과 시 경고 행을 준다고만 썼고, 어떤 지연이 초과인지 계약에 박지 못했다(다른 수치들처럼 임의 초기값을 두는 대신 공백으로 남겼다).
- S1이 "사유 코드는 각각 `_next_action` 1개와 테스트 1개를 가진다"고 못박았는데 처음 초안은 READ_ONLY와 마스킹 계열에서 그 규칙을 스스로 깼고, `_reason_code` 값 집합도 열거하지 않은 채 "고정"이라고 선언했다. 수정 이력에서 레지스트리 표를 열거하고 테스트를 7개→9개로 늘려 해소했다 — 규칙을 세우는 문장과 코퍼스를 채우는 작업이 분리돼 있으면 다시 깨질 자리다.
- 리뷰어라면 공격할 곳: 봉투가 두 형태로 갈라진 점 — SQL 경로는 메타 7컬럼, 시트 경로는 헤더 블록 3필드 + `_meta` 범위다. 두 형태의 등가성이 `t_sheet_cell_visibility` 하나에만 걸려 있고, 시트 경로가 계약 단위로 승격되는 폴백 상황에서는 그 테스트가 계약 전체의 유일한 지지대가 된다.
