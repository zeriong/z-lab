# 하루 1억 이벤트 로그 수집 파이프라인

- 추론 프레임: envelope
- 한 줄 요약: 일 1억 건은 처리량 문제가 아니다(평균 1,157 eps) — 산수가 지목하는 병목은 쓰기 단위 크기·쿼리 스캔량·저장 부피이며, 버퍼 계층은 초당 처리량이 아니라 "싱크가 죽어 있어도 되는 시간"을 사기 위해 도입한다.

## 프레임이 요구하는 시작점 — 설계 전 자릿수 계산

이 절에서는 제품·아키텍처 고유명사를 쓰지 않는다. 단위 명사(이벤트, 행, 객체, 파티션, 코어, 바이트)만 쓴다.
투입: 일 1억 건, 평균 직렬화 1 KB, 일주기 피크 3배·순간 10배, 압축비 8:1, 보존 1년. 전부 §가정에서 수명이 관리된다.

### (1) 각 축을 두 번 읽기 — 비율로, 그리고 부피로

| 축 | 비율 | 부피 | 무서운 쪽 |
|---|---|---|---|
| 건수 | 1,157 eps 평균 | 1년 365억 행 | 부피 |
| 바이트 | 1.2 MB/s, 피크 12 MB/s | 100 GB/일, 원본 36.5 TB/년 | 부피 |
| 스파이크 | 10배 = 11,600 eps | 5분 버스트 3.5 GB, 싱크 72시간 정지 시 300 GB 적체 | 부피 |
| 쓰기 요청 | — | 128 MB로 묶으면 781개/일, 이벤트당 1개면 1억 개/일 | 부피 |
| 비용 | $/일 | 3년 누적 | 둘 다 |

비율로는 세 축 모두 사소하다. 12 MB/s는 노트북 업링크 수준이고 1,157 eps는 단일 프로세스가 처리한다. 처리량은 이 워크로드의 설계 변수가 아니다.

### (2) 자릿수

- **컴퓨트**: 코어당 5,000 eps로 보면 평균 0.25코어, 피크 2.5코어. 결론 "한 자릿수 코어"는 계수가 2배 틀려도 같다.
- **저장**: 압축 후 12.5 GB/일 → 1년 4.6 TB, 3년 13.7 TB. $0.023/GB·월이면 12개월차 월 $105, 36개월차 $315. 무압축이면 36.5 TB/년, 월 $840 — 압축은 성능 장치가 아니라 **8배 비용 레버**다.
- **쓰기 요청**: $0.005/1,000요청. 781객체/일 = 월 $0.12. 이벤트 단위로 쓰면 1억 요청/일 = **월 $15,000**. 같은 데이터, **5자릿수 차이.** 지배 비용 변수는 초당 건수가 아니라 쓰기 단위 크기다.
- **쿼리 스캔**: $5/TB. 프루닝이 듣는 질의(파티션 2개 × 컬럼 3개 ≈ 5 GB) 100회/일 = 월 $75. 실패해 30일 전체(375 GB)를 훑으면 37.5 TB/일 = **월 $5,600**, 저장비의 18배.
- **파티션 입도**: 일 단위 = 파티션 하나 12.5 GB(최소 스캔 단위 과대). 분 단위 = 1,440객체/일 × 8.7 MB(소객체+메타데이터 오버헤드). 시간 단위 = 417만 행 ≈ 520 MB. 수백 MB 대역에 드는 것은 시간 단위뿐 — **시간 파티션은 취향이 아니라 산수의 출력이다.**
- **버퍼**: 정지 72시간 흡수 = 원본 300 GB, 3부 복제 시 디스크 900 GB, 복제 트래픽 200 GB/일 × $0.01 = 월 $60. (72시간 = 금요일 저녁 장애가 월요일 오전 인지되는 최악 경로 62~66시간 + 여유.)
- **총계**: 좋은 쪽 월 $500(컴퓨트 $100·버퍼 $200·저장 $105·전송 $60·쿼리 $75), **나쁜 쪽 월 $6,000** — 변동 전부가 쿼리 스캔에서 온다. 어느 쪽이든 운영 인력 0.5명의 인건비보다 작다 → **비용 최적화보다 운영 부담이 상위 제약.**

## 문제 정의 / 목표

일 1억 건의 제품 이벤트를 누락 없이 받아 1시간 지연으로 분석 가능하게 적재하고 월 비용을 위 자릿수 안에 묶는다. 성공은 "빠르다"가 아니라 ① 싱크 장애 구간 누락 0 ② 쓰기 요청비가 총액의 소수점 ③ 대표 질의 스캔량이 예산 내. 실시간 경보는 범위 밖이다.

## 명시적 가정

- **평균 이벤트 크기 1 KB.** 저장 부피·파티션 입도·쓰기 단위·전송비가 모두 여기에 비례한다. 틀리면: 5 KB에서 500 GB/일, 저장 월 $1,500+, 시간 파티션 2.6 GB로 과대 → 파티션 축 재설계. 가장 싼 조기 검증: 실제 이벤트 10만 건 표본의 직렬화 p50/p95(S0, 반나절). 깨졌을 때 경로: 필수 필드 화이트리스트로 스키마 감축 → 그래도 3 KB 초과면 비필수 타입에 샘플링 게이트.
- 압축비 8:1. 틀리면 3:1에서 저장·전송 2.7배지만 월 $1,000 미만으로 자릿수 유지.
- 순간 피크 10배. 틀리면 20배에서 5분 7 GB, 엣지 디스크 여유 재계산.
- 코어당 5,000 eps. 틀려서 1,000 eps여도 피크 12코어로 결론 불변.
- 중복 허용(at-least-once). 틀리면 쿼리 시점 제거로 미루는 이 설계가 무효.
- 이벤트는 자사 클라이언트·서버에서만 발생. 틀리면 인증·쿼터·유입 방어가 엣지의 주 기능이 되어 컴퓨트 계산이 무의미.

## 민감도 — 어떤 가정이 몇에서 결론을 뒤집는가

| 가정 | 기준 | 뒤집히는 점 | 무엇이 죽는가 |
|---|---|---|---|
| 평균 크기 | 1 KB | 5 KB | "전량 원본 보관"이 죽고 스키마 감축·샘플링이 강제됨 |
| 일 건수 | 1억 | 5억 | 시간 파티션 2.6 GB → 두 번째 파티션 축(이벤트 타입) 필수 |
| 순간 피크 | 10배 | 20배 | 엣지 디스크만의 버스트 흡수가 죽음 → 배압 규약 필요 |
| 목표 지연 | 1시간 | 5분 미만 | 배치 상한 128 MB→5 MB, 객체 2만 개/일, 요청비 25배 → **대안 1이 죽는다** |
| 쿼리 스캔 | 일 200 GB | 일 2 TB | 쿼리비가 저장비 초과 → 정렬키·사전집계 도입 |
| 보존 | 1년 | 3년 + 무압축 요구 | 110 TB, 월 $2,500 |
| *(비수치)* 개인정보 삭제 요구 | 없음 | 주체 단위 삭제 의무 | **불변 객체 전용 저장이 죽는다** → 주체별 키 암호화 후 키 폐기, 또는 파티션에 주체 해시 축 |
| *(비수치)* 최소 보존 의무 | 없음 | 감사·법정 보존 지정 | 트리거 E의 무조건 적용이 죽음 → 타입별 예외 목록 선행 |
| *(비수치)* 데이터 주권 | 단일 리전 | 리전 고정 규제 | 저비용 리전 이전이라는 비용 카드가 죽음 |
| *(비수치)* 품질 하한 | 균일 | 과금 유도 이벤트 누락 0 | 전역 샘플링이 죽음 → 샘플링은 비필수 타입 한정 |
| *(비수치)* 운영 인력 | 0.5명 | 0.2명 | 자체 운영 브로커 선택지가 죽음(§대안 2) |

## 접근 및 단계

번호는 의존성 순서다. S0과 S4는 서로 무관하고 S1만 공유하므로 S4는 S2·S3와 병렬로 간다.

- **S0 — 투입 숫자 실측**(선행: 없음/병렬). 표본 10만 건의 직렬화 p50/p95, 1주 분당 카운트 max/mean, 표본 실압축비. 검증: 세 값이 §가정을 확인 또는 대체. 근거: (2)의 저장·파티션·버퍼 계산 전부가 이 세 수에 매달림.
- **S1 — 스키마·쓰기 단위 확정**(선행: S0의 크기). 필수 필드 화이트리스트, 목표 객체 128~256 MB, 파티션 키 = 수신 시각(시간) + 이벤트 타입, 컬럼형 + 블록 압축. 검증: 하루치 처리 후 객체 500~1,500개, 중위 크기 ≥ 64 MB. 근거: 요청 단가 5자릿수 차이, 파티션 입도 산수.
- **S2 — 수집 엣지**(선행: S1의 포맷). 수신 → 로컬 append-only 버퍼 → 배치 업로더. 노드 2대는 가용성용이며 용량용이 아니다(0.25코어). 검증: 12,000 eps 5분 주입(3.5 GB) 동안 손실 0, 로컬 큐 최대 적재 < 디스크 50%.
- **S3 — 내구성 버퍼 계층**(선행: S2 동작). 목표는 정지 72시간 무손실 = 원본 300 GB / 복제 후 900 GB. 검증: 싱크를 6시간 의도 차단 후 복구 → 누락 0, 적체 해소 ≤ 차단 시간 × 1.2.
- **S4 — 쿼리 계층·수명주기**(선행: S1의 파티션 키 / S2·S3와 병렬). 시간 파티션 프루닝, 90일 후 콜드 계층, 1년 후 삭제(보존 의무 예외 목록 우선). 검증: 대표 질의 10개 스캔 합 < 일 200 GB.
- **S5 — 계측의 계측**(선행: S3, S4). 수신 건수, 객체 수·중위 크기, 일 스캔 바이트, 항목별 청구액을 일 1회 기록. 검증: 아래 트리거의 임계값 전부가 이 대시보드 하나에서 읽힌다(운영 상한: 주 1회 점검).

## 재설계 트리거 (숫자로 선약속)

- **A(상향)** 7일 이동평균 일 수집 > 3억 → 파티션 축 추가. 근거: 3배에서 시간 파티션이 1.5 GB를 넘어 (2)의 수백 MB 대역을 벗어남.
- **B(상향)** 7일 중위 이벤트 크기 > 3 KB → 스키마 감축 심사. 근거: 5 KB에서 민감도 표가 설계를 뒤집으므로 그 앞에 세운 경보선이고, 3배는 저장·전송 예산 3배 지점.
- **C(상향)** 월 쿼리 스캔비 > 월 저장비 → 정렬키·사전집계. 근거: (2)의 두 곡선 교점.
- **D(상향)** 엣지 버퍼 최대 적재 > 디스크 50% → 버퍼 증설. 근거: 50%는 잔여 지속 시간 = 현재 지속 시간을 보장해 인지·대응 시간을 남김.
- **E(하향)** 어떤 이벤트 타입이 90일간 어떤 질의에도 스캔되지 않음 → 수집 중단 심사, 기본값 중단. 근거: 90일은 최장 정기 리포트 주기(분기)를 한 번 포함하는 최소 창.
- **F(하향)** 일 수집 < 1천만이 3개월 지속 → 버퍼 계층 철거, 엣지 직접 배치로 축소. 근거: 1천만이면 원본 10 GB/일, 72시간분 30 GB가 엣지 디스크에 들어감.

## 첫 실측 마일스톤 (손으로 고른 값의 수명)

| 값 | 현재 | 첫 실측 | 측정자·시점 |
|---|---|---|---|
| 크기 1 KB / 압축 8:1 / 피크 10배 | 추정 | 표본 10만 건 · 1주 분당 카운트 · 실압축 | 데이터팀, S0(1주 내) |
| 코어당 5,000 eps | 추정 | S2 부하 주입 결과 | 플랫폼팀, S2 |
| $0.023/GB·월, $0.005/1,000요청, $5/TB | **전부 리스트 가격**(약정·리전·계층 할인 미반영) | 첫 월말 청구서의 항목별 실단가 | 플랫폼팀+재무, S4 이후 첫 월말 |

그때까지 비용 결론은 **자릿수만** 유효하다. 배수 비교("쿼리비가 저장비의 18배")는 실단가 확인 후 재계산한다.

## 대안과 기각 사유

1. **엣지 → 객체 스토리지 직접 배치(중간 버퍼 없음)** — 기각: 72시간 정지 흡수를 오토스케일로 사라지는 인스턴스 로컬 디스크에 의존한다. 부활: 트리거 F 발화, 또는 정지 허용 목표를 1시간으로 하향 합의.
2. **샤드 과금형 관리 스트림 vs 자체 운영 브로커** — 피크 11,600 eps면 12샤드 ≈ 월 $130 + 페이로드 $42, 브로커 3대(월 $400~600 + 운영 시간)보다 싸다. 관리형 채택, 자체 운영 기각. 부활: 일 5억 초과(샤드 60개, 월 $700대) 또는 버퍼 보존 요구 7일 초과.
3. **스트림 처리로 즉시 집계** — 기각: 목표 지연이 1시간. 부활: 5분 미만 지연이 요구로 명문화되면 배치 상한과 요청비가 다시 지배 변수가 되어 설계 전체를 다시 연다.
4. **원본 무압축 보관** — 기각: 8배 비용 레버를 버린다. 부활: 원본 바이트 보존이 감사 요건이 되면 원본은 콜드 계층에만 두고 분석 사본을 별도 유지.

## 리스크와 완화

- **카디널리티 폭발**(자유 속성이 컬럼으로 승격 → 스캔량 증가): 속성은 단일 자유 필드로 봉인, 컬럼 승격은 심사. 임계 숫자를 잡지 못했다(§자백).
- **중복 유입**: 이벤트 ID 필수 + 쿼리 시점 제거. 과금성 집계에 이 테이블을 쓰지 않는다고 못 박는다.
- **시각 왜곡·지연 도착**: 파티션은 수신 시각, 분석은 이벤트 시각 컬럼 병행, 24시간 유예 후 파티션 봉인.
- **스키마 변경으로 과거 파티션 판독 불가**: 필드 삭제 금지·추가만 허용, 파티션에 스키마 버전 기록.
- **운영 부담이 파이프라인을 죽인다**(인건비 > 인프라비): 대시보드 1개, 주 1회 점검, 트리거 6개 외 규칙 추가 금지.
- **개인정보 삭제 요구의 사후 발생**: 주체 식별자를 별도 컬럼으로 분리해 사후 암호화·삭제 경로를 남긴다.

## "완료"의 판정 기준

1. **싱크 경로를 72시간 차단한 뒤 복구한다 — 차단 구간 수신 건수와 복구 후 저장 건수가 이벤트 ID 집합 기준으로 일치하고(중복 허용, 누락 0), 적체 해소 시간이 차단 시간의 1.2배 이내다.** 측정: 엣지 수신 카운터 대 저장 계층 distinct ID 수, 플랫폼팀 수동 실행.
2. 월 청구서의 쓰기 요청 항목 < 총액 5%, 객체 중위 크기 ≥ 64 MB. 측정: 청구서 + S5 대시보드.
3. 대표 질의 10개의 일간 스캔 합 < 200 GB. 측정: 쿼리 엔진 스캔 바이트 지표.
4. 트리거 A~F의 임계값 전부가 S5 대시보드에서 직접 읽힌다(사람이 계산할 항목 0개).

1번은 이 설계의 어떤 차단 장치로도 자동 만족되지 않는다 — 누락을 막는 장치가 곧 검증 대상이기 때문이다.

## 프레임 이탈 / 관성 회귀

- **계산 절의 고유명사 금지를 우회했다.** (2) 버퍼의 "3부 복제"는 중립 단위가 아니라 특정 브로커 관행의 수다. "샤드"는 계산 절에서 빼는 대신 §대안 2로 옮겼는데, 그 절의 12샤드 계산은 계산 절이 할 일이다.
- **S0~S5 번호가 사다리로 읽힌다.** 병렬 관계를 표기 대신 문장 한 줄로 때웠다.
- **코어당 5,000 eps는 출처 없는 유일한 계수다.** 수명 상한(S2)을 붙이고 결론을 자릿수 진술로 약화시켰지만, 약화가 근거를 만들지는 않는다.
- **가장 약한 절은 §리스크의 카디널리티 항목**이다. 다른 모든 임계에 숫자를 붙였는데 여기만 "심사"로 끝나고, 필요한 입력(속성별 카디널리티 분포)을 S0 실측 목록에도 넣지 않았다. 리뷰어라면 여기를 친다.
- **관습을 산수보다 앞세운 곳**: 시간 입도는 계산으로 뽑았지만 "수신 시각 기준"은 관행을 그대로 삼켰고, 이벤트 시각 기준의 파티션 재작성 비용을 계산하지 않았다.
- **§완료 3번은 좋은 쪽 시나리오만 검사한다.** (2)에 나쁜 쪽 월 $6,000을 적어 놓고도 판정선은 일 200 GB(월 $75) 쪽에만 걸었다.
