# 주 3시간으로 유지하는 사이드 프로젝트 운영
- 추론 프레임: constraint-first
- 한 줄 요약: 주 3시간의 적은 총량이 아니라 **배포와 함께 자라는 누적 운영 부담**이고, 순예산 150분은 통상 궤적에서 52주차에 완전히 소진된다 — 기능을 깎으면 그 시점만 미뤄지므로, "가동 책임이 나에게 있다"는 전제를 삭제한 산출물 형태만 이 벽 안에서 유지된다.

## 프레임이 요구하는 시작점 — 벽을 세우고 교집합을 판정한다

반사적 습관은 "3시간을 잘 쓰는 법"(세션 기법, 주간 계획표)을 쓰는 것이고 이 프레임은 그것을 금지한다. 먼저 무엇이 구조적으로 불가능한지 증명한다.

**벽 (숨은 벽 포함)**
- **W1** — 주 180분. 평탄. 주어진 상수.
- **W2** — "유지": 프로젝트는 살아 있어야 한다. 조작적 정의 = 12주마다 최소 1회 사용자가 인지할 수 있는 릴리스. 이 벽이 없으면 "아무것도 만들지 않는다"가 W1을 자동 만족시킨다.
- **W3** — "운영": 이미 배포된 것에 대한 최소 의무(보안, 의존성, 데이터 보전, 문의). 요구 안에 묻혀 있던 벽이며 **누적항**이다.

W1이 무는 차원 분해: 총량이 아니라 (a) 분포 — 주 2세션이면 1회 최대 약 75분 연속, (b) 지연 — 세션 간 최대 간격 4일, 결손 1주를 허용하면 최악 11일. 따라서 W1은 "응답 지연 < 11일"인 모든 요구를 벽 밖으로 밀어낸다. 이것은 모순이 아니라 **벽 밖 요구**이므로 기각으로 충분하다(실시간 알림, SNS 운영).

**교집합 판정 — 산수**

순예산 = 180 − 위생 고정비 30분 = **150분/주**. (30분 = 세션 재진입 2×10분 + 의존성·백업 확인 10분. 초기값 — 8주 세션 타임스탬프 로그의 중위값으로 대체, 측정자 본인.)

W3의 주당 draw:
- 유지 표면(독립적으로 깨질 수 있는 단위: 런타임, 저장소, 외부 API 의존, 배포 채널) 1개당 **8분/주** — 도출: 표면당 월 1회 장애 × 30분 대응 = 7.5분/주, 반올림. 12주 실제 장애 로그로 대체.
- 사용자 1명당 **0.3분/주** — 도출: 0.02건/주/명 × 15분/건. 0.02는 임의 초기값 — 첫 사용자 20명의 문의 로그로 대체.

통상 궤적(임의 초기값: 창작 시간이 3주에 표면 1개를 낳고, 사용자는 주 +2명 — 8주 실측으로 대체):
- 36주차: 표면 12개 = 96분, 사용자 72명 = 22분. 합 118분. 창작 32분 잔존.
- **52주차: 표면 17개 = 136분, 사용자 104명 = 31분. 합 167분 > 150분. 창작 몫이 음수가 된다.**

**판정: 교집합은 t=0에서 비어 있지 않고 52주차에 빈다.** 그리고 이 소진은 트리밍으로 막히지 않는다 — 기능을 절반 줄이면 N만 미뤄지고 기울기(8분/표면/주)는 그대로다. 감도: 두 궤적 가정이 2배 틀려도 N은 26~104주 사이이며 결론("누적항이 지배한다")은 뒤집히지 않는다.

## 구조의 전제 파괴 (P1)

기울기를 0에 가깝게 만드는 전제는 하나뿐이다. 삭제할 전제:

> **P1 — "배포된 산출물의 가동 책임은 나에게 있고, 유지 표면은 기능과 함께 자란다."**

삭제의 귀결(메뉴가 아니라 도출):
1. 실행은 사용자 기기에서 — 라이브러리/CLI/정적 파일/브라우저 로컬 저장 → 런타임 표면 0.
2. 데이터는 사용자 소유, 내 저장소 없음 → 데이터 보전 의무와 개인정보 규제 표면 0.
3. 배포는 불변 버전 — 한 번 태그된 것은 계속 동작하고 서버 버전이 없다 → 하위호환 의무가 유한.
4. 외부 API 의존은 0 또는 1. 1이면 "이것이 유일하게 자라는 표면"임을 문서에 못박는다.
5. 응답 의무는 공개 정책으로 유한화한다(정밀화 표).

기울기 재계산: 표면 1~2개 고정 → W3 = 8~16분/주 + 사용자항. 사용자 약 400명까지 창작 몫 > 0.

## 문제 정의 / 목표

주 180분 안에서 (a) 12주마다 릴리스가 나가고 (b) 누적 운영 부담의 기울기가 0에 머무는 사이드 프로젝트의 운영 규칙을 확정한다.

## 정밀화 vs 완화 (정직한 공개)

| 원 요구 | 처리 | 유형 | 공개 위치 |
|---|---|---|---|
| "사용자 문의에 응답한다" | 보안 취약점 = 11일 내 응답 / 버그 = 다음 릴리스에서 일괄 / 기능 요청 = 응답하지 않음 | **정밀화** — 누구를 보호하는지로 분할 | README |
| "응답 24시간" → "11일" | 지연 상한 자체를 낮춤 | **완화** | README에 근거(세션 분포)까지 표기 |
| "항상 동작한다" → "태그된 버전은 계속 동작, 최신 유지 보증 없음" | 보증 범위를 버전 축으로 분할 | **정밀화** | 라이선스 + README |
| "모든 의존성 최신" → "보안 권고 있는 것만" | 대상 축소 | **완화** | CONTRIBUTING |

보안 채널의 11일은 관행값(7일, 72시간)이 아니라 세션 분포에서 도출한 값이다(최대 간격 4일 + 결손 1주) — 이 벽 안에서 관행값은 지킬 수 없는 약속이다.

## 명시적 가정

- **[전체가 걸림] 180분은 협상 불가능한 상수다 — 의지의 문제가 아니라 구조적 상한이다.** 틀렸을 경우: 실제 상한이 90분이면 벽이 좁아진 것이므로 삭제 순서 1번을 즉시 집행한다. 300분이면 이 계획은 무효이고, 벽을 다시 선언한 새 계획이 필요하다. 가장 싼 조기 검증: 지난 8주 캘린더 + 커밋 타임스탬프 역추적 1회(30분, S0).
- 실행자는 1인이다. 틀렸을 경우: 조율 시간은 새 예산이 아니라 150분 안에서 나온다 → 후보 표를 재판정한다.
- 사용자 증가는 내 창작 시간과 무관하다(검색 유입). 틀렸을 경우(증가가 홍보량에 비례): 누적항이 자기제한적이 되어 N이 늘어난다 — 즉 보수적인 쪽으로 틀린 것이다.
- 산출물의 가치가 가동 시간에 의존하지 않는다. 틀렸을 경우: 주제 자체가 벽 밖이므로 계획을 수정하지 않고 주제를 바꾼다.

## 접근 및 단계 (각 단계에 그것이 내려온 벽을 표기)

- **S0** [W1 검증] 독립. 8주 역추적으로 실제 가용 시간을 실측. 검증: 주간 값 8개와 중위값이 기록됨.
- **S1** [W1+W3 교집합] S0 소비. 후보 표 확정 + **사전 확정 삭제 순서**(1 외부 API 의존 → 2 배포 채널 축소 → 3 문의 채널 폐쇄). 검증: 삭제 순서가 번호로 문서에 존재.
- **S2** [P1] S0만 소비 — S1과 병렬 가능. 산출물 형태 확정: 실행 위치, 데이터 소유, 버전 정책. 검증: 표면 목록을 세어 2개 이하.
- **S4** [W1 분포] S2 소비 — S3와 병렬 가능(둘은 서로 의존하지 않는다). 릴리스를 무의사결정으로: 태그 1회 = 배포 끝. 검증: 릴리스 체크리스트가 3단계 이하.
- **S3** [W3 정밀화] S1+S2 소비. 공개 정책 1장(응답 SLA, 무보증, 데이터 미수집). 검증: 정밀화 표 4행이 모두 문서 문장으로 존재.
- **S5** [W1 분포] S3+S4 소비. 세션 프로토콜 — 종료 시 다음 진입점 1줄을 남긴다. 검증: 세션 시작~첫 편집 시각차가 8주 로그에서 감소 추세.
- **S6** [W1+W3 상시] S0 로그 소비, 반복. 시간 로그 + 12/24주차 표면 카운트.
- **8주차 게이트(기본값 있음)**: 로그 중위값 > 180분이면 논의 없이 **삭제 순서 1번 집행**.

**벽 구멍의 선언**: 세션 시간은 4주 창 안에서만 차입한다 — 어느 4주 창의 합도 720분(=180×4)을 넘지 않는다. 위반 결과: 2개 창 연속 초과 시 삭제 순서 1번 집행. 이 조항이 없으면 "주말 몰아치기"가 벽을 조용히 무효화한다.

## 대안과 기각 사유

1. **자체 호스팅 SaaS(가입+결제+대시보드)**. 기각: 표면만 5개 이상 → t=0에 순예산의 1/4을 소비하고 52주보다 훨씬 먼저 소진. 부활 조건: 관리형 조합으로 8주 실측 운영 draw ≤ 20분/주가 확인될 때.
2. **시간을 늘린다(주 6시간)**. 기각: 180분은 이 계획의 대상이 아니라 상수다. 부활 조건: S0 실측이 실제 가용 6시간을 보일 때 — 그것은 완화가 아니라 벽 재선언이므로 새 계획이다.
3. **실시간 대응을 자동화로 대체(알림 → 자동 롤백)**. 기각: 자동화 자체가 유지 표면이고 감시의 실패는 조용하다. 부활 조건: 자동화가 외부 관리형이고 내 유지 표면 증가가 0으로 셀 수 있을 때.
4. **협업자 1인 영입해 3시간 유지**. 기각: 조율은 새 예산이 아니라 150분에서 나온다. 부활 조건: 4주 실측 조율 시간 ≤ 15분/주이고 전부 비동기 텍스트로 완결될 때.

## 리스크 & 완화

- 벽을 지키다 진척 0(W2 사망): 12주 릴리스 게이트가 기본값으로 감시 — 2회 연속 미달이면 종료를 선언한다(조용한 정지 금지).
- 성공이 곧 부하: 사용자 400명 도달 시 사전 규칙 — 이관(메인테이너 추가) 또는 기능 동결. 400은 위 산수의 창작 몫 0 지점(도출).
- 보안 부채 누적: 의존성 개수 상한 5개(임의 초기값 — 12주 후 실제 권고 빈도로 재도출) + 공개된 무보증 정책.
- 동기라는 숨은 통화: 150분이 전부 위생에 먹히면 재미가 0이 된다. 표면 카운트가 상한을 넘는 즉시 삭제로 되돌린다.
- 법·규제: 데이터 미수집이 P1에서 도출되므로 개인정보 의무가 발생하지 않는다. 수집이 필요해지는 순간 후보 표를 재판정한다.
- 데이터 손실 책임: 데이터가 사용자 소유이므로 내 의무가 아니다. 단 마이그레이션이 필요한 포맷 변경은 불변 버전 정책으로 금지한다.

## "완료"의 판정 기준

- **[필수 실측]** 12주 연속 세션 로그에서 주간 실투입 중위값 ≤ 180분이고, **어느 4주 창의 합도 720분 이하**다(720 = 180×4, 도출). 이 문장은 이 계획의 차단 장치가 자동 만족시킬 수 없다 — 운영 표면을 없애도 창작 시간은 넘칠 수 있다.
- 12주차와 24주차에 유지 표면을 센다: 증가 ≤ 1. 비순환 — 표면 추가는 내 창작 행위로 일어나므로 P1이 자동 만족시키지 않는다.
- 24주 동안 12주 간격 릴리스 태그가 최소 2개 존재한다(W2 생존).
- (보강 증거, 결정적 아님) 4주 무개입 테스트 후 미처리 항목 0 — P1이 구조적으로 만족시키므로 증거력이 약하다고 미리 표기한다.

## 누락 범주 점검 스윕

훑은 범주와 착지 지점: 법·규제(리스크), 세금·결제(후보 표), 데이터 손실(리스크), 문서화(후보 표), 종료·이관(400명 규칙), 협업자(가정), 돈(비용 0 — 자체 호스팅 삭제의 부수 효과), 사용자 커뮤니케이션(정밀화 표). **미착지 1건 — 접근성**: 산출물 형태가 정해지기 전에는 판정할 수 없으므로 S2의 출력에 붙는 미결 항목으로 남긴다.

## 프레임 이탈 / 관성 회귀

- **숨은 벽을 내가 세웠다.** W2의 조작적 정의("12주마다 1회 릴리스")는 요구에 없던 내 수치다. 초기값으로 표기했지만, 법정이 자기 피고를 만든 것에 가깝고 이 문장이 §시작점의 가장 약한 고리다.
- **52주라는 결론은 두 개의 근거 없는 궤적 수(3주당 표면 1개, 주 +2명)에 걸려 있다.** 감도 한 줄로 방어했지만 감도 역시 같은 모델 안에서 계산되었으므로 모델이 틀리면 방어도 함께 틀린다. 직접 고침 시도로 8주 실측 대체 시점을 붙였으나, 실측 전에 계획을 실행해야 하는 순서 문제는 남는다.
- **단계 번호가 사다리로 읽힌다.** S3와 S4는 서로 의존하지 않아 순서를 바꿔 배치하고 병렬 표기를 붙였지만(편집 이력), 여전히 S0→S6 번호가 상승 서사를 암시한다.
- **리뷰어라면 §리스크의 "동기라는 숨은 통화" 항목을 공격하겠다.** 여섯 항목 중 유일하게 측정 장치가 없고, 완화가 "삭제로 되돌린다"는 문장 하나다.
- **관행을 택한 곳**: 게이트·사전 확정 삭제 순서·공개 정책은 이 도메인의 통상적 해법이고 프레임이 도출한 것이 아니다. 프레임이 실제로 뒤집은 결정은 산출물 형태(P1) 하나이며, 나머지는 그 판정을 집행하는 장치다.
