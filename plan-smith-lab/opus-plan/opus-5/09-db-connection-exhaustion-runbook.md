# 새벽 3시 프로덕션 DB 커넥션 고갈 장애 런북
- 추론 프레임: triage
- 한 줄 요약: 2분짜리 단일 조회로 원인 계열만 가르고, 되돌리기가 싼 "비필수 워크로드 차단"을 기본 트랙으로 삼아 5분 안에 지혈하며, 증거가 먼저 사라지는 순서대로 조치를 배열한 3계층 런북.

## 프레임이 요구하는 시작점 — 가용 시간 티어와 부작용 병기

이 문서의 축은 연대기가 아니라 **그 시점에 쓸 수 있는 시간 예산**이다. 5분 티어는 "먼저 하는 일"이 아니라 "5분밖에 없을 때 하는 전부"다. 티어 **내부** 순서는 휘발성 × 비가역성으로 정한다 — 조치가 지워버릴 증거를 먼저 뜬다. 모든 조치에 발동 조건과 부작용을 병기한다.

### T0 — 초저비용 분류 (예산 2분, 단일 조회)

상태별·앱별 커넥션 스냅샷 **한 번**을 읽고 계열만 가른다. 근본 원인은 찾지 않는다.

| 읽히는 것 | 계열 | 5분 티어에서의 처방 |
|---|---|---|
| 사용 커넥션이 한도의 절반 이하 | E 계측 오류 | 알람 스누즈(만료 시 자동 재발화) 후 종료 |
| `idle in transaction` 다수, 상위 점유가 배치/워커 | B 트랜잭션 방치 | 기본 트랙 + 필터 kill |
| active 다수 + 락 대기 체인 존재 | C 락·장기 쿼리 | 기본 트랙 (락 헤드 kill은 30분 티어) |
| active 다수, 쿼리 짧음, 사용자 트래픽 급증 | A 수요 | 기본 트랙 + 읽기 replica 우회 |
| 조회 실패 또는 2분 초과 | 판정 불가 | 기본 트랙 **무조건** 실행 |

예산 2분의 근거: 5분 티어에 스냅샷 1회 + 기본 트랙 발동이 반드시 들어가야 하고 그 실행을 3분으로 잡은 뺄셈이다. 3분은 **리허설 실측치로 교체**한다(리허설 때 DBA 온콜이 자산 문서에 기입). 예산 만료는 실패가 아니라 "판정 불가"라는 정당한 분류이며, 곧바로 기본 트랙으로 라우팅한다 — 새벽 3시에 원인을 캐고 싶은 충동은 이 캡으로만 막힌다.

### 기본 트랙 — 비필수 워크로드 차단 (가역성 규칙으로 선정)

되돌리는 방법이 단일 명령(레이트 제한 재개)이고, 오분류했을 때 태우는 비용이 **배치 미완료(아침 정산·리포트 지연)와 큐 적재**뿐이다. 이 비용은 명시하고 알고 지불한다. 새벽 3시라는 시각이 이 선택의 근거다 — 사용자 트래픽은 최저, 배치·워커 점유는 최고다.

**탈락한 기본 트랙: 앱 롤링 재시작.** 되돌릴 수 없고, 열린 트랜잭션·스레드 상태라는 증거를 영구 소멸시키고, 재연결 폭풍으로 고갈을 재현한다. 오분류 비용이 비대칭적으로 비싸므로 가역성 규칙에서 탈락한다.

### 오분류 회복 장치

차단 발동 후 **최장 배치 트랜잭션 소요 시간**(자산 문서의 값)이 지났는데 점유 커넥션이 내려가지 않으면 B/C 오분류로 확정하고 30분 티어의 재분류 게이트(G1)로 승격한다. 그 값이 문서화되어 있지 않으면 잠정 2분을 쓴다 — **임의 선언값**이며, 첫 리허설의 실측 분포가 교체한다.

## 문제 정의 / 목표

새벽 3시, 커넥션 풀 고갈로 사용자 요청이 대기 타임아웃으로 실패한다. 대응자는 1인, 판단력은 저하, 승인자는 자고 있다. 목표는 둘뿐이다. ① 5분 안에 사용자 영향을 멈춘다. ② 아침에 원인을 규명할 수 있는 증거를 남긴다. 원인 규명 자체는 이 런북의 목표가 아니다.

## 명시적 가정

- **고갈 상태에서도 관리자 진단 접속 경로가 살아 있다.** 틀리면 런북은 1행에서 정지하고 무진단 지혈(기본 트랙 → 프록시 재시작)만 남는다. 이 가정은 자산 목록 ①과 리허설이 처리한다 — 가장 싼 선행 검증은 지금 프로덕션의 예약 슬롯 설정값 한 줄을 읽는 것이다(비용 0). 대비 경로: 예약 경로 부재가 확인되면 T1 스냅샷을 건너뛰고 기본 트랙부터 실행하되, 증거 없음을 사건 기록에 남긴다.
- Postgres 계열 + 앱측 커넥션 풀. 틀리면(MySQL 등) 조회 대상 이름만 대체되고 티어 구조는 그대로다.
- 알람은 실제 고갈을 가리킨다. 틀릴 경우를 위해 분류표에 E 계열을 두었다.
- 비필수 워크로드가 단일 스위치로 멈춘다. 틀리면 기본 트랙의 발동 시간이 3분을 넘겨 5분 티어가 붕괴한다 → 자산 목록 ③의 리허설이 이것을 검사한다.

## 접근 및 단계 — 3계층

런타임 조치는 아래 3계층이 전부다. 이어지는 자산 목록과 금지 목록은 티어가 아니라 평시 준비 항목이다.

### 5분 안에 할 일

| # | 조치 | 발동 조건 | 부작용 |
|---|---|---|---|
| T0 | 분류 (위 표) | 알람 수신 | 2분간 대기 에러 계속 누적 |
| T1 | 스냅샷 번들 1회 실행(활동·락·풀 메트릭을 파일로) | 예약 경로 접속 성공 | 예약 슬롯 1개 소비. 실패하면 즉시 T2로 |
| T2 | 비필수 워크로드 차단 | 분류 결과 무관(E 제외) | 배치 미완료, 큐 적재. 재개는 레이트 제한 필수(재폭주) |
| T3 | 필터 kill (`idle in transaction` + 자산 문서의 방치 임계 초과 + 정산 계열 앱 제외) | 분류 B일 때만 | 해당 트랜잭션 롤백 → 재처리 필요, 클라이언트 재시도 폭주 |
| T4 | 종료 판정 또는 30분 티어 진입 | T2 후 | — |

**T1이 T2·T3보다 앞선 이유는 순서가 빠른 게 아니라 증거가 먼저 사라지기 때문이다.** 차단과 kill은 프로세스 목록과 락 체인을 즉시 소멸시킨다. 반대로 DB 로그와 시계열 메트릭은 보존되므로 티어 안에서 뜨지 않는다.

### 30분 안에 할 일

| # | 조치 | 발동 조건 | 부작용 |
|---|---|---|---|
| G1 | 재분류 게이트 (분류표 재실행, 이번엔 락 트리 포함) | 오분류 신호 발화 | 재분류 동안 추가 지연 |
| G2 | 스레드 덤프 확보 **후** 인스턴스 1대만 격리 재시작 | 누수 계열 확정 + 덤프 파일 존재 | in-flight 요청 실패, 캐시 콜드. **덤프 없는 재시작은 금지** |
| G3 | 락 체인 헤드 1건 kill (2인 확인) | 분류 C + 대기 체인의 헤드가 단일 트랜잭션으로 특정됨 | 헤드 트랜잭션 롤백. 오판 시 정산 재처리 |
| G4 | 에스컬레이션(DBA 온콜 + 정산 오너 호출) 및 사건 기록 시작 | T2로 지혈 실패 | 새벽 호출 비용. 늦추는 것이 더 비쌈 |

### 사후에 할 일 (포인터 4건 상한)

상한 4는 **임의 선언값**이다 — 새벽 대응자 1인이 아침 인수인계에 실제로 넘길 수 있는 항목 수를 첫 실사건에서 온콜이 세어 교체한다. 초과분은 이 런북이 아니라 별도 백로그로 나간다.

1. **누수 지점 확정** — 스냅샷의 `idle in transaction` 상위 앱의 트랜잭션 경계 감사. 오너: 해당 서비스 팀 / 트리거: 스냅샷 파일 존재. 부작용: 경계 축소는 배치 처리량을 떨어뜨릴 수 있다.
2. **풀 산술 CI 게이트** — Σ(인스턴스 수 × 풀 max) + 예약 슬롯 ≤ `max_connections`. 부작용: 풀 축소 없는 스케일아웃 배포가 차단된다.
3. **`idle_in_transaction_session_timeout` / `statement_timeout` 도입** — 부작용: 조용히 성공하던 장기 배치가 실패로 전환되며 첫 주 실패 건수가 급증한다.
4. **자산·리허설 갱신** — 실측 시간값 기입, 킬 스위치 검증. 부작용: 스테이징 부하 창을 점유한다.

## 컴파일타임 자산 목록 (평시 준비물 — 없으면 위 티어는 전부 허구)

① 예약 진단 접속 경로 ② 단일 명령 스냅샷 번들 스크립트(출력 경로 고정) ③ 비필수 워크로드 킬 스위치 + 레이트 제한 재개 명령 ④ 상태별·앱별 커넥션 대시보드(2분 분류의 전제) ⑤ 새벽 승인 대행 지정(2인 확인 대상: DBA 온콜, 정산 오너) — **아래 금지 목록을 승인 대행에게 사전 전달**한다(재시작을 지시할 사람이 대응자가 아니라 이쪽이다) ⑥ 값 문서: `max_connections`, 인스턴스 수 × 풀 max, 최장 배치 트랜잭션 소요, 방치 임계, 파라미터 변경 시 재시작 필요 여부.

**리허설:** 스테이징에서 풀을 포화시킨 뒤 런북을 완주하고, 실측 시간으로 ⑥의 값들을 교체한다. 주기는 잠정 분기 1회 — **임의 선언값**이며, 첫 두 회차에서 발견된 자산 무효화 건수를 보고 온콜 책임자가 조정한다.

## 금지 행동 — 압박받는 뇌가 손을 뻗을 곳

| 유혹 문법 | 실제 비용 | 지정 대체 | 구조적 집행 |
|---|---|---|---|
| "고갈이니 풀 max를 올리면 되지" | `max_connections` 초과 → 전면 거부로 확대. 메모리 압박. 파라미터 변경에 DB 재시작이 필요할 수 있음 | T2로 수요를 줄인다 | 풀 설정 런타임 변경 경로 없음 — 배포 파이프라인만 통과 가능 |
| "오래된 쿼리를 전부 끊자" | 정산·마이그레이션 롤백 → 재처리. 대기 큐 붕괴 후 재폭주 | T3 필터 kill | kill 스크립트는 필터 인자 없이는 실행 불가 |
| "DB를 재시작/페일오버해 초기화하자" | 복제 지연 구간의 데이터 손실 창, 캐시 콜드 → 느린 쿼리 → 재고갈 | 30분 티어 이후로 이관 | DBA 온콜 + 승인 대행 2인 승인 게이트 |
| "알람 임계를 올려 조용히 하자" | 다음 발생을 못 본다 | 스누즈 | 스누즈에 기본값 — 만료 시 자동 재발화 |

## 대안과 기각 사유

- **풀 사이징 상향을 1차 조치로 두는 런북.** 기각: 원인이 누수·락일 때 상향은 고갈 시점만 늦추고 DB 전면 거부로 사고를 키운다. 부활 조건 — 사후 2번의 산술 검사에서 실제 상한이 `max_connections`보다 크게 낮고, 이후 사건들의 T0 분류가 연속으로 A(수요)로 나오면 상향은 사후 항목으로 부활한다. "연속 3건"을 잠정 기준으로 두되 이는 **임의 선언값**이며, 사후 1번의 누수 감사 결과가 나오면 그 결론이 기준을 대체한다.
- **자동 대응(고갈 감지 시 킬 스위치 자동 발동).** 기각: 오분류 시 사람의 회복 장치가 없고, E 계열(계측 오류)에서 정상 배치를 매일 죽인다. 부활 조건 — 알람 오발화 0이 관측된 사건이 **연속 3건**(위와 동일한 임의 선언값, 동일 교체 규칙) 쌓이면 자동화한다.

## 리스크 & 완화

| 리스크 | 완화 |
|---|---|
| 자산이 썩는다(스크립트·연락망이 조용히 무효화) | 리허설이 자산 목록 전 항목을 실행 경로로 검사. 실패 항목은 사후 4번으로 |
| 리허설이 영원히 미뤄진다 | 사후 4번을 사건 종료 조건에 포함 — 리허설 날짜 미기입이면 사건 미종결 |
| 새벽 1인 대응자에게 2인 승인 상대가 없다 | 승인 대행을 자산 ⑤로 사전 지정. 미지정이면 해당 조치는 아침으로 이월(런북이 대기를 지시) |
| 5분 티어가 실제로 5분을 넘긴다 | 리허설 실측이 유일한 검사 수단. 초과 시 T3를 30분 티어로 내린다 |

## "완료"의 판정 기준

1. **(실측)** 스테이징에서 풀을 포화시킨 상태로 이 런북을 처음 보는 온콜 1인에게 주면, 외부 질문 0회·즉흥 판단 0회로 5분 티어를 완주하고 스톱워치 실측이 5분 이내다. 측정: 리허설 진행자가 스톱워치 + 스냅샷 파일 존재 여부로 판정. *(이 판정문 형식은 `checklist` 프레임의 완료문 규범을 차용했다 — 무판단 실행을 요구하는 문서라는 점이 같다.)*
2. **(산술)** 배포 시 CI가 Σ(인스턴스 × 풀 max) + 예약 슬롯 ≤ `max_connections`를 검사해 위반 시 차단한다. 통과/차단 로그가 증거다.
3. **(사건 단위)** 5분 티어 종료 판정 = 커넥션 점유율이 한도의 0.7 이하로 5분 연속 유지 + 예약 슬롯 확보. **0.7과 5분 창 모두 임의 선언값**이며, 첫 리허설과 첫 실사건의 점유율 시계열로 DBA 온콜이 교체한다.

판정 1은 이 런북의 어떤 차단 조치로도 자동 만족되지 않는다 — 사람이 문서만으로 완주하는지를 측정하기 때문이다.

## 프레임 이탈 / 관성 회귀

- **가장 약한 부분은 사후 4번(자산·리허설 갱신)이다.** 나머지 셋은 산출물이 있는데 이것만 "갱신한다"는 동사에 그친다. 리스크 표의 "리허설 날짜 미기입 = 사건 미종결"이 유일한 강제 장치이고, 그것도 사건 기록 서식이라는 미확인 자산에 의존한다. 리뷰어라면 여기를 친다.
- **30분 티어에 무게가 실렸다.** 프레임은 사후 티어 비대를 경계하라고 했고 그건 상한 4로 막았으나, 대신 G1~G4가 5분 티어의 조치 수(T0~T3)와 같아졌다. 티어 간 무게 분포 점검에서 중간 티어 쪽 변위를 잡아내지 못했다.
- **관성 회귀:** 티어 내부를 "관찰 → 조치 → 확인"이라는 익숙한 상승 배열로 짜려 했다. 휘발성 순서가 우연히 그것과 겹쳐서, 프레임이 실제로 순서를 뒤집은 곳은 G2 한 군데(재시작을 덤프 게이트 뒤로 밀어낸 것)뿐이다. 나머지 순서는 프레임의 성과가 아니라 상식의 성과다.
