# 날짜 범위 겹침 계산 유틸 — 오픈소스 라이브러리 플랜

- 추론 프레임: api-first
- 한 줄 요약: 예약 충돌 검사 호출부 10줄을 계약으로 못박고, 그 10줄을 참으로 만드는 최소 내부(반개구간 두 정수 + 생성자 검증)만 만든다.

## 프레임이 요구하는 시작점 — 사용자가 실제로 타이핑할 10줄

```ts
// v1 = 가설. S0(호출부 발굴) 통과 시 이 주석을 제거한다.
import { range, overlaps, touches, mergeAll, subtract, overlapMinutes } from "date-overlap";

const booked = rows.map(r => range(r.start_at, r.end_at));      // 2 문자열·null 그대로
const wanted = range("2026-08-01T09:00:00Z", "2026-08-01T10:00:00Z");
const conflicts = booked.filter(r => overlaps(r, wanted));      // 4 끝==시작은 false
if (conflicts.length) throw new ConflictError(conflicts.map(String));
const backToBack = booked.filter(r => touches(r, wanted));      // 6 맞닿음은 경고만
const busy = mergeAll(booked);                                  // 7 정렬+병합, 맞닿음은 이어붙임
const free = subtract(range(dayStart, dayEnd), busy);           // 8 빈 구간 Range[]
const usedMin = overlapMinutes(wanted, busy);                   // 9 숫자 하나, 0 가능
console.log(free.map(String), usedMin, backToBack.length);      // 10 doctest 기대 출력
```

**이 10줄이 잠그는 것(계약):** 함수 6개의 이름·인자 개수·반환 종류, `Range`의 필드(`start`/`end`, epoch ms), `String(r)` ↔ `range(iso)` 왕복, 인접 규칙(`overlaps`는 false / `mergeAll`은 병합), 배열 반환은 시작 시각 오름차순.
**자유로운 것:** 에러 메시지 문구, `toString`의 정확한 문자열(왕복 성립만 보장), 후방호환 필드 추가, 내부 표현. 이 구분이 없으면 개선이 전부 파괴적 변경으로 읽힌다.

**10줄이 죽인 결정 3건**(부품이 실제로 작동한 지점):
- *기존 세계 반영* → `Date`만 받는 시그니처를 죽였다. 2행의 호출부는 DB 행이고, DB 행은 문자열과 `null`을 준다 → 파싱·정규화 계층이 별도로 존재해야 한다.
- *엣지 케이스 못박기* → `{ inclusive: true }` 옵션을 죽였다. 4행과 7행의 인접 규칙이 반대라는 사실이 같은 화면에 드러나서, 플래그 대신 `touches`를 독립 술어로 분리했다.
- *실행 가능한 명세* → "`toString`은 계약"을 죽이고 왕복만 잠갔다. 동시에 코드로 표현 불가능한 조항(무의존성·타입 해석·에러 문구·파싱 호환·성능)이 산문으로 새는 것을 막기 위해 전부 이름 붙은 계약 테스트로 옮겼다(S5).
- 덤: 길이 0 구간은 "반개구간 의미론"에서 연역하지 않고 **방출 지점**에서 결정했다. 내부에서 교집합을 계산하는 곳은 `overlapMinutes`와 `subtract` 두 군데뿐이고, 거기서 길이 0이 나오는 경우는 인접 하나이며 그 값은 버려야 한다. 그러므로 생성자가 `start >= end`를 거부하면 길이 0은 애초에 표현 불가능해지고, 함수 6개의 진리표에서 해당 행이 전부 사라진다.

## 문제 정의 / 목표

예약·근무표·구독 기간을 다루는 코드는 매번 `a.start < b.end && b.start < a.end`를 다시 쓰고, 인접·열린 끝·병합에서 매번 다르게 틀린다. 목표는 위 10줄이 그대로 동작하는 무의존성 TS 패키지(ESM+CJS, MIT). 비목표: 시간대 변환, 달력 반복 규칙(RRULE), 구간 트리 수준의 대용량 질의, 문구 국제화.

## 명시적 가정

- **A1(전체가 걸린 가정): 사용자는 "시각 구간"을 다루고 끝은 nullable이다** — 즉 위 10줄이 진짜 호출부다. 틀렸을 경우: 달력 날짜(종일 이벤트, 종료일 *포함*) 사용자가 다수면 인접·포함 규칙이 정반대가 되어 계약 전체가 무효. 가장 싼 조기 검증: S0의 호출부 표 30건 + 이 10줄을 그대로 RFC 이슈로 공개해 반응 수집(코드 0줄). 폴백: 내부 표현이 epoch ms 두 개뿐이므로 바뀌는 것은 생성자·직렬화 계층 하나 — `dateRange("2026-08-01","2026-08-03")`을 별도 생성자로 추가하고 연산 6개는 손대지 않는다.
- A2: 호출자가 UTC 인스턴트로 정규화해 넘긴다. 틀렸을 경우: 로컬 자정 경계(8행의 `dayStart`)가 어긋난다 → 문서에 비목표로 명시하고 경계 생성은 호출자 책임으로 남긴다.
- A3: 목록 크기는 수천 단위. 틀렸을 경우: `mergeAll`의 정렬이 병목 → 구간 트리가 필요해지고 v1 범위 밖(성능 계약 테스트가 먼저 깨져서 알려준다).
- A4: `date-overlap` npm 이름을 확보할 수 있다. 틀렸을 경우: 스코프 패키지로 변경, 계약 무영향.

## 접근 및 단계

- **S0 호출부 발굴 (선행 없음).** 공개 저장소·이슈 트래커·내 프로젝트에서 겹침 계산 호출부 30건을 수집해 `docs/discovery.md`에 4열 표로 기록(입력 타입 / 끝 nullable 여부 / 날짜냐 시각이냐 / 인접 기대). *검증:* 30칸이 빈 셀 없이 채워짐. *거부 게이트:* 날짜 전용 호출부가 1/3을 넘으면 위 10줄을 기각하고 달력 생성자를 포함해 다시 쓴 뒤 S1을 재시작한다. 수치 30·1/3은 **임의**(한 번에 읽을 수 있는 분량, 다수 판정선) — S7에서 실제 이슈 표본으로 교체. 게이트를 통과하면 예시의 `v1 = 가설` 주석을 제거한다.
- **S1 예시를 실행 가능한 명세로 고정 (S0 판정 소비).** README 코드블록을 추출해 CI에서 실행. `rows`·`dayStart`·`dayEnd`는 코퍼스의 고정 픽스처로 치환되어 10행 출력이 결정적이 된다. 같은 코퍼스에 애매 사례 3건을 이름 붙여 추가: 인접, 열린 끝(`null`), 길이 0 거부. *검증:* 세 규칙을 코드에서 일부러 반전시키면 해당 케이스가 깨진다 — 깨지지 않으면 그 케이스는 계약이 아니라 장식이므로 다시 쓴다.
- **S2 표현과 생성자 (S1).** `Range`는 동결된 `{start, end}` epoch ms, `end` 없음 = `+Infinity`. 문자열·숫자·`Date`·`null` 수용, ISO 8601 구간 문자열 단일 인자 형태도 수용(왕복용). `start >= end`는 `RangeError`. 직렬화는 `시작/끝` 형태이고 **끝이 무한이면 `2026-08-01T09:00:00.000Z/..`** — 5행이 열린 구간을 그대로 출력하므로 이 형태가 없으면 왕복 속성과 D1이 동시에 구멍난다. *검증:* 왕복 속성 `range(String(r))`이 원본과 동일(무한 끝 포함); 잘못된 입력 표본이 전부 생성 시점에서 throw → 이후 연산 6개는 전함수가 되어 방어 코드가 필요 없다. (2·3행)
- **S3 술어 (S2).** `overlaps` = `a.start < b.end && b.start < a.end`, `touches` = 한쪽 끝과 다른 쪽 시작이 같음. *검증:* 대칭성, `overlaps`와 `touches`의 상호배타, `overlaps(a,b) ⇔ overlapMinutes(a,[b]) > 0`. (4·6행)
- **S4 연산 (S2, S3).** `mergeAll`(정렬 후 `touches` 포함 병합), `subtract`, `overlapMinutes`. *검증:* 출력 불변식(오름차순, 서로 겹치지도 맞닿지도 않음) + 커버리지 보존 — 무작위 200개 구간 목록에 대해 표본 1000개 시각에서 `covered(t, 원본) === covered(t, mergeAll(원본))`, 그리고 `subtract` 결과 ∪ `busy`가 하루 전체를 덮음. 표본 수 200·1000은 **임의**(1초 내 실행되는 상한), 첫 성능 계약 측정 시 재산정. (7·8·9행)
- **S5 산문 조항의 테스트화 (S1과 병렬).** `no-deps`(설치 트리 의존성 0), `types-node16`(예시를 `tsc`로 컴파일), `error-text`(`ConflictError` 메시지에 두 구간의 `toString`이 포함), `parse-conformance`(`Z`/`+00:00`/밀리초 유무/공백 구분자 등 입력 표를 고정하고 Node LTS 두 버전에서 동일 epoch ms를 요구 — 런타임별 `Date.parse` 차이를 계약으로 못박는다), `perf`(구간 10,000개 `mergeAll` 100ms 미만 — **임의** 상한, 일반 요청 처리 예산 기준, 실사용 이슈로 교체). *검증:* 각 테스트가 이름으로 계약 조항을 가리킨다.
- **S6 패키징 (S2–S5).** ESM+CJS 이중 배포, `.d.ts`, semver 정책 문서에 "파괴적 변경 = 잠긴 목록의 변경뿐"을 명시.
- **S7 재게이트 (v0.1 배포 후 실사용).** 들어온 이슈·사용 사례로 S0 표를 갱신하고 임의 수치를 교체.
- **예시 코퍼스 거버넌스:** 예시 파일 10개 상한(솔로 메인테이너가 매 PR에서 전부 읽을 수 있는 양 — **임의**, 두 번째 커미터가 생기면 재산정). 새 케이스는 기존 케이스를 대체하거나 잠긴 조항을 신설할 때만 진입(기본 거부). major에서 조항이 사라지면 예시도 함께 은퇴.

S0→S7의 번호는 의존 순서의 투영이다. 실제 형태는 사다리가 아니라 나무다(S5는 S1 직후 병렬, S3·S4는 S2에만 의존).

## 대안과 기각 사유

1. **date-fns에 기여(이미 `areIntervalsOverlapping`이 있다).** 기각: 2행의 문자열·`null` 수용과 8행의 `subtract`는 상류의 `Interval` 계약과 API 정책을 바꿔야 얻어진다. *부활 조건:* S0의 30건 중 과반이 이미 date-fns에 의존하고, 부족한 것이 `subtract`·`mergeAll` 둘뿐이면 새 패키지를 접고 상류 PR로 전환한다("과반"은 **임의** 판정선 — S0 표가 채워지면 실제 분포로 재설정).
2. **닫힌 구간(종료 포함).** 기각: 병합에서 인접이 이중계산되고 길이 0 문제가 되살아난다. *부활 조건:* S0 게이트가 날짜 전용 다수를 보고하면, 닫힌 구간은 `dateRange` 생성자 **내부**에서만 채택하고 외부 표현은 반개구간으로 유지한다.
3. **옵션 객체(`{ inclusive }`, `{ unit }` 등)로 규칙·단위를 설정 가능하게.** 기각: 함수 6개 × 옵션이 진리표를 배가시키고 위 10줄이 두 가지로 읽힌다. `overlapMinutes`가 단위를 이름에 박은 것도 같은 이유다(9행이 분 단위 하나만 필요했다). *부활 조건 두 갈래:* ① 상반된 인접 규칙을 요구하는 실명 소비자가 각자의 예시 코퍼스 케이스를 함께 제출할 때 — 문의 1건은 취향이고 2건은 분기라는 판단이므로 **2곳으로 임의 설정**, 첫 실제 요청 내용으로 재설정. ② 시간·일 단위 요구가 오면 옵션이 아니라 `overlapHours`처럼 이름을 하나 더 내보내는 쪽을 먼저 시도하고, 요구 단위가 3종을 넘어가면 그때 옵션 객체를 재심한다. 날짜 아닌 타입으로의 일반화(제네릭 구간 라이브러리)도 ①의 문턱을 쓴다.

## "완료"의 판정 기준

- **D1(실측·헤드라인):** CI가 README 코드블록을 추출해 실행하고, 10행의 출력이 문서에 적힌 기대 문자열과 **문자 단위로 일치**한다. 불일치 시 배포 차단.
- **D2(실측):** `npm pack` 산출물을 빈 디렉토리에 설치해 ESM·CJS 양쪽에서 예시 10줄이 실행되고, 설치 트리의 의존성 개수가 0이다.
- **D3(실측):** 무작위 200개 구간 목록 × 표본 1000 시각에서 커버리지 보존 속성 위반 0건.
- **D4:** 이 라이브러리를 처음 보는 사람이 README만으로 예약 충돌 검사를 작성한다 — 소스 열람 0회, 질문 0회로 계수(`checklist` 프레임의 완료문 차용).

D3만으로 끝내면 안 되는 이유: 생성자 거부가 "잘못된 입력 버그 0건"을 정의상 참으로 만든다. 차단기가 자동 충족할 수 없는 문장은 D1(문서-구현 일치)과 D4(제3자 이해)뿐이다.

## 프레임 이탈 & 관성 회귀

- 가장 약한 절: **S0**. 프레임의 필수 부품이라 넣었지만 사용자가 0명인 신규 패키지에서 "실제 호출부 30건"은 절반이 허구다 — 공개 코드 검색과 내 저장소를 사용자 표본이라 부른 것에 지나지 않는다. 리뷰어라면 여기를 찔러 "이 발굴은 A1을 검증하지 못한다"고 할 것이고 옳다. 게이트에 실효(예시 기각 → S1 재시작)를 붙인 것이 내가 한 최선이고, 그것으로 표본의 약함이 사라지지는 않는다.
- 같은 절의 `30건`·`1/3`은 근거 없는 수치다. 임의 표기와 교체 시점(S7)을 달았지만 "나중에 측정"에 가깝다. 사용자 0명 상태에서 유도할 근거가 없어, 수치가 틀려도 절차는 걸리도록 게이트의 효력으로 대체했다.
- 단계 번호를 S0..S7 오름차순으로 붙였다. 의존 구조는 나무인데 표기는 사다리다 — 문장으로 바로잡았을 뿐 표기는 관행(읽기 편함)을 택했다.
- 관행 선택: 반개구간과 ISO 8601 구간 표기는 프레임에서 도출된 것이 아니라 도메인 정석이다. 예시가 그것을 골랐다기보다 내가 정석을 예시에 넣었다.
- 차용: D4의 "질문 0회" 문장은 `checklist` 프레임의 완료문을 가져온 것이다. api-first에서 도출한 문장이 아니다.
