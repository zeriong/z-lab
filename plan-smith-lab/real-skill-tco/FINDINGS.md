## 관측된 것 (부분 — 판정 근거가 아니다)

### R1. 실제 파이프라인의 계획 단계는 에이전트 하나 근사보다 훨씬 비싸다 (카나리, n=1)

스톱워치 한 페이지 과제에서 계획 단계만: base 110,783 토큰 · 170초 → plan-smith(실제) 1,866,644 토큰 · 2,267초 — **16.8배 · 13.3배**.
plan-writer가 세 번 불렸다(작성 · 새 인스턴스 배선 감사 · 감사 반영). 이전 계열(pure-model, transfer, tco, model-bump)의 plan-smith arm은
모두 에이전트 하나가 스킬 문서를 읽고 쓰는 근사였으므로 **그 계열들의 계획 비용은 과소평가였을 가능성이 높다.**

### R2. 게임 과제에서 plan-smith 계획은 끊기기 전까지 이미 base 계획보다 많이 썼다 (끊긴 세션, 하한)

끊긴 시점은 대개 plan-writer 작성 단계였다(패킷만 남음). **완료까지의 배수는 이보다 크다.** 구현 단계가 이를 되찾는지는 재지 못했다.

### R3. plan-smith 패킷에 계정 이메일이 들어간다 — 2/10, 전부 fable-5.1

패킷 템플릿의 `- Requested by: <user>` 필드를, 헤드리스 세션의 계정 정보로 채운 경우가 있었다:
fable-5.1 2/5 (1차 r2, 3차 r1 — `Requested by: zeriong (<계정 이메일>)`), opus-5.5 0/5(이름만). 플랜 폴더를 커밋하는 사용자라면 이메일이
저장소에 남는다. **이 실험의 산출물에서도 그렇게 새어 나갔다** — 푸시 전 사용자 승인을 받아 미푸시 커밋 4개의 이력을 다시 써서 `<EMAIL>`로 가렸고(2026-09-29), 이후 커밋하는 기록은 `../scrub.py`로 가린다. 백로그 B19.

### R4. 하네스 사실

- `--settings`의 `enabledPlugins` 만으로는 헤드리스에서 플러그인 스킬이 로드되지 않았다 — `--plugin-dir` 가 필요했다.
- 헤드리스에서 `AskUserQuestion` 은 제공되지 않는다 — 확인 게이트는 프롬프트의 배치 승인 문장으로만 넘어간다.
- 백그라운드 `claude -p` 는 호스트 잠자기를 막지 못한다 → `StreamSuspended` 와 "cut off mid-stream" 이어쓰기 주입이 생긴다.
- 인자 없는 `wait` 는 러너 자신의 `caffeinate` 작업까지 기다려 교착된다.
