# real-skill-tco-1.6.0 지표 — r1만, plan-smith는 하한

**범위.** 사용자 결정으로 r1에서 마무리했고(SPEC "r1에서 마무리"), 그 r1의 plan-smith 두 체인은 조직 지출 한도로 끊겼다(SPEC "지출 한도로 … 종료").
완주한 체인은 **base-plan 2개**뿐이다. plan-smith 쪽은 fable-5.1의 **완주한 계획 단계**와 opus-5.5의 **끊긴 계획 단계**만 있다.
구현·수리 비용은 0 이상이므로, plan-smith 계획 비용만으로 R의 **하한**이 성립한다. 모델·arm당 n=1이므로 방향 신호다.

원천: `evidence/<id>_{plan,impl}.json` (CLI `--output-format json`, `modelUsage` 는 서브에이전트 포함, 호스트 정보 가림) ·
끊긴 단계는 `evidence/aborted/20260930-174247-*/` · 패스별 분해는 트랜스크립트 감사 [`evidence/transcript-audit.json`](evidence/transcript-audit.json).
계산: [`metrics.py`](metrics.py) (단계 합), 아래 R은 그 값을 손으로 나눈 것이다.

## 1. 단계별 원지표 (CLI)

토큰 = input + output + cache_read + cache_creation (전 모델 합). 시간 = `duration_ms`. 달러 = `total_cost_usd`(CLI 추정치).

| 체인 | 단계 | 토큰 | output | cache_read 비중 | 시간 | CLI $ | 턴 | 상태 |
|---|---|---|---|---|---|---|---|---|
| opus-5.5 base-plan r1 | 계획 | 573,155 | 101,572 | 64% | 1,078초 | 2.97 | 7 | 1-shot |
| | 구현 | 1,841,756 | 130,139 | 84% | 1,139초 | 4.25 | 17 | 1-shot · 관측 DONE |
| fable-5.1 base-plan r1 | 계획 | 783,436 | 89,200 | 74% | 1,209초 | 6.95 | 12 | 1-shot |
| | 구현 | 1,074,619 | 109,775 | 77% | 1,121초 | 8.38 | 16 | 1-shot · 관측 DONE |
| fable-5.1 plan-smith r1 | 계획 | **3,059,106** | 404,363 | 62% | **5,007초** | **31.58** | 24 | **1-shot 완주**(분할까지) |
| | 구현 | 0 | 0 | — | 1초 | 0.00 | 1 | 지출 한도 — 시작 직후 종료, 미실행 |
| opus-5.5 plan-smith r1 | 계획 | **≥ 5,820,136** | 540,300 | 76% | **≥ 5,034초** | **≥ 16.53** | 29 | 지출 한도로 **끊김**(분할 뒤 결함 수정 재시작 직후) |

**"1-shot"의 뜻.** 네 base 단계와 fable 계획은 한 세션으로 끝났다. `*.resumed` 표시는 **이전 시도가 보관됐다**는 뜻일 뿐이다.
이전 시도는 두 종류다. r1 기동 실패는 세션이 없어 0토큰이었다. plan-smith r1은 일시정지로 끊긴 시도가 있었다(아래 4절).
측정값은 모두 새로 시작한 세션의 것이다.

**두 원천의 차이.** fable plan-smith 계획은 CLI가 3,059,106, 트랜스크립트가 2,995,113이다. 차이 63,993은 전부 output이다(CLI 404,363 vs 340,370).
원인은 확정하지 못했다. SPEC대로 CLI 값을 쓴다. 나머지 단계는 두 원천이 일치한다.

## 2. R — 체인 비용 비율 (하한)

R = Σ plan-smith 체인 / Σ base 체인 (모델별). plan-smith 체인에는 계획 비용만 넣었다(구현 ≥ 0).

| 모델 | base 체인 (계획 + 구현) | plan-smith (계획만, 하한) | **R_tok** | **R_time** | R_usd | R_out |
|---|---|---|---|---|---|---|
| opus-5.5 | 2,414,911 토큰 · 2,217초(37.0분) · $7.21 | ≥ 5,820,136 · ≥ 5,034초(83.9분) · ≥ $16.53 | **≥ 2.41** | **≥ 2.27** | ≥ 2.29 | ≥ 2.33 |
| fable-5.1 | 1,858,055 토큰 · 2,330초(38.8분) · $15.33 | ≥ 3,059,106 · ≥ 5,007초(83.5분) · ≥ $31.58 | **≥ 1.65** | **≥ 2.15** | ≥ 2.06 | ≥ 2.03 |

계산: opus 5,820,136 / 2,414,911 = 2.410 · 5,034 / 2,217 = 2.271 · 16.53 / 7.21 = 2.293 · 540,300 / 231,711 = 2.332.
fable 3,059,106 / 1,858,055 = 1.646 · 5,007 / 2,330 = 2.149 · 31.58 / 15.33 = 2.060 · 404,363 / 198,975 = 2.032.

**결정 규칙(SPEC, 사전 등록) 적용:** 두 모델 모두 R_tok ≥ 1.1 → **"비용이다"** 구간. 하한이므로 구현 단계를 돌려도 이 구간을 벗어날 수 없다.
R_tok과 R_time은 같은 방향이고, 달러도 같은 방향이다. n=1이므로 사전 등록한 n=3 판정은 아니다.

계획 단계끼리만 비교하면: opus ≥ 10.2배 토큰 · ≥ 4.67배 시간, fable 3.90배 토큰 · 4.14배 시간 · 4.54배 달러.

비교 기준: base 계획 세션 전체가 opus 573,155 토큰 · 18.0분, fable 783,436 · 20.1분이다.

분할 비용: 분할 단독 측정([`../split-1.6.0/`](../split-1.6.0/) S6, opus 중앙값 157초 · $0.79)보다 크다. 파이프라인 안에서는 분할 패스만 8.4~10.4분 걸렸다.
분할이 없는 base와 비교할 때 이 비용은 전부 plan-smith 쪽에 붙는다.
