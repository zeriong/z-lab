**범위: 모델·arm당 n=1, plan-smith는 하한.** 사전 등록은 n=3이었다. 사용자 결정(2026-09-30)으로 r1에서 마무리했고,
그 r1의 plan-smith 두 체인은 조직 지출 한도로 끊겼다. fable은 계획을 완주했지만 구현이 돌지 않았고, opus는 계획 도중에 끊겼다.

## 질문에 대한 답

**같은 모델이 계획하고 구현할 때, 이 과제에서 실제 plan-smith 1.6.0은 토큰도 시간도 아끼지 못했다. 오히려 두 배 넘게 썼다.**

| 모델 | base 체인 전체(계획 + 구현, 관측 DONE) | plan-smith **계획 단계만** | R_tok | R_time |
|---|---|---|---|---|
| opus-5.5 | 2,414,911 토큰 · 37.0분 · $7.21 | ≥ 5,820,136 · ≥ 83.9분 · ≥ $16.53 (끊김) | **≥ 2.41** | **≥ 2.27** |
| fable-5.1 | 1,858,055 토큰 · 38.8분 · $15.33 | 3,059,106 · 83.5분 · $31.58 (완주) | **≥ 1.65** | **≥ 2.15** |

사전 등록한 결정 규칙으로 보면 두 모델 모두 **"비용이다"(R_tok ≥ 1.1)** 구간이다. 구현 단계를 돌려도 이 구간을 벗어날 수 없다.
1순위(토큰)와 2순위(시간)가 같은 방향이고, 달러도 같은 방향이다(≥ 2.29배 · ≥ 2.06배).

같은 방향의 관측이 이전에도 반복됐다(모두 끊긴 세션의 하한). 이 계열에서 일시정지된 r1은 계획 57분에 opus 2.31M · fable 1.54M 토큰을 썼다.
1.4.2 계열에서는 plan-smith 계획이 base 계획의 3.1배 이상(opus), 1.4배 이상(fable)이었다. 카나리는 69배였다.

**이 결정의 근거 범위 (제4조).** 결정은 사용자의 것이다. 아래는 측정이 닿은 곳과 닿지 않은 곳을 적은 것이다.

  긴 대화에서의 의도 보존(이 과제는 요구사항 파일 하나), 품질(사다리 포화, plan-smith arm은 구현이 돌지 않음)도 재지 않았다.
  폐기는 이 영역에서도 기대 효능이 비용을 넘지 않는다고 본 판단이며, 측정으로 확인한 것은 아니다.
- 효능의 원천으로 확인됐던 **내용 규칙**(구현자 정보 한 줄 B12, 복사 가능한 이음새 B13, 구현자 계약 B11)은 파이프라인과 분리해 다른 형태로 쓸 수 있다.
  비용은 파이프라인(메인 에이전트 43~50%, 분할 20~27%)에서 나왔다. 그 형태의 효능은 재지 않았다.

## 관측된 것

### F1. base 계획만으로 두 모델 모두 한 번에 작동하는 게임을 만들었다

opus-5.5와 fable-5.1의 base-plan r1이 모두 **DONE**(L5 + uncaught 0)이었고, 10스테이지도 실재했다. 수리 루프는 없었다.
이 과제에서 base 계획의 비용은 곧 완성까지의 비용이다. plan-smith가 되찾을 수 있는 몫은 구현 단계뿐인데, 그것이 0이 되어도 R은 1.65를 넘는다.

### F2. plan-smith 계획 비용의 절반은 메인 에이전트, 5분의 1 이상은 분할이다

METRICS 3절. fable(완주)은 메인 에이전트 49.8%, 분할 19.6%, 작성 14.3%, 반영 10.9%, 감사 5.4%였다.
opus(끊김)는 메인 43.5%, 분할 26.5%, 반영 9.4%, 작성 9.3%, 추가 보강 7.1%, 감사 4.2%였다.

- **작성 패스 하나가 base 계획 세션 전체와 비슷한 규모다**(토큰 0.94배 · 0.55배). 시간은 2.2배 걸렸다(39~45분 vs 18~20분).
  플랜 분량은 비슷하다 — base 37~44k자, plan-smith 40~43k자. plan-smith는 더 큰 플랜을 만든 것이 아니라 **같은 크기의 플랜을 더 비싼 절차로** 만들었다.
- 메인 에이전트는 83분 동안 24~29턴을 돌았고, 그 토큰의 대부분은 cache_read다(스킬 문서 · 프레임 원문 · 패킷을 실은 컨텍스트를 매 턴 다시 읽는다).
- **분할은 파이프라인 안에서 단독 측정보다 훨씬 비쌌다.** 분할 패스만 8.4~10.4분 · 586k~1.54M 토큰이 들었다.
  단독 측정([`../split-1.6.0/`](../split-1.6.0/) S6, opus 중앙값 157초 · $0.79)의 3~4배 시간이다. 원인은 분리하지 않았다(입력 크기 · 서브에이전트 effort · 검증 방식).
  이 과제의 플랜은 base든 plan-smith든 20,000자를 넘으므로, **1.6.0에서는 분할이 사실상 매번 돈다.**

### F3. 분할 담당의 결함 보고를 메인 에이전트가 세 번 세 가지로 다뤘다 (제품 관측)

`references/split.md` 는 분할 담당에게 "결함을 보면 고치지 말고 보고하라"고 한다. 그런데 SKILL.md Stage 2d에는 메인 에이전트가 **그 보고를 어떻게 처리할지**가 없다.

| 세션 | 보고된 결함 | 메인 에이전트의 처리 | 결과 |
|---|---|---|---|
| 카나리(opus) | 문구 3건 | 검사 통과 **뒤에** 파트를 직접 고침 — `plan.unsplit.md` 는 이미 지운 뒤라 재검사 없음 | 설계 불변식 1("메인은 플랜을 쓰지 않는다") · 2d("옮기기만")와 충돌 |
| r1 fable | 2건(부기 불일치 · 명시 안 된 이음새) | 고치지 않고 그대로 전달 | 가장 싸다. 결함은 플랜에 남음 |
| r1 opus | 5건 | 본문에서 확인 → **분할을 되돌리고**(`rm -r parts`, unsplit 복원) → plan-writer 재호출 → (재분할 예정) | 지출 한도로 끊김. 완주했다면 수정 + 재분할 비용이 더 붙었다 |

분할 담당은 배선 감사와 별개로 **세 번째 검토자**처럼 동작하고 있다. 처리 규칙이 없으니 메인 에이전트의 재량에 따라
불변식 위반, 결함 방치, 재작성 루프로 갈린다. n=3, 과제 1종.

### F4. opus 메인 에이전트가 절차에 없는 보강 패스를 스스로 추가했다

opus r1은 감사 반영 뒤 메인 에이전트가 직접 `grep` 으로 "실패 화면 공백"을 찾았다. 그리고 plan-writer를 한 번 더 불렀다
(`Close fail-screen gap in plan`, 415,754 토큰 · 5.3분). SKILL.md의 build-out 절차(작성 → 감사 → 반영 → 분할)에는 이 패스가 없다.
메인 에이전트가 플랜을 직접 쓰지 않고 plan-writer에게 맡긴 것은 불변식을 지킨 것이다. 그러나 패스 수의 상한이 없어 비용이 열려 있다. n=1.

### F5. 실제 파이프라인의 계획 비용은 이전 계열의 근사보다 훨씬 크다

- 카나리(스톱워치 한 페이지, opus-5.5): base 59,335 토큰 · 126초 → plan-smith 1.6.0 4,104,268 토큰 · 2,670초 — **69배 · 21배**.
- 현행 README·FAQ의 "계획 3.0배(229k vs 689k)"는 에이전트 하나가 스킬 문서를 읽고 쓰는 **근사**를 잰 값이다(transfer/v1.4-validation).
  이 계열의 실제 파이프라인 계획은 게임 과제에서 **base 계획의 3.9배(fable, 완주) · 10.2배 이상(opus, 끊김)** 이다.
  README의 수치는 실제 제품의 계획 비용을 크게 낮춰 적고 있다.

### F6. 패킷의 `Requested by` 가 계정 이메일을 끌어온다 (B19 보강)

1.6.0 계열에서 만들어진 패킷 7개 중 **2개**가 `Requested by: zeriong (<계정 이메일>)` 을 적었다. 7개는 카나리 1, 일시정지로 끊긴 r1 2,
세션 종료로 끊긴 r2 2, 한도로 끝난 r1 2다. 이메일을 적은 것은 카나리와 끊긴 r2로, **둘 다 opus-5.5**였다.
1.4.2 계열 2/10(전부 fable-5.1)과 합치면 **4/17, 두 모델 모두**다. 나머지는 이름만 적거나 "사용자", "배치 실행"처럼 맥락을 적었다.
러너의 가림·검사가 공개 저장 전에 잡았다(끊긴 r2 패킷은 저장소 밖 픽스처에만 있다).

부수: 끊긴 r1 fable 패킷은 `Requested by: zeriong (배치 실행 — 비교 실험 셀 \`fable-5.1_plan-smith_r1\`)` 이라고 적었다.
**픽스처 경로의 셀 이름으로 자신이 비교 실험의 한 arm임을 알아챈 것이다.** 두 arm 모두 자기 셀 이름이 경로에 보이므로 조건은 대칭이다.

### F7. 하네스 사실 (재발견 비용 절약용)

- `claude -p` 는 stdin을 3초 기다린다 — `< /dev/null` 필요.
- CLI 자동 업데이트(2.1.283 → 2.1.284) 직후 기동한 4세션이 세션 생성 없이 빈 출력으로 끝났다 → `DISABLE_AUTOUPDATER=1`.
- 오케스트레이터 Claude Code 세션이 끝나면 그 세션이 띄운 백그라운드 프로세스가 함께 죽는다 → 러너는 `nohup` + 이중 fork로 분리.
- `--setting-sources project` + `claudeMdExcludes: ["**/CLAUDE.md"]` 로 사용자 플러그인·스킬·CLAUDE.md·훅이 0이 된다(첨부 구조로 확인).
  초기 캐시 컨텍스트가 22,532토큰에서 1,982토큰으로 줄었다.
- 지출 한도는 **진행 중인 세션을 끊는다.** 한도 메시지가 `result` 로 오고 `is_error: true` 이며, 구현처럼 새로 시작한 세션은 0토큰으로 끝난다.
  지출 한도로 끊긴 것이 두 계열을 합쳐 세 번이다(1.4.2 1·3차, 이 계열 r1). plan-smith 한 체인이 계획만으로 $17~32를 쓰는 규모에서는 한도가 곧 실험 설계의 제약이다.

## 측정하지 않은 것

- **plan-smith arm의 구현과 게임 품질.** 두 셀 모두 구현이 돌지 않았다. plan-smith 플랜이 더 나은 게임을 만드는지는 이 계열로 말할 수 없다.
  다만 base도 두 모델 모두 DONE이었고 사다리는 포화 상태다(B15). 그래서 이 사다리로는 품질 우위가 드러날 여지 자체가 작다.
- **opus plan-smith 계획의 완주 비용.** 끊긴 시점까지만 셌다. 완주했다면 결함 수정과 재분할이 더 붙었다.
- **n.** 모델·arm당 1이다. 실행 간 분산은 모른다. 참고로 plan-smith 쪽 값을 그대로 둘 때 "비용이다" 구간(R_tok ≥ 1.1)을 벗어나려면 base 체인이 fable은 50% 이상, opus는 119% 이상 비싸져야 한다.
- **과제 1종**(2D 물리 게임, 요구사항 파일 하나). 대화 맥락이 긴 실제 작업에서 패킷이 주는 가치는 재지 않았다.
- **구현자가 계획자보다 약한 경우.** 이 계열의 질문은 같은 모델이다. 약한 구현자(haiku)에서의 절감은 model-bump 2b가 다뤘다(R 0.435, 단 근사 파이프라인).
- plan-writer의 effort(고정 불가, effort-flags E6), 대화형 세션의 확인 게이트, 달러의 정답(CLI 추정치).
- 두 원천의 차이(fable 계획 output 63,993토큰)의 원인.
