# 웹 브라우저 앵그리버드 게임 — 구현 플랜

## 1. 목표와 범위

새총으로 발사체를 당겨 쏘고, 포물선 궤적·중력·충돌·구조물 파괴로 돼지를 제거하는 물리 기반 슬링샷 게임을 웹 브라우저에서 구현한다. 스테이지는 10개, 인게임 우측에 일시정지 버튼이 있고 클릭 시 "다시하기 / 메인으로" 오버레이가 뜬다. 데스크톱 브라우저(Chrome 최신) 마우스 입력을 1차 타깃으로 하고, 터치는 포인터 이벤트로 함께 흡수한다. 사운드·저장(진행도 localStorage)은 부가 범위로 두되 코어 루프를 막지 않는 선에서만 넣는다.

## 2. 기술 선택

**물리 엔진: Matter.js 채택 (직접 구현 안 함).**
이 게임의 재미는 "구조물이 그럴듯하게 무너지는 것"에서 나온다. 강체 스태킹(블록 쌓기), 회전 관성, 마찰, 복합 충돌 해소를 직접 구현하면 그 자체가 프로젝트가 된다. Matter.js는 강체·복합체·충돌 이벤트(`collisionStart`)·sleeping을 기본 제공하고, 번들 하나로 의존성이 끝난다. 대안인 Box2D(wasm)는 정밀하지만 빌드·바인딩 비용이 크고, Planck.js는 문서가 얇다. 이 규모에서는 Matter.js가 비용 대비 최적이다.

**렌더링: Canvas 2D 직접 렌더 (Matter.Render 미사용).**
Matter의 내장 렌더러는 디버그용 와이어프레임 수준이라 게임 룩을 못 만든다. 물리는 Matter가 계산하고, 매 프레임 body들의 `position/angle`을 읽어 Canvas 2D에 스프라이트(또는 도형+그라디언트)를 그린다. DOM/SVG는 수십 개 강체가 매 프레임 움직이는 데 부적합하고, WebGL(PixiJS)은 이 규모에 과하다. UI(HUD, 일시정지 오버레이, 메인 메뉴)는 Canvas 위에 겹친 HTML/CSS로 만든다 — 버튼·텍스트는 DOM이 접근성과 구현 속도 모두에서 압도적으로 낫다.

**빌드: Vite + TypeScript.** 프레임워크(React 등) 없이 바닐라 TS. 게임 루프와 상태 머신이 중심이라 React가 끼면 오히려 렌더 주기 관리가 꼬인다.

**루프: 고정 타임스텝.** `requestAnimationFrame`으로 그리되, 물리는 `Matter.Engine.update(engine, 1000/60)`을 누적기(accumulator) 패턴으로 고정 60Hz 스텝 실행. 프레임레이트가 달라도 궤적이 동일해야 스테이지 난이도가 재현 가능하다.

## 3. 아키텍처와 상태 머신

```
src/
  main.ts            // 부트스트랩, 루프
  game/StateMachine.ts
  game/states/ MainMenu / Playing / Paused / StageClear / StageFailed
  game/Stage.ts      // 스테이지 로드·월드 구성·판정
  game/Slingshot.ts  // 드래그 입력, 발사, 궤적 예측
  game/entities/     // Bird, Pig, Block(재질별)
  data/stages.ts     // 스테이지 10개 정의
  ui/Hud.ts, PauseOverlay.ts, ResultOverlay.ts
```

상태 머신(단일 enum + 전이 함수):

```
MainMenu → (스테이지 선택/시작) → Playing
Playing → (일시정지 버튼) → Paused
Paused → (계속) → Playing
Paused → (다시하기) → Playing (동일 스테이지 재로드)
Paused → (메인으로) → MainMenu
Playing → (돼지 전멸) → StageClear → (다음 스테이지) → Playing
Playing → (새 소진 & 돼지 잔존) → StageFailed → (다시하기) → Playing
```

전이는 이 표에 있는 것만 허용하고 나머지는 무시(방어적 no-op). `Paused`에서는 물리 엔진 업데이트를 중단하되 마지막 프레임은 계속 그려서 배경이 정지 화면으로 남게 한다.

**일시정지 UI:** 인게임 화면 **우측 상단**에 고정된 ⏸ 버튼(DOM, `position:absolute; right:16px; top:16px`). 클릭 시 반투명 딤 + 중앙 패널 오버레이에 **계속하기 / 다시하기 / 메인으로** 3버튼. 요구사항의 필수는 다시하기·메인으로 2개지만, 계속하기 없이는 일시정지를 풀 수 없으므로 포함한다(⏸ 재클릭으로도 해제 가능).

## 4. 스테이지 시스템 (10단계)

**데이터 구조:** 스테이지는 코드가 아니라 선언적 데이터로 정의한다. 별도 JSON 파일 대신 TS 모듈(`stages.ts`)로 두면 타입 체크와 상수 재사용이 공짜다.

```ts
interface StageDef {
  id: number;            // 1..10
  birds: BirdType[];     // 발사 순서대로, 개수 = 시도 횟수
  pigs: { x, y, size }[];
  blocks: { x, y, w, h, material: 'wood'|'stone'|'ice', angle? }[];
  ground: { platforms?: Rect[] };  // 기본 지면 + 추가 플랫폼
}
```

**로딩/전환:** 스테이지 시작 시 `Matter.World.clear` 후 StageDef로부터 body를 생성해 다시 채운다(엔진 재생성 없이 월드만 리셋 — "다시하기"도 같은 경로). 좌표는 1280×720 가상 해상도 기준으로 정의하고 캔버스에 letterbox 스케일링한다.

**난이도 커브:** 1~2단계는 단순 스택(튜토리얼), 3~5단계에서 재질 혼합(얼음=약함, 돌=단단), 6~8단계는 지붕 아래 숨은 돼지·다층 구조, 9~10단계는 새 수를 빠듯하게 줘서 궤적 정밀도를 요구. 각 스테이지는 "의도된 해법 1개 + 우연 해법 허용"으로 설계하고, 밸런싱은 구현 후 실플레이로 조정한다(플랜상 가장 시간을 잡아먹을 항목으로 예약).

**진행도:** 클리어한 최고 스테이지를 localStorage에 저장, 메인 메뉴 스테이지 선택에서 잠금 해제 표시.

## 5. 슬링샷 게임플레이

**입력:** 포인터 다운이 새총 근처(반경 임계값 내)에서 시작되면 드래그 모드. 드래그 중 새를 포인터 위치로 따라오게 하되 새총 기준 최대 당김 반경(예: 90px)으로 클램프. 포인터 업 시 발사 — 발사 속도 = `(새총 앵커 - 놓은 위치) × 강성 계수`. Matter의 Constraint로 묶는 방식보다, 드래그 중에는 새를 kinematic으로 두고 릴리즈 순간 `setVelocity`를 주는 방식이 제어가 쉽고 튜닝 포인트가 명확해서 이쪽을 택한다.

**궤적 예측:** 드래그 중 예상 초기 속도로 등가속 포물선 점선(점 12~15개)을 그린다. 실제 물리(공기저항 없음, Matter 기본 gravity)와 같은 공식을 쓰므로 초반 궤적은 정확히 일치한다. 충돌 이후는 예측하지 않는다(원작도 동일).

**발사 후:** 카메라는 고정(1280×720 안에 전 씬이 들어오게 스테이지를 설계해 카메라 스크롤 자체를 범위에서 뺀다 — 리스크 절감). 새가 정지(속도 임계 이하 2초) 또는 화면 밖 이탈 시 해당 시도 종료, 다음 새 장전.

**충돌·파괴·점수:**
- `collisionStart` 이벤트에서 상대 속도 기반 충격량을 계산해 각 body의 HP에서 차감. 재질별 HP: 얼음 < 나무 < 돌.
- 블록 HP 소진 → 월드에서 제거(+파편 파티클), 점수 +500. 돼지는 HP가 낮고 소진 시 제거, 점수 +5000.
- **클리어 판정:** 돼지 0마리 → 남은 새 ×10000 보너스 → StageClear.
- **실패 판정:** 새 소진 후 마지막 새의 시도 종료 시점에 돼지 잔존 → StageFailed. (마지막 새가 날아가는 도중에는 판정 유예 — 흔한 판정 버그 지점이므로 "시도 종료 후 판정"을 규칙으로 못 박는다.)

## 6. 구현 단계 (각 단계가 실행 가능한 체크포인트)

1. **골격** — Vite+TS 셋업, 캔버스, 고정 스텝 루프, Matter 월드에 지면+박스 하나 떨어뜨려 렌더 확인. → 검증: 박스가 60fps로 낙하·정지.
2. **슬링샷 코어** — 드래그·클램프·발사·궤적 점선. → 검증: 같은 당김이면 같은 궤적(3회 반복 스크린 좌표 오차 < 2px).
3. **엔티티와 파괴** — 재질별 블록, 돼지, 충격량→HP 파괴, 점수. → 검증: 얼음은 1타, 돌은 직격에도 생존하는 튜닝 확인.
4. **스테이지 시스템** — StageDef 스키마, 로더, 월드 리셋, 스테이지 1~3 데이터. → 검증: 다시하기 시 완전 동일 초기 배치.
5. **상태 머신 + UI** — 메인 메뉴, HUD(점수·남은 새), 우측 일시정지 버튼, 오버레이, 클리어/실패 화면, 전이 전부 연결. → 검증: 위 전이표의 모든 화살표를 수동 순회.
6. **스테이지 4~10 제작 + 밸런싱** — 전 스테이지 실클리어 확인, 난이도 조정. → 검증: 제작자 기준 모든 스테이지 클리어 가능.
7. **폴리시** — 파티클, 사운드(선택), localStorage 진행도, 터치 확인.

단계 1~5가 끝나면 스테이지 3개짜리 완전한 수직 슬라이스가 나온다. 일정이 밀리면 7을 자르고 6을 줄이는 식으로 방어한다.

## 7. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 충격량 기반 파괴 튜닝이 어긋나 블록이 스치기만 해도 부서지거나 안 부서짐 | 3단계에서 충격량 로그를 화면에 출력하는 디버그 모드를 먼저 만들고 임계값을 데이터로 뺀다 |
| 스택된 블록이 저절로 미세하게 흔들리다 무너짐 (물리 엔진 고질 문제) | Matter sleeping 활성화 + 스테이지 로드 후 안정화 프리롤 30스텝 실행 후 입력 허용 |
| 마지막 새 판정 타이밍 버그 (날아가는 중 실패 처리) | "시도 종료 이벤트 이후에만 판정" 규칙을 Stage.ts 단일 지점에 구현 |
| 스테이지 10개 밸런싱 시간 과소평가 | 6단계에 전체 일정의 25%를 배정, 스테이지 에디터 대신 핫리로드(Vite)로 데이터 수정 반복 |
| 프레임 드랍 시 궤적 변화 | 고정 타임스텝 누적기로 원천 차단 (1단계에서 확정) |

## 8. 완료 판정 기준 (Definition of Done)

아래를 모두 만족하면 완료로 본다. ①②⑤는 실측 가능한 정량 기준이다.

1. **[실측]** 스테이지 1~10 전부, 주어진 새 수 안에서 클리어 가능함을 실플레이로 확인 (10/10 클리어 녹화 또는 체크리스트).
2. **[실측]** 인게임 중 Chrome DevTools Performance 패널 기준 5초 구간 평균 프레임 55fps 이상 (블록 20개+ 스테이지에서 측정).
3. 드래그→발사→포물선→충돌→파괴→돼지 제거의 코어 루프가 마우스만으로 동작.
4. 우측 일시정지 버튼 → 오버레이(계속/다시하기/메인으로)가 뜨고, 다시하기는 동일 스테이지 초기 상태로, 메인으로는 메인 메뉴로 전이하며, 일시정지 중 물리가 완전히 정지.
5. **[실측]** 상태 전이표의 모든 전이(8개)를 수동 테스트 체크리스트로 통과, 콘솔 에러 0건.
6. 새로고침 후에도 스테이지 잠금 해제 상태가 유지(localStorage).
