# 웹 앵그리버드류 슬링샷 게임 — 구현 플랜

## 0. 목표와 범위

10개 스테이지, 새총(슬링샷) 발사 → 포물선 궤적 → 중력 → 충돌 → 구조물 파괴 → 목표(돼지) 제거로 이어지는 물리 기반 퍼즐 액션 게임을 웹 브라우저에서 동작시킨다. 우측에 일시정지 버튼을 두고, 클릭 시 다시하기/메인으로 이동이 가능한 오버레이를 제공한다. 별도 백엔드 없이 정적 호스팅으로 배포 가능한 클라이언트 단일 앱으로 만든다(스코어/진행도는 로컬 저장소에만 저장, 서버 저장은 범위 밖).

## 1. 기술 선택

**물리 엔진: Matter.js 채택.** 직접 구현(자체 rigid body + 충돌 판정)은 앵그리버드 특유의 "구조물이 쌓이고 무너지는" 느낌을 내려면 강체 충돌, 안정적인 스태킹(sleeping/resting contact), 회전·마찰·복원력까지 직접 튜닝해야 하는데, 이건 곧 물리 엔진 하나를 새로 만드는 일이다. 10 스테이지를 일정 내에 완성하는 게 목표이므로 검증된 2D 물리 엔진을 쓰는 게 합리적이다. Matter.js는 다음 이유로 선택한다: (1) 브라우저 전용 2D에 특화, 번들 크기 작음(~100KB급) (2) 강체 스태킹/슬립 처리가 기본 내장 (3) 충돌 이벤트(collisionStart 등)를 게임 로직(파괴 판정, 점수)과 분리해서 훅 걸기 쉬움 (4) 커스텀 렌더러를 붙이기 쉬워서(엔진과 렌더링 분리) 아트 스타일을 자유롭게 가져갈 수 있음. Box2D 포팅(Planck.js)도 후보였으나 API 복잡도 대비 이득이 크지 않아 보류.

**렌더링: Canvas 2D API 채택 (Matter.js 자체 렌더러는 쓰지 않음).** 이유: Matter.js의 기본 렌더러는 디버그용에 가깝고, 스프라이트/파티클(파괴 파편, 먼지 이펙트)을 자연스럽게 넣으려면 직접 그리는 게 낫다. WebGL/PixiJS는 스테이지 10개 수준의 2D 씬에는 과한 선택이고, 팀이 Canvas 2D에 더 익숙하다는 전제하에 개발 속도를 우선한다. 물리 시뮬레이션은 Matter.js의 fixed timestep(예: 1/60s, `Engine.update`)으로 별도 진행하고, 렌더링은 매 `requestAnimationFrame`마다 물리 바디의 현재 위치를 읽어 그리는 방식으로 완전히 분리한다(시뮬레이션-렌더 분리는 나중에 배속/리플레이 기능을 넣더라도 안전).

**프레임워크: 순수 TS + Vite.** React 등 UI 프레임워크는 HUD/오버레이 같은 얇은 DOM UI에만 최소로 쓰고(혹은 순수 DOM+CSS로도 충분), 게임 루프 자체는 프레임워크 개입 없이 직접 제어한다. 상태(리액트 state 등)로 게임 루프를 돌리면 리렌더 타이밍 이슈가 생기기 쉬워서, 게임 코어와 UI 레이어를 명확히 분리하는 편이 유지보수에 유리하다.

## 2. 아키텍처 개요

모듈을 4개 레이어로 나눈다.
- **Core (물리/시뮬레이션)**: Matter.js 엔진 래핑, 바디 생성 팩토리(새·돼지·나무/돌/유리 블록), 충돌 이벤트 → 게임 이벤트 변환.
- **Game (룰/상태)**: 상태 머신, 스테이지 로더, 점수/생명(남은 새 수), 클리어/실패 판정.
- **Render**: Canvas 2D 드로잉, 카메라(발사 후 발사체 추적), 궤적 예측선, 파티클.
- **UI (DOM)**: 메인 메�뉴, 스테이지 선택, 인게임 HUD(남은 새 수, 점수), 일시정지 버튼 및 오버레이, 클리어/실패 모달.

레이어 간 통신은 단순 이벤트 버스(발행/구독) 하나로 통일한다. 예: `game:paused`, `stage:cleared`, `bird:launched`. UI는 Game 레이어의 상태를 구독만 하고, Game 레이어를 직접 조작하지 않도록(단방향) 한다.

## 3. 상태 머신

`Main → InGame → Paused → (Cleared | Failed)` 를 명시적 상태 객체로 구현한다(문자열 enum + 전이 테이블, 별도 라이브러리 없이 직접 구현해도 충분한 규모).

- `Main`: 스테이지 선택 화면. `startStage(n)` → `InGame`.
- `InGame`: 물리 루프 실행 중. `pause()` → `Paused`(물리 업데이트만 정지, 렌더는 마지막 프레임 유지 + 오버레이 표시). 돼지 전멸 → `Cleared`, 새 소진 && 목표 미달성 → `Failed`.
- `Paused`: 우측 일시정지 버튼 클릭으로 진입. 오버레이에 "다시하기"(현재 스테이지를 `InGame`으로 재시작, 물리 바디 전부 재생성), "메인으로"(`Main`으로 전이, 현재 스테이지 리소스 해제) 두 버튼만 노출. `resume()`으로 `InGame` 복귀도 지원(오버레이에 "계속하기" 추가 여지는 있으나 요구사항엔 없으므로 1차 범위에는 넣지 않음 — 필요시 논의).
- `Cleared/Failed`: 결과 모달, "다음 스테이지"/"다시하기"/"메인으로" 선택.

전이는 반드시 상태 머신 객체를 통해서만 일어나게 하고, UI 컴포넌트가 직접 `engine.stop()` 같은 걸 부르지 않도록 강제한다(회귀 버그 방지).

## 4. 10개 스테이지 시스템

스테이지는 코드가 아니라 **선언적 JSON 데이터**로 정의한다. 필드: `id`, `birds`(발사 가능한 새 종류·순서 배열), `pigs`(위치·반경), `blocks`(타입: wood/stone/glass, 위치, 회전, 크기 — 재질별 강도·질량은 상수 테이블에서 조회), `slingshotAnchor`(새총 위치), `groundY`, `parScore`(별점 기준, 선택). 이렇게 데이터화하면 스테이지 10개를 밸런싱할 때 코드를 안 건드려도 되고, 나중에 에디터를 붙이기도 쉽다.

난이도 곡선: 1~3은 나무 블록 위주로 물리 감 익히기, 4~6은 재질 혼합(유리는 약함, 돌은 강함) + 새 종류 분화(직진형/폭발형 등 2종 이상 도입), 7~10은 다단 구조물 + 제한된 새 수로 정밀 조준 요구. 새 종류를 2가지 이상 넣는 이유는 "돼지만 잡으면 끝"인 단조로움을 피하고 슬링샷 게임 특유의 전략성(어떤 새를 어디에 순서대로 쓸지)을 살리기 위함.

로딩/전환: 스테이지 전환 시 이전 Matter.js `World`를 완전히 폐기하고 새로 생성한다(바디 재사용 시 잔여 속도/충돌 상태가 남는 버그를 겪은 경험이 있어, 매 스테이지 클린 월드로 시작하는 걸 원칙으로 한다). JSON은 `stages/stage-01.json` ~ `stage-10.json`으로 정적 파일 분리, 빌드 시 번들에 포함(런타임 fetch 불필요, 첫 로딩 지연 최소화).

## 5. 슬링샷 입력과 궤적 예측

포인터다운을 새 위치 근방에서 감지 → 드래그 중 새 바디를 물리 시뮬레이션에서 잠시 제외(`isStatic` 또는 별도 kinematic 상태)하고 포인터 좌표를 따라가게 하되, 새총 앵커 기준 최대 당김 반경을 제한(원 밖으로는 못 당기게 clamp)한다. 포인터업 시 `힘 = (앵커 - 현재위치) * 계수`로 임펄스를 적용해 발사한다(당긴 방향의 반대로 발사 — 익숙한 새총 감각).

궤적 예측선은 실제 물리 충돌을 일으키지 않는 "그림자 시뮬레이션"으로 그린다: 현재 당김 벡터로부터 등가속도 포물선 공식(x = v₀t, y = v₀t + ½gt²)을 이용해 점 여러 개를 찍는 방식이 가장 싸고 예측 가능하다(Matter.js 서브스텝을 몰래 돌려서 예측하는 방법도 있으나, 실제 충돌체와 겹치면 노이즈가 생기므로 단순 공식 기반으로 충분히 그럴듯하다). 드래그 중 매 프레임 갱신.

## 6. 충돌·파괴·점수·클리어 규칙

Matter.js의 `collisionStart`/`collisionActive` 이벤트에서 충돌 임팩트(상대 속도 기반 운동량)를 계산해, 블록별 내구도 임계값을 넘으면 "파괴" 처리(바디를 월드에서 제거하고 파편 파티클 스폰, 재질별 파괴음). 돼지는 임팩트가 일정치 넘거나 블록에 깔리면 제거. 모든 돼지 제거 = 클리어, 새가 모두 소진되고 돼지가 남아있으면 실패(단, 마지막 새의 물리가 완전히 멈춘 뒤 판정 — 발사 직후 바로 실패 처리되지 않도록 "정지 대기" 타이머 둠). 점수는 파괴한 블록/돼지별 고정 점수 + 남은 새 1마리당 보너스로 단순하게 시작(밸런싱은 플레이테스트 후 조정).

## 7. 일시정지 UI

인게임 화면 우측 상단 고정 위치에 항상 보이는 파우즈 버튼(터치 타깃 44px 이상)을 배치한다. 클릭 시 캔버스 위에 반투명 오버레이(DOM 레이어, 캔버스를 가리지 않고 그 위에 얹음)를 띄우고 "다시하기", "메인으로" 두 버튼을 세로 배치한다. 오버레이가 떠 있는 동안은 `requestAnimationFrame` 루프에서 물리 업데이트만 스킵하고(렌더는 마지막 프레임을 그대로 유지하거나 살짝 어둡게 처리), 입력 이벤트는 오버레이가 캡처해 밑의 캔버스로 전달되지 않게 한다.

## 8. 구현 단계

1) 프로젝트 세팅(Vite+TS), Matter.js 연동, 빈 캔버스에 정적 바디 하나 렌더 — 검증: 중력으로 박스가 바닥에 떨어짐.
2) 새총 드래그/발사 + 궤적 예측선 — 검증: 드래그 각도·힘에 따라 발사체가 예측선과 일치하는 궤적으로 날아감.
3) 블록 파괴·돼지 제거·점수 로직 — 검증: 임팩트 임계값 이상 충돌 시 블록이 사라지고 점수가 오름.
4) 상태 머신 + 일시정지 오버레이(다시하기/메인으로) — 검증: 각 전이가 의도한 화면으로만 이동하고 잘못된 상태에서 진입 불가.
5) 스테이지 데이터 포맷 확정 후 1개 스테이지 완성 → 나머지 9개 스테이지 데이터 제작 및 난이도 튜닝.
6) 클리어/실패 판정, 스테이지 선택 메인 화면, 로컬스토리지 진행도 저장.
7) 폴리싱(사운드, 파티클, 모바일 터치 대응, 성능 프로파일링).

## 9. 리스크

- **물리 안정성**: 얇은 블록이 쌓였을 때 Matter.js 기본 solver 정밀도로 떨림(jitter)이 생길 수 있음 → iteration 수 상향, 블록 최소 두께 제약으로 완화.
- **모바일 터치**: 드래그 제스처가 스크롤/줌과 충돌 가능 → 캔버스 영역에 `touch-action: none` 적용.
- **밸런싱 시간**: 10 스테이지 난이도 튜닝은 반복 플레이테스트가 필요해 일정 리스크가 가장 큼 → 데이터 기반 설계(JSON)로 코드 재작업 없이 반복 가능하게 미리 대비.
- **파괴 판정의 과도/과소 민감도**: 임계값 하나로 모든 재질을 커버하기 어려움 → 재질별 상수 분리, 플레이테스트로 조정.

## 10. 완료 판정 기준 (Definition of Done)

- 10개 스테이지 모두 데이터가 존재하고, 각 스테이지를 처음부터 끝까지 플레이해 클리어(모든 돼지 제거) 또는 실패(새 소진)까지 도달 가능함을 수동 플레이로 확인한다.
- **실측 가능 기준**: 스테이지 1을 새총으로 3회 이내 발사해 모든 돼지를 제거했을 때, 5초 이내에 상태가 `Cleared`로 전이되고 클리어 모달이 표시된다(자동화 테스트 또는 수동 스톱워치 측정 가능).
- 인게임 중 우측 일시정지 버튼 클릭 → 오버레이 표시 → "다시하기" 클릭 시 동일 스테이지가 초기 상태(새 수·블록 배치 원복)로 재시작되고, "메인으로" 클릭 시 메인 화면으로 전이되며 이때 물리 루프가 완전히 정지(백그라운드에서 계속 도는 좀비 루프 없음)함을 확인한다.
- 60fps 기준 프레임 드랍 없이(크롬 개발자도구 Performance 패널에서 측정 시 평균 16.7ms/frame 내외) 스테이지 하나(가장 블록 많은 스테이지)가 구동됨을 확인한다.
