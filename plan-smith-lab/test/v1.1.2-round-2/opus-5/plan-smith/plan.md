# 웹 브라우저 앵그리버드 — 10 스테이지 구현 플랜

- Reasoning frame: spec-coverage / Style: opus
- 한 줄 요약: 요구 3개(10스테이지·슬링샷 물리 루프·우측 일시정지→다시하기/메인으로)를 **요구 × 표면 매트릭스**로 전개해 빈칸 없이 판정하고, 얇은 E2E 한 줄기 → 스테이지 콘텐츠 10개 → **이름 붙은 완성도 패스** 순서로 짓는다.

**하드 제약** (출처: 요구사항 문서 `game-prompt.md`)
1. 스테이지 **10단계** — 로더 1개 + 스테이지 1개가 아니라, 난이도 곡선을 가진 **저작 콘텐츠 10개**.
2. 앵그리버드와 동일 계열 게임 시스템 — 새총 당겨 발사, 포물선·중력·충돌·구조물 파괴로 돼지 제거.
3. **일시정지 버튼이 인게임 우측**에 존재, 클릭 시 **다시하기 / 메인으로** 버튼 노출.
4. (실험 제약) 게임을 구현하지 않는다 — 산출물은 플랜 문서 1개.

**기각 대안** (본문 §7에 근거·부활 조건)
- 물리 엔진 직접 구현 / WebGL 렌더러(PixiJS) / UI 프레임워크(React·Vue) / 절차적 스테이지 생성.

**Gate 0 판정 — build-out.** 이유: 요구 3개가 모두 확정 명세이고, 이 플랜을 문자 그대로 따랐을 때의 위험은 "잘못 골랐다"가 아니라 **"빠뜨렸다"**(점수·별·저장·오디오·이펙트·배경·스택)다. → 프레임 `spec-coverage`. **차용 1건**: 물리 엔진 결정 한 칸에만 `dialectic`을 차용(패자 논거 승격 + 재판정 트리거 — §7-A).

## 1. 요구 × 표면 커버리지 매트릭스

빈칸은 스코프 결정이 아니라 **플랜의 결함**이다. 모든 칸은 `구축` / `보류(+트리거)` / `해당없음(+이유)` 중 하나. 명세가 명시한 R1·R2·R3의 칸은 **`구축`만 허용**된다(격하·보류 금지).

### 1-A. 명세가 직접 말한 요구

| 요구 | 표면 | 판정 | 이 표면의 "완성" 1문장 |
|---|---|---|---|
| R1 10 스테이지 | 스테이지 정의 스키마 | 구축 | `StageDef` 타입 + 런타임 검증기가 있고, 잘못된 스테이지 파일은 로드 시점에 이름과 필드를 지목해 거부한다 |
| R1 | 저작된 스테이지 10개 | 구축 | 10개 전부 저작자가 실제로 클리어했고, §6 표의 "가르치는 것"이 스테이지마다 다르다 |
| R1 | 스테이지 로딩/전환 | 구축 | 전환 후 물리 월드 바디 수가 기준선으로 복귀하고(누수 0), 전환 중 입력이 다음 스테이지로 새지 않는다 |
| R1 | 스테이지 선택 화면 | 구축 | 10칸이 해금 상태·획득 별과 함께 한 화면에 보이고, 미해금 칸은 클릭해도 진입하지 않는다 |
| R2 슬링샷 루프 | 새총 조준(드래그) | 구축 | 포인터를 누른 채 끌면 고무줄과 새가 커서를 따라오고, 최대 당김 거리에서 시각적으로 멈춘다 |
| R2 | 궤적 예측 | 구축 | 발사 전 점선이 실제 비행 초반 경로와 눈에 띄게 어긋나지 않는다(§5-3 수치 기준) |
| R2 | 발사·비행·중력 | 구축 | 당김 벡터의 반대 방향으로 날고, 최대 파워 궤적의 정점·체류시간이 §8 튜닝 기준 안에 든다 |
| R2 | 충돌·데미지·파괴 | 구축 | 재료별로 다르게 부서지고(얼음↔돌 육안 구분), 가만히 쌓인 구조물이 스스로 붕괴하지 않는다 |
| R2 | 돼지 제거 | 구축 | 직격뿐 아니라 **구조물 붕괴·굴러온 파편**으로도 제거된다 |
| R2 | 클리어/실패 판정 | 구축 | 돼지 0 → 클리어. 새 소진 + 월드 정지 + 돼지 잔존 → 실패. 어느 쪽도 아닌 상태로 멈추지 않는다(정지 감지 §8) |
| R2 | 새 종류 | 구축(2종) | 기본새와 탭-대시새의 해법이 실제로 다르다(돌 벽은 대시로만 실용적으로 뚫린다) |
| R3 일시정지 | 우측 일시정지 버튼 | 구축 | 인게임 HUD **우측 상단**에 상시 존재, 히트 영역 ≥44px, 키보드 `Esc`로도 열린다 |
| R3 | 일시정지 오버레이 | 구축 | **다시하기 / 메인으로**가 있고, 오버레이가 떠 있는 동안 물리·타이머·오디오가 전부 정지한다 |
| R3 | 계속하기(재개) | 구축 | 오버레이를 닫으면 정지 직전 상태(새 위치·당김 여부 포함)로 정확히 이어진다 |
| R3 | 다시하기 경로 | 구축 | 스테이지를 처음 상태로 재구성하고, 이전 시도의 파편·점수·오디오가 남지 않는다 |
| R3 | 메인으로 경로 | 구축 | 메인 화면으로 나가며 인게임 리소스를 해제하고, 다시 들어가도 초기 상태다 |

> R3의 "계속하기"는 명세에 없다. 하지만 재개 경로가 없으면 일시정지는 **되돌릴 수 없는 화면**이 되어 그 자체로 미완성이므로, 명세 확장이 아니라 표면 완성 요건으로 `구축`에 넣었다.

| 요구 | 표면 | 판정 | 이 표면의 "완성" 1문장 |

| R4 | 별 1~3 | 구축 | 스테이지별 임계값이 데이터로 존재하고, 획득 별이 결과 화면과 선택 화면에서 동일하다 |

| R5 감각 피드백 | 파괴 파티클·화면 흔들림 | 구축 | 나무·얼음·돌이 서로 다른 파편/색으로 부서지고, 큰 붕괴에서만 화면이 흔들린다 |

## 2. 문제 정의 / 목표

물리 슬링샷 게임의 어려움은 물리 자체가 아니라 **셋이 동시에 성립해야 한다는 점**이다.

1. **느낌** — 당김→발사→붕괴의 인과가 손에 붙어야 한다(수치 튜닝 문제).
2. **콘텐츠** — 같은 메커닉으로 서로 다른 10개 문제를 저작해야 한다(스키마 + 저작 노동 문제).
3. **셸** — 메인/선택/일시정지/결과가 상태 누수 없이 왕복해야 한다(상태 머신 문제).

세 개는 서로 다른 실패 양상을 가지며, 한 개만 잘해도 "된 것"으로 보이지 않는다. 이 플랜의 단계 순서(§5)는 이 세 축이 **각각 검증 가능해지는 순서**로 짜였다.

## 3. 납품 스택 — 무엇을 사고 무엇을 강제하는가

정석 조합이라도 명시하지 않으면 구현자의 기본값이 빈칸을 채운다(라운드1의 관측된 사고: CDN 스크립트 태그 + 존재하지 않는 벤더 파일 폴백). 그래서 선택과 **그 선택이 강제하는 것**을 함께 적는다.

| 선택 | 무엇을 사는가(강제되는 것) |
|---|---|
| **TypeScript**(strict) | `StageDef` 스키마와 상태 머신 전이가 컴파일 타임에 검사된다 — 선언되지 않은 전이·누락 필드가 빌드에서 죽는다 |
| **Vite** + npm(로컬 설치, CDN 금지) | 의존성이 `package.json`에 고정되고, `npm run build`가 유일한 배포 산출 경로가 된다 |
| **Canvas 2D**(단일 캔버스) | 월드 렌더는 즉시모드 한 곳 — 씬 그래프 동기화 버그가 구조적으로 없다 |
| **Matter.js**(강체·충돌) | 마찰·복원·수면(sleeping)·복합체를 직접 만들지 않는다. 대가는 §7-A의 4개 제약 |
| **DOM/CSS 오버레이**(메뉴·HUD·일시정지) | 버튼이 진짜 `<button>` — 포커스·키보드·히트테스트를 다시 구현하지 않는다. **우측 일시정지 버튼은 캔버스 위 DOM 요소**로 배치 |
| **WebAudio**(오디오) | 발사·충돌 사운드의 지연이 `<audio>` 태그보다 낮고, 일시정지 시 컨텍스트 suspend 한 번으로 전부 멈춘다 |
| **localStorage**(영속) | 스키마 버전 키를 함께 저장 — 형식이 바뀌면 마이그레이션 아니면 초기화, 둘 중 하나로만 갈린다 |

파일 경계(구현자의 기본값이 아니라 이 플랜이 정한다): `main.ts`(부트) / `state-machine.ts` / `physics.ts`(Matter 래핑·고정 스텝) / `render.ts` / `input.ts`(포인터·궤적) / `damage.ts`(재료·데미지) / `stages/*.ts`+`stage-schema.ts` / `score.ts` / `storage.ts` / `audio.ts` / `effects.ts` / `ui/*.ts`(DOM 화면) / `types.ts`.

## 4. 명시적 가정 (틀렸을 때의 영향)

- **[전체가 매달린 가정] Matter.js를 고정 타임스텝으로 돌리면 같은 입력이 같은 결과를 낸다(별 임계값·par 튜닝의 전제).**
  - 틀리면: §6의 별 기준과 저작자 par가 재현되지 않아 스테이지 난이도 조정이 매 회차 다른 결과를 낸다.
  - **가장 싼 조기 검증**: 5단계가 아니라 **2단계**에서, 같은 시드·같은 발사 벡터로 5회 시뮬레이션해 착지 x가 동일한지 본다(코드 30줄 수준).
  - **폴백**: 결정성을 포기하고 별 임계값에 여유(+15% 〔임의 초기값 — 7단계 par 측정 후 재산정〕)를 주고, 진행 해금을 점수가 아니라 **클리어 여부**로만 판정한다. 리플레이 기능은 그때 완전히 버린다.
- 가정: 스테이지당 동적 바디 60개 + 파편 상한 이내에서 Canvas 2D + Matter.js가 60fps를 유지한다.
  - 틀리면: 렌더가 아니라 물리가 병목일 가능성이 높으므로 파편 상한·수면 임계를 먼저 조이고, 그래도 안 되면 §7-B 부활 조건(WebGL)이 발동한다.
- 가정: 저작자 1인이 10개 스테이지를 설계·클리어·par 기록까지 감당할 수 있다.
  - 틀리면: 스테이지 수가 아니라 **스테이지당 저작 밀도**를 줄인다(장식 블록 축소). 10개는 하드 제약이므로 수를 줄이는 폴백은 없다.
- 가정: 대상은 데스크톱 브라우저 우선, 터치는 동작 보장 수준.
  - 틀리면: 1-B의 모바일 튜닝 보류 행이 트리거로 승격된다.

## 7. 대안 & 기각 근거

### 7-A. 물리 엔진: Matter.js vs 직접 구현 (`dialectic` 차용 — 이 한 칸 한정)

- **판정 함수(사전 고정)**: 실패 비용 = 폭발 반경 × 복구 가능성. 엔진을 잘못 고르면 파괴·마찰·수면이 전부 영향받고(반경 최대), 게임 로직이 엔진 API에 물린 뒤 갈아타는 비용은 사실상 재작성(복구 불가). → 반경·복구성 모두 최악 축이므로 **검증된 기성품**이 이긴다.
- **판정**: Matter.js 0.20 계열 채택. 정석에 재도달한 결론이며, 이 차용의 산출물은 승자가 아니라 **패자 논거가 승격된 아래 4개 제약**이다.
- **패자(직접 구현) 논거 승격 — Matter.js 브랜치의 하드 제약**:
  1. **고정 타임스텝 강제** — `Engine.update(engine, 1000/60)`을 누산기로 호출. rAF delta를 그대로 넘기지 않는다(가변 스텝은 결정성과 터널링을 동시에 망친다).
  2. **정적 바디의 질량을 절대 만지지 않는다** — 데미지는 충돌 충격량(상대 속도·침투 깊이)에서 계산하고, `1/mass` 항을 쓰지 않는다. 정적 바디의 무한 질량이 계산에 섞여 NaN이 되는 경로를 코드에 두지 않는다.
  3. **파편 난수는 시드 고정** — 파편 방향/개수까지 재현되어야 저작자 par가 의미를 갖는다.
  4. **파괴는 조인트 파단이 아니라 "바디 제거 + 파편 스폰"** — Matter에 파단 가능한 조인트가 없으므로, 재료 HP 모델을 우리가 소유하고 엔진에는 강체만 맡긴다.
- **재판정 트리거**: (a) 기준 머신에서 동적 바디 60개 + 파편 상한 상태의 p95 프레임 시간이 16.6ms를 넘고 파편 상한·수면 임계 조정으로도 회복되지 않을 때, 또는 (b) 스테이지 설계 2개 이상이 Matter로 표현 불가능한 거동을 요구할 때. 그때도 엔진 교체가 아니라 **해당 서브시스템만 직접 구현**한다(전면 교체는 위 판정 함수가 이미 기각했다).

### 7-B. 그 외

- **WebGL 렌더러(PixiJS 등)** — 기각: 화면당 스프라이트가 수백 단위이고 병목은 렌더가 아니라 물리일 가능성이 높다. **부활 조건**: 파티클 동시 2,000개 또는 드로우콜 300 초과 지점에서 Canvas 2D가 프레임 예산을 못 지킬 때.
- **UI 프레임워크(React/Vue)** — 기각: 화면이 5개(메인/선택/일시정지/클리어/실패)이고 게임 루프와 리액티브 렌더의 소유권 다툼이 순손실. **부활 조건**: 화면이 8개를 넘거나 설정/도전과제처럼 상태가 많은 화면이 추가될 때.
- **절차적 스테이지 생성** — 기각: 하드 제약이 "난이도 곡선을 가진 10단계"이며, 생성기는 곡선을 보장하지 못하고 튜닝 대상이 두 배가 된다. **부활 조건**: v1 이후 무한 모드를 별도 기능으로 붙일 때(10개 저작 콘텐츠를 대체하는 용도로는 부활하지 않는다).
- **물리를 쓰지 않는 스크립트 궤적** — 기각: 하드 제약 2(구조물 파괴)가 강체 상호작용을 요구하므로 요구 위반이다.

## 8. 수치와 그 근거 — 태그 없는 숫자는 두지 않는다

〔도출〕= 한 줄 근거 있음 / 〔초기값〕= 임의 시작값 + 교체 시점 명시 / 〔임의〕= 근거 없음을 선언.

| 값 | 초기 설정 | 태그 |
|---|---|---|
| 논리 캔버스 | 1280×720 | 〔도출〕16:9, 대부분 창에서 레터박스 여백 최소 |
| 물리 스텝 | 1/60초 고정 | 〔도출〕rAF 표준 주기와 일치, 누산기 보정으로 표시율 무관 |
| 중력 | Matter 기본 y=1.0 | 〔초기값〕5단계 느낌 튜닝에서 교체 — **기준**: 최대 파워 궤적의 정점이 화면 높이의 40~50%, 체류시간 1.6~2.2초 |
| 최대 당김 거리 | 110px | 〔초기값〕5단계에서 교체 — 기준: 새총 그래픽을 벗어나지 않으면서 파워 단계가 눈에 보일 것 |
| 최대 발사 속도 | 1,320px/s (=22px/스텝) | 〔초기값〕5단계 튜닝에서 위 정점·체류시간 기준으로 교체 |

## 9. 리스크 & 완화

| 리스크 | 완화 | 조기 신호 |
|---|---|---|
| 물리 튜닝이 끝없이 늘어남("느낌"에 완료 기준이 없다) | 5단계 튜닝의 완료 기준을 **수치**로 고정(정점 40~50%, 체류 1.6~2.2초). 기준 충족 후 추가 튜닝은 9단계 이후로 미룬다 | 5단계가 다른 단계 합보다 길어질 때 |
| 구조물이 로드 직후 스스로 붕괴 | 데미지 임계를 계측값 위로(§8), 스테이지 저작 시 블록을 격자에 정렬하고 초기 겹침 검사를 검증기에 넣는다 | 4단계 계측 로그에 정착 충격량이 임계에 근접 |
| 수면(sleeping) 바디 때문에 클리어/실패 판정이 안 남 | 정지 감지에 6초 하드 캡 + 캡 만료를 정상 판정으로 취급(§8) | 4단계 검증 (b)항 실패 |
| 스테이지 전환 시 바디·이벤트 리스너 누수 | 로더에 언로드 경로를 쌍으로 두고, 6단계 검증에서 바디 수 기준선 복귀를 확인. 리스너 등록은 한 함수로만 | 왕복 후 바디 수 증가 |

| 저장 형식 변경으로 기존 진행이 깨짐 | 스키마 버전 키 + 불일치 시 마이그레이션 또는 초기화(둘 중 하나로만 갈림) | 8단계 손상 복구 검증 |

## 10. "완료"의 정의

전부 **측정 가능한 문장**이며, 각 항목은 이 플랜의 차단 장치가 스스로 만족시킬 수 없는 것으로 골랐다.

1. **클리어 가능성 + 감각 체크리스트** — 저작자가 아닌 테스터 1명이 리로드 없이 메인에서 시작해 스테이지 1→10을 전부 클리어하고, 스테이지별 사용 발사 수를 기록한다. 10/10이면 통과, 하나라도 클리어 불가면 실패. **같은 플레이 중 체크리스트를 동시에 채운다**: 발사·충돌·파괴·돼지 제거·클리어 5개 이벤트에서 각각 소리가 났는가(5/5), 나무·얼음·돌이 서로 구분되는 파편으로 부서졌는가(3/3). 하나라도 비면 실패. (측정: 테스터가 직접, 기록지 1장)
2. **일시정지 계약** — 10개 스테이지 각각에서 [일시정지 → 계속하기], [일시정지 → 다시하기], [일시정지 → 메인으로]를 1회씩(총 30회) 수행. 매회 (a) 오버레이 중 물리 스텝 0, (b) 복귀·재시작 후 월드 바디 수가 기준선과 동일, (c) 효과음 중복 재생 없음. 30/30 통과가 조건. (측정: 바디 수는 콘솔 카운터, 물리 스텝은 스텝 카운터 로그, 효과음은 청취)
3. **프레임 예산** — 스테이지 10에서 파편이 최대인 구간을 포함해 60초 플레이 시 p95 프레임 시간 ≤ 16.6ms. (측정: Chrome, 기준 머신 1대를 문서에 명기, `performance.now()` 히스토그램)
4. **영속성** — 빈 localStorage로 시작 → 3스테이지 클리어 → 브라우저 완전 종료 후 재실행 → 별·해금·음소거가 그대로. 이어서 저장 값을 손으로 망가뜨린 뒤 재실행 → 크래시 없이 초기 상태로 복구. (측정: 개발자 도구에서 직접)
5. **결정성** — 같은 시드로 기록된 입력 시퀀스를 5회 재생 → 클리어 판정과 최종 점수가 5회 모두 동일. (측정: 입력 로그 리플레이. §4 가정이 폴백으로 갔다면 이 항목은 "판정만 동일"로 완화하고 그 사실을 명기)

부수적으로: `tsc --noEmit` 무경고, `npm run build` 성공, 최신 Chrome/Firefox/Safari 데스크톱에서 1항 통과.

## Frame deviations & habit regressions

- **가장 약한 곳: §6의 별3 기준 열이 전부 "7단계 측정"이다.** 프레임의 콘텐츠 축을 지키려면 10개 스테이지가 실재해야 하는데, 별 임계값만은 실제 플레이 없이 채우면 거짓 숫자가 된다. 그래서 임계값 대신 **임계값을 만드는 규칙**(par×0.70/0.90, §8)을 확정하는 쪽으로 직접 고쳤다. 그래도 표 한 열이 비어 보이는 것은 사실이고, 리뷰어라면 여기를 먼저 찔러야 한다.
- **오디오·이펙트 누락을 잡는 장치가 처음 원고에는 없었다(편집으로 해소).** 9단계를 이름 붙인 것만으로는 완료 판정이 그 단계를 강제하지 못했다 — §10의 5개 항목 중 어느 것도 `audio.ts`·`effects.ts`가 아예 없는 빌드에서 실패하지 않았다. §10-1에 감각 체크리스트(소리 5종/파편 3종)를 넣어 고쳤다. 이 결함이 라운드1에서 실제로 관측된 것과 같은 형태였다는 점이 확인 계기였다.
- **정석을 프레임보다 앞세운 곳: §3 스택과 §7-A.** Matter.js/Canvas 2D/TS는 이 도메인의 사실상 표준이고, 판정 함수를 돌리기 전에 이미 답이 정해져 있었다. 그래서 `dialectic` 차용을 "승자 뽑기"로 쓰지 않고 **패자 논거 4개를 승자의 하드 제약으로 승격**시키는 데만 썼다. 그 4개(고정 스텝·정적 바디 질량 불가침·시드 고정·조인트 파단 대신 HP 모델)가 없다면 이 차용은 삭제해야 했다.
- **매트릭스 입도에서 흔들렸다(§1-A).** 프레임은 "요구 × 표면" 한 행을 요구하는데, R2의 "충돌·데미지·파괴"와 "돼지 제거"는 같은 표면의 다른 함수로 볼 수도 있다. 파괴 규칙과 제거 판정이 각각 다른 완성 기준을 갖기 때문에 분리를 유지했지만, 이 판단은 취향에 가깝다.
- **수렴 본능이 나온 지점**: §1-B에서 모바일 레이아웃·키보드 전용 플레이·i18n을 보류로 돌렸다. 셋 다 트리거를 붙였으므로 침묵 누락은 아니지만, "보류 + 트리거"는 이 스타일이 안전하게 기대는 형식이기도 하다. 명세가 직접 말한 R1·R2·R3와 완성도에 직결되는 오디오·이펙트·점수·저장은 하나도 보류로 보내지 않았다는 점만 스스로 확인해 둔다.
- **리뷰어라면 공격할 곳: §8의 재료 HP·데미지 임계.** 임계값이 계측 기반이라고 적었지만 그 계측은 4단계에서 처음 이루어진다. 4단계에서 "정착 충격량"이 예상보다 크게 나오면 임계값이 올라가고, 그러면 돌(HP 90, 임계 14)이 사실상 무적이 되어 §6의 4·6·10 스테이지 설계가 함께 흔들린다. 이 연쇄를 끊는 장치는 지금 문서에 없다 — 4단계 검증 (a)항이 유일한 방어선이다.
