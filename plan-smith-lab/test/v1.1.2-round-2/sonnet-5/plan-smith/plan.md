# 웹브라우저 앵그리버드류 슬링샷 게임 — 10스테이지 구현 플랜
- Reasoning frame: spec-coverage / Style: opus
- 요구 3항목(10스테이지 / 슬링샷 물리 게임플레이 / 우측 일시정지→다시하기·메인으로)을 전부 `build`로 못박고, "완결감"에 필요한 나머지 표면(점수·별점·사운드·저장·메뉴 등)을 빈 칸 없이 판정한 뒤, Matter.js + Canvas2D + TypeScript 스택으로 얇은 수직 슬라이스 → 폭 → 콘텐츠 저작 → 폴리시 순서로 쌓는 build-out 플랜.

## 실행 스탬프 & 의도 요약 (사실만 — 논증은 없음)

| 항목 | 값 |
|---|---|
| plan-smith 설치 버전 | 1.1.3 (문서 전용 릴리스 — `frames.md`/`styles.md`/`SKILL.md`는 1.1.2와 바이트 동일, `../RUN-META.md` 교차 확인) |
| frames.md 줄 수 | 364줄 |
| 작성 모델 | claude-sonnet-5 (main/writer 역할 분리 없이 단일 배치 실행) |
| 실행 방식 | batch/scripted, 대화형 확인 게이트 자가 승인 |

- **과제(1줄):** 앵그리버드류 물리 슬링샷 게임을 브라우저에 10스테이지 분량으로 구현하는 플랜을 작성한다(코드 작성 금지, 플랜 문서만).
- **목표(성공 정의):** 요구사항 3항목이 전부 `build`로 이행되고, 그 외 "완결감"에 필요한 모든 표면이 매트릭스에서 빈 칸 없이 `build`/`defer(+트리거)`/`n-a(+사유)`로 판정되며, 최소 1개의 실측 가능한 완료 기준이 존재한다.
- **하드 제약(출처: 요구사항 문서 원문):**
  1. 스테이지 10단계.
  2. 게임 시작 → 새총 드래그·조준·발사, 포물선 궤적·중력·충돌·구조물 파괴로 목표(돼지 등) 제거 — 앵그리버드와 같은 물리 기반 슬링샷 게임플레이.
  3. 일시정지 버튼이 인게임 **우측**에 존재, 클릭 시 **다시하기 / 메인으로** 버튼 노출.
- **Gate 0 판정:** **build-out**. 이유: 요구사항이 이미 스테이지 수·게임 시스템·UI 배치까지 구체적으로 확정된 완결 스펙이고, 이 플랜을 문자 그대로 따랐을 때의 위험은 "잘못된 선택"이 아니라 "빠뜨린 표면"(사운드·저장·메뉴 등)이다. `frames.md` 10행이 명시하는 실패 사례(동일 스펙을 좁히는 프레임에 태워 사운드/이펙트/저장 레이어가 통째로 증발한 경우)와 이 과제의 형태가 정확히 일치한다.
- **프레임:** `spec-coverage`. 물리 엔진 선택(§물리 엔진 결정)만 별도 하위결정으로 한 번 빌려 쓴다(빌림 기록).
- **스타일:** opus, standalone(릴레이 아님 — 이 플랜에는 다음 패스가 없고, 확인되지 않은 결함은 뒤로 미루지 않고 지금 고치거나 정직하게 defer 사유를 남긴다).
- **미해결 사항:** 아래 §요구사항×표면 매트릭스와 §숫자·계수 태그에서 "열린 질문"으로 표시한 2건(모바일 트래픽 측정 도구, 다중 새 타입 재점화의 정량 기준 부재)은 이 플랜이 결정하지 않고 다음 실행 전 확인 지점으로 남긴다.

## 딜리버리 스택 (명시 + 이유)

| 구성 | 선택 | 이 선택이 강제하는 것 |
|---|---|---|
| 언어 | TypeScript | 스테이지 JSON 스키마와 상태 머신 전이표를 컴파일 타임에 체크(잘못된 스테이지 데이터를 로딩 시점이 아니라 저작 시점에 잡음) |
| 빌드 도구 | Vite | 서버 없는 클라이언트 전용 게임에 맞는 최소 설정 + 빠른 로컬 개발 루프 |
| 렌더링 | Canvas2D | 2D 스프라이트·파티클 수준이면 충분(§물리 엔진 결정과 별도로, WebGL/Pixi는 §대안 참조 — 기각) |
| 물리 | Matter.js | §물리 엔진 결정 참조 |
| 오디오 | HTMLAudioElement 풀(4~5개 SFX) | 효과음 4종 + 선택적 BGM 1개뿐이라 전용 오디오 라이브러리 의존성 추가가 정당화되지 않음 |
| 저장 | localStorage | "클라이언트 전용, 서버 없음" 가정(§명시 가정)과 일치, 별도 백엔드 불필요 |

### 물리 엔진 결정 (borrow: constraint-first 스타일 판정 기준 1회 차용, 5줄)
후보: Matter.js vs 직접 구현. 판정 기준 = 재작업 비용(파괴 연출이 기대만큼 안 나올 때 되돌리는 비용) × 의존성/제어권 손실 비용. 직접 구현은 강체·제약 솔버·파편 판정을 처음부터 만들어야 해 재작업 비용이 매우 크고, Matter.js는 이미 강체+제약+충돌을 제공해 의존성 비용만 진다. → **Matter.js 채택.** 이 선택이 산다: "구조물 파괴"(요구 5)를 처음부터 구현하지 않고 재질별 내구도 규칙(§숫자 태그)만 얹어 구현한다는 것.

## 문제 정의 / 목표

앵그리버드류 슬링샷 물리 퍼즐 게임을 브라우저에서 10개 스테이지, 완전한 일시정지 흐름(우측 버튼 → 다시하기/메인으로)과 함께 "플레이 가능한 완결 상태"로 내놓는다. 완결 상태의 정의는 §요구사항×표면 매트릭스가 빈 칸 없이 판정되는 것이며, 스테이지 수만 채우고 점수·저장·사운드가 증발하는 것은 이 정의를 만족하지 않는다.

## 상태 머신 (요구 3의 골격, 암묵 요구 #18·#19·#20·#26의 근거)

| 상태 | 진입 조건 | 화면/UI | 나가는 전이 |
|---|---|---|---|
| MAIN | 앱 최초 로드 / "메인으로" 클릭 | 시작 버튼, (진행 데이터 있으면) 이어하기 | → STAGE_SELECT |
| STAGE_SELECT | MAIN에서 시작 클릭 | 클리어 여부·별점 표시된 1~10 리스트, 미클리어 다음 스테이지 이후 잠금 | → PLAYING(선택 id) |
| PLAYING | 스테이지 선택 / "다시하기" 클릭 | 인게임 HUD(남은 새·점수·우측 일시정지 버튼) | → PAUSED(일시정지 클릭) / → CLEARED(돼지 전멸) / → FAILED(새 소진 & 돼지 잔존) |
| PAUSED | PLAYING 중 우측 일시정지 버튼 클릭 | 다시하기 / 메인으로 오버레이, **Matter.js Engine.update 호출 정지**(물리 시간 실제로 멈춤, 시각적 정지만이 아님) | → PLAYING(재개는 스코프 외 — 요구사항은 다시하기/메인으로만 명시, "이어서 재개" 버튼은 n-a: 원문에 없음) / → PLAYING(다시하기, 동일 스테이지 재시작) / → MAIN(메인으로) |
| CLEARED | 돼지 전멸 | 별점·점수 오버레이, 다음 스테이지/메인 | → STAGE_SELECT 또는 → PLAYING(다음 스테이지) |
| FAILED | 새 소진 & 돼지 잔존 | 실패 오버레이, 다시하기/메인 | → PLAYING(다시하기) / → MAIN |

## 대안 & 기각 사유

1. **직접 구현 물리 엔진** — 기각: 강체·제약 솔버·파편 판정을 처음부터 만드는 재작업 비용이 Matter.js 채택 대비 압도적으로 큼(§물리 엔진 결정). 재점화 조건: 번들 크기 상한이 50KB(gzip) 미만으로 걸리거나, 결정론적 리플레이(경쟁 리더보드)가 필요해질 때.
2. **WebGL/Pixi 렌더링** — 기각: 2D 스프라이트·파티클 규모에서 셰이더/GPU 파이프라인이 필요 없음. 재점화 조건: 동시 파티클 수가 ~2000개를 넘거나 포스트프로세싱(화면 흔들림의 색수차 등) 요구가 생길 때.
3. **서버 기반 멀티플레이/리더보드**(§매트릭스 #23) — 기각: 요구사항에 근거 없음, 상태 머신에 서버 개념이 없어 도입 시 아키텍처 전체 재설계. 재점화 조건: 제품 로드맵에 소셜/경쟁 기능이 추가될 때.

## 완료의 판정 기준

1. **(실측 가능, 필수)** 이 플랜의 저자가 아닌 사람이 새 브라우저 프로필에서 스테이지 1→10을 한 세션 안에 순서대로 클리어하고, 각 스테이지에서 우측 일시정지 버튼 클릭 → "다시하기" 1회, 별도로 일시정지 → "메인으로" 1회를 실행한다. 화면 녹화를 증빙으로 남기고 "10/10 스테이지 클리어, 다시하기 10/10 동작, 메인으로 10/10 동작"으로 기록한다. 측정자: 저자 아닌 동료 1인, 도구: 화면 녹화 + 체크리스트.
2. 스테이지 클리어 오버레이가 스크롤 없이 별점과 점수를 한 화면에 표시하는지 스크린샷으로 확인.
3. 스테이지 3 클리어 후 탭을 닫고 재실행 시, 스테이지 선택 화면에 1~3이 클리어 상태로 남아 있는지 확인(이 항목이 "0" 실패를 만족하려면 저장 자체가 아예 안 되는 것이 아니라, "클리어한 스테이지가 클리어로 표시되는지"를 봐야 한다 — 저장 로직 부재도 이 테스트를 통과시키지 않도록 클리어 표시가 있는지 명시적으로 확인).

## Frame deviations & habit regressions

- §접근&단계의 0~10번이 의존성 순서이면서 동시에 거의 그대로 시간 순서이기도 하다. 실제 선행조건(2가 나머지 전부의 전제, 6이 7의 전제 등) 때문에 그렇게 된 것이지 상승 서사 습관으로 채운 건 아니지만, 표만 보면 착각하기 쉽다 — "선행조건" 열을 넣어 상쇄했으나 완전히 해소됐다고 자평하지 않는다.
- §매트릭스 #22(새 특수 능력 다양화)의 재점화 트리거가 "피드백에서 지적되면"으로 정성적이다. 다른 defer 항목(#14 BGM, #21 모바일)은 그나마 "지적/UA 비중"으로 관측 가능한 신호가 있는데, #22는 정량 임계치가 없어 사실상 무기한 defer가 될 위험이 있다. 이 플랜 안에서 직접 고치려 했으나("피드백 N건 이상" 같은 임계치를 넣으려 했으나) 이 게임을 아직 아무도 플레이하지 않은 시점에 N을 정하는 것 자체가 근거 없는 숫자를 하나 더 만드는 일이라 판단해, 정직하게 약점으로 남겼다.
- §숫자·계수 태그의 마지막 행(모바일 트래픽 20%)은 담당자와 측정 도구를 비워뒀다. 스텝10 회귀 스윕에서도 이 항목은 검증 대상이 아니다 — 배포 시점 전까지 열린 채로 남는다.
- 만약 내가 이 플랜의 리뷰어라면 가장 먼저 찌를 곳은 §콘텐츠 축의 점수 공식이다. 돼지 처치 점수(5000)와 잔여 새 보너스(2000)의 비율(2.5:1)이 왜 그 비율인지에 대한 근거가 없다 — declared arbitrary로 태그는 붙였지만, "정확도 위주 게임"과 "생존 새 수 위주 게임" 중 어느 쪽으로 플레이어를 유도할지에 대한 실제 설계 의도는 이 플랜에 없다. 1차 플레이테스트에서 재조정한다고만 적어뒀을 뿐, 재조정의 판단 기준 자체는 정의하지 않았다.
