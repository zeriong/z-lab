## 의도 패킷 (Intent Pocket)

**목표:** 완성된 10단계 앵그리버드 게임 — 각 단계는 플레이 가능하고, 새총 발사·물리 시뮬레이션·목표 제거·상태 전환이 모두 작동하는 상태.

**하드 제약:**
- 10단계 모두 구현 (스텁 아님, 각각 게임플레이 콘텐츠)
- 물리 기반 슬링샷 게임플레이 (중력, 충돌, 포물선)
- 오른쪽 우측 일시정지 버튼 → 다시하기/메인으로 메뉴

**기각된 대안:**
- 직접 물리 엔진 구현 — 거절: 개발 기간, 버그 리스크 높음 → Matter.js 사용
- 각 단계별 커스텀 에셋 — 거절: 스코프 초과 → 기하 도형(원, 직사각형)으로 시각화

**위험 카테고리:** 충돌 판정 정확성, 10단계 밸런싱 (과도한 어려움), 상태 머신 오류 (메뉴↔게임 전환 중단)

## 설계 결정

### 1. 물리 엔진 선택 → Matter.js
- **근거:** 2D 강체 물리(Rigid Body Physics) 검증됨, 충돌 판정 정확, 오픈소스·커뮤니티 지원
- **대체안 거절 이유:** Babylon.js 물리 = 더 복잡한 3D 셋업 필요; Rapier = WASM 로드 추가 복잡도
- **영향:** 포물선·중력·충돌이 자동 계산 → 코드 간소화

### 2. 렌더링 → Canvas 2D (Pixi.js 또는 순수 Canvas)
- **근거:** 2D 게임, 고성능, 가볍다
- **선택 상세:** Pixi.js 권장 (스프라이트 배치, 파티클 용이) 또는 순수 Canvas (최소 의존성)
- **Stage 1 마일스톤:** 렌더링 선택 후 하나의 원형 객체 드로우 + Matter.js 충돌 테스트

### 3. 10단계 콘텐츠 구조
- **형식:** JSON 파일 10개, 각 파일에 구조물·목표·발사체 초기 위치, 어려움 파라미터 (발사체 수, 구조 복잡도)
- **로드:** 메인 메뉴에서 Stage N 선택 시 해당 JSON 로드 → 게임 상태 초기화
- **전환:** 클리어 시 다음 Stage 자동 로드 (또는 메뉴로 돌아가기)
- **난이도 곡선:** Stage 1 (간단, 1 구조물) → Stage 10 (복잡, 3+ 구조물, 발사체 2-3개)

### 4. 슬링샷 입력 및 UX
- **드래그 메커닉:** 마우스/터치 드래그로 새총 각도·백터 조정
- **실시간 피드백:** 드래그 중 예상 궤적을 점선(점점이 궤도)로 표시, 각도·초속도 수치 표시
- **발사:** 마우스 릴리스 시 즉시 발사
- **상태 머신:** 준비(새총 보임) → 조준(드래그) → 발사 중(포물선) → 대기(결과 확인)

### 5. 충돌 판정 및 파괴
- **Matter.js 충돌 감지:** 모든 객체에 collisionGroup 할당 (발사체/구조물/목표)
- **파괴 규칙:**
  - 발사체 + 구조물 = 구조물 HP 감소 (또는 즉시 제거)
  - 발사체 + 목표 = 목표 제거 (파티클 효과, 점수 +100)
  - 발사체 + 바닥 = 정지 또는 제거
- **시각 피드백:** 파괴 시 페이드 아웃(0.5초) + 점수 팝업

### 6. 클리어 조건 및 실패 판정
- **클리어:** 모든 목표 제거 AND 발사체 정지 (3초 이상 속도 = 0)
  - 팝업: "Stage N Clear! Score: XXX" + 다음 진행 버튼
- **실패:** 발사체 소진(스테이지별 할당된 수 사용) AND 목표 남음
  - 팝업: "Failed. Restart?" 또는 자동 제한 시간(90초) 초과
  - 다시하기 / 메인으로 선택지

### 7. 일시정지 오버레이 및 메뉴
- **오른쪽 UI 버튼:** 고정 위치 (오른쪽 상단, 30×30px, "⏸" 아이콘)
- **일시정지 상태:** 물리 시뮬레이션 중단, 렌더링은 계속, 검정 반투명 오버레이 (alpha=0.5)
- **메뉴 선택지:**
  - "계속" (일시정지 해제)
  - "다시하기" (현재 Stage 재시작)
  - "메인으로" (메인 메뉴 복귀)

### 8. 상태 머신 설계
```
Main Menu → Stage Selection
           ↓
        GameLoop (준비 → 조준 → 발사 → 클리어/실패 판정)
           ↓
     ┌─ Clear Popup (Score) → Next Stage / Main Menu
     ├─ Fail Popup (Retry) → Restart / Main Menu
     └─ Pause Overlay → Continue / Restart / Main Menu
           ↓
      Main Menu (또는 다음 Stage)
```
**구현:** 최상위 state enum (MENU, GAME, PAUSE, CLEAR, FAIL), 각 상태의 렌더/입력 핸들러 분리

### 9. 스코어 시스템 (선택사항, 선호)
- **점수:** 목표 제거 시 +100, 보너스 (발사체 남은 수 × 10)
- **저장:** localStorage에 각 Stage 최고 점수 저장, 메인 메뉴에 표시 (선택 사항 — defer 가능)
- **상태:** 메뉴얼 기록 필수, 별 체계(1–3별)는 defer 후속 작업

### 10. 스택 (Stack) 및 아키텍처
- **프론트엔드:**
  - HTML5 Canvas (또는 Pixi.js)
  - Matter.js (물리)
  - TypeScript (타입 안정성)
  - Vite (빌드, 개발 서버)
- **디렉토리:** `/src/game` (루프, 상태), `/src/components` (UI), `/src/physics` (Matter.js 래퍼), `/data/stages` (JSON 10개)
- **상태 관리:** 단순 객체 (Game, Stage, Score) — Redux 불필요

## 접근 및 단계

### Phase 1: 최소 E2E 슬라이스 (1–2주)
**목표:** 하나의 Stage에서 발사 → 충돌 → 클리어 판정까지 모든 루프가 작동

1. **프로젝트 초기화**
   - Vite + Canvas (또는 Pixi.js)
   - Matter.js 설치 및 기초 물리 루프 구성
   - 검증: 원형 객체 1개가 중력으로 낙하

2. **슬링샷 입력 구현**
   - 마우스 드래그 감지
   - 드래그 벡터 → 발사 방향·속도 변환
   - 발사 시 새 발사체 생성
   - 검증: 드래그하면 궤적 표시, 릴리스하면 발사

3. **충돌 판정 및 파괴**
   - Matter.js 충돌 이벤트 구독
   - 목표 + 발사체 충돌 시 목표 제거
   - 검증: 목표 맞히면 사라짐

4. **클리어 판정**
   - 조건: 목표 = 0 AND 발사체 정지
   - 팝업 띄우기
   - 검증: 조건 만족 시 팝업 표시

5. **메뉴 및 상태 머신**
   - 메인 메뉴 (Stage 1 버튼)
   - Game 상태로 전환
   - 검증: 메뉴 → 게임 → 클리어 → 메뉴 사이클 작동

### Phase 2: 일시정지 및 UI 완성 (1주)

6. **일시정지 버튼 및 오버레이**
   - 오른쪽 버튼 UI 배치
   - 클릭 시 물리 시뮬레이션 일시정지
   - 메뉴 선택지 표시 (계속/다시하기/메인)
   - 검증: 일시정지 중 물리 멈춤, 메뉴 작동

7. **실패 판정 추가**
   - 발사체 소진 + 목표 남음 → 실패 팝업
   - 다시하기 / 메인으로 선택
   - 검증: 실패 조건 만족 시 팝업

8. **메뉴 개선**
   - 모든 Stage 목록 (1–10)
   - 클리어 상태 표시 (선택)
   - 검증: 모든 Stage 버튼이 게임 시작

### Phase 3: 콘텐츠 및 밸런싱 (2주)

9. **10단계 데이터 설계**
   - Stage 1–10 각각 JSON 작성 (구조물 배치, 목표 위치, 발사체 수, 어려움)
   - 난이도 곡선 검증 (1 = 쉬움, 10 = 어려움)
   - 검증: 각 Stage 플레이 가능, 클리어 판정 작동

10. **스코어 시스템 (선택)**
    - 목표 제거 시 점수 계산
    - localStorage 저장
    - 메뉴에 최고 점수 표시 (선택)
    - 검증: 점수 계산·저장·표시 작동

### Phase 4: 폴리시 및 테스트 (1주)

11. **시각 폴리시 (파티클, 효과)**
    - 파괴 시 페이드/파티클 (선택, 기본 페이드만)
    - 클리어 시 확대 효과
    - 검증: UI 일관성 및 반응성

12. **E2E 테스트 및 밸런싱**
    - 모든 10단계 플레이 테스트
    - 어려움 조정 (Stage JSON 재작성)
    - 성능 검증 (fps 60 목표, 최소 30)
    - 검증: 10단계 모두 클리어 가능, 부자연스러운 어려움 없음

## 완료 정의 (Definition of Done)

1. **10단계 모두 구현 및 플레이 가능:** 각 Stage JSON이 로드되고, 발사 → 충돌 → 클리어 판정이 모두 작동하는 상태. Stage 1은 1회, Stage 10은 3회 이상 플레이하여 클리어 확인.

2. **물리 시뮬레이션 안정:** 포물선이 예측 가능하고 프레임 드롭 없음. `requestAnimationFrame`에서 초당 최소 30fps 유지 (fps 카운터로 검증).

3. **슬링샷 UI 반응성:** 드래그 시 각도·속도가 실시간 표시되고, 릴리스 시 0.1초 이내에 발사. (Performance.now() 로그로 검증)

4. **일시정지 기능 작동:** 오른쪽 버튼 클릭 시 물리 중단, 메뉴 표시. 메뉴에서 다시하기/메인으로 선택 시 상태 복구.

5. **메뉴 네비게이션:** 메인 메뉴 → Stage 선택 → 게임 → 클리어/실패 → 메뉴 사이클이 모든 Stage에서 무결.

6. **점수 시스템 (선택):** localStorage 저장 + 로드 작동, 메뉴에 표시 (또는 defer). 측정: 점수가 저장되었는지 개발자 도구 검증.

   - 최종: 다이어그램 추가, 각 상태 진입 조건 명시.

2. **10단계 콘텐츠 구조의 모호함 — 해결함 (§10단계 콘텐츠 구조):**
   - "Stage별로 다르게" 정도로 마무리하려 했으나, spec-coverage 요구 사항 "Content axis, not only mechanics axis"가 각 Stage를 "JSON 파일 + 난이도 곡선"으로 구체화하도록 강제했습니다.
   - 최종: JSON 로드 메커니즘, 난이도 1→10 진행 명시.

3. **스코어 시스템 침묵 — 명확히 보류함 (§스코어 시스템):**
   - 점수를 "한 문장으로 끝내거나 아예 빼기" 유혹이 있었습니다 (spec-coverage는 완성도를 요구하므로).
   - 대신 "기본 점수 계산 + localStorage 선택사항"으로 기록하여 **어떤 부분은 Build, 어떤 부분은 Defer인지 명확히** 했습니다.

4. **완료 정의의 검증 불가능성 — 수정함 (§완료 정의):**
   - 초기 정의: "모든 게임이 작동한다" (검증 불가능)
   - 수정: 각 항목마다 "3회 플레이", "fps 카운터 검증", "Performance.now() 로그" 등 측정 가능하도록 조정했습니다.

**약점 영역 (리뷰 시 집중):**
- **§3. 슬링샷 드래그 메커닉:** "실시간 피드백"과 "궤적 프리뷰"가 모두 필수인지, 하나만 최소인지 불명확. 이 둘의 우선순위 기준이 명시되지 않았습니다. (제안: Phase 1 검증 후 하나는 Phase 2로 이동 가능)
- **§난이도 곡선:** "Stage 1 쉬움, Stage 10 어려움" 정도만 기술. 중간 Stage(5, 6)의 구체적 어려움 기준이 없어, Phase 3에서 재작성 비용 높을 수 있습니다.
- **§성능 타겟:** "최소 30fps"는 선언했으나, 10단계 동시 렌더(또는 복잡한 구조물)에서 정말 달성 가능한지 Phase 1에서 초기 측정 필수.
