### 측정 방법과 그 한계 (제4조)

- 모든 셀에 **동일하게** `setPointerCapture`/`hasPointerCapture`를 무력화했다. 합성 PointerEvent는
  브라우저가 모르는 `pointerId`를 쓰므로 캡처 호출이 실패하는데, 이는 **측정 하니스의 아티팩트**이지
  제품 결함이 아니다. 무력화하지 않으면 정상 코드도 FAIL로 보인다.
- 판정 신호의 강도가 셀마다 다르다: sonnet·fable·opus/plan-smith는 **HUD/오버레이 텍스트 변화**라는
  명시 신호를 얻었고, 베이스라인은 **픽셀 변화만** 얻었다. 그래서 베이스라인은 FAIL이 아니라 **판정 불가**로 적는다.
- **첫 측정에서 sonnet을 FAIL로 오판했다.** 슬링샷 앵커를 추정 좌표로 찍었기 때문이고, 소스에서
  실제 앵커 `(140,440)`를 읽어 다시 하니 즉시 클리어됐다. 자동 측정은 좌표 하나에 취약하다 —
  **0이 나오면 제품을 의심하기 전에 계측을 의심해야 한다.**
- 게임의 재미·난이도·물리 품질·10스테이지 전체 동작은 **측정하지 않았다.** 하중 경로 1개만 구동했다.

## 루브릭이 미리 정한 판정 규칙의 적용

> "1차 FAIL + 항목 1·2 통과 → 조항이 발화했는데도 실패한 것이므로 처방이 틀렸다. v1.3으로 조항을
> 더 붙이지 말고 접근을 재설계한다."

**이 조건은 발동하지 않았다** — 1차 지표가 PASS 3건 / 판정 불가 1건 / N/A 1건이고 FAIL은 0건이다.
반대로 "1차 PASS + 2차 실패 항목 존재"에 해당하므로, 항목 5(구현자 계약)는
**불필요했거나 문안이 틀렸다는 근거**가 된다.
