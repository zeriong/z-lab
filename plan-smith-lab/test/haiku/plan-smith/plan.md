# 웹 앵그리버드 게임 구현 플랜

- Reasoning frame: backward / Style: opus
- 게임 완료 기준을 먼저 정하고, 각 기준을 만족시키는 기술·데이터 구조·상태 머신을 역추적하여 10단계 웹 기반 물리 슬링샷 게임 설계

---

## 게임 완료 기준 (Acceptance Criteria)

아래 5개 기준 중 어느 하나라도 실패하면 게임이 미완성이다. 이 기준들이 기술 스택과 아키텍처의 모든 선택을 지배한다.

### AC1: 10개 스테이지 모두 플레이 및 클리어 가능
- **재설정값(anchor)**: 모든 스테이지가 물리 엔진으로 작동해야 하고, 각 스테이지마다 명확한 클리어 조건(모든 적 제거)이 있어야 한다.
- **배제하는 대안**:
  - ❌ 시뮬레이션만 돌고 점수 계산이 안 되는 미완성 물리
  - ❌ 일부 스테이지만 구현한 부분 게임
  - ❌ 10개 스테이지 로드/전환이 없는 구조

### AC2: 결정론적 물리 시뮬레이션 + 궤적 예측 표시
- **재설정값(anchor)**: 같은 슬링샷 상태(각도, 힘)로 발사하면 **항상 같은 경로**를 따라야 한다. 궤적 예측선이 플레이어에게 보여야 한다.
- **배제하는 대안**:
  - ❌ 부동점 오차로 인한 비결정적 물리
  - ❌ 궤적 예측 없이 "감으로" 발사하는 UX
  - ❌ 기계학습/랜덤 노이즈 포함 물리

### AC3: 일시정지 상태 정확 복원 + 메뉴 전환
- **재설정값(anchor)**: 일시정지 중일 때 게임 상태(모든 물체 위치/속도/충돌 상태)가 메모리에 정확히 보존되어야 하고, "다시하기"와 "메인으로"를 클릭했을 때 상태가 올바르게 전환된다.
- **배제하는 대안**:
  - ❌ 렌더링만 멈추고 시뮬레이션이 계속 도는 구조
  - ❌ 상태 복원 오차 있는 구현

### AC4: 프레임 레이트 안정성 (60fps 이상 목표)
- **재설정값(anchor)**: 물리 계산과 렌더링이 분리되어야 하며, fixed timestep으로 물리를 진행하고 렌더링 프레임과 비동기화되어야 한다.
- **배제하는 대안**:
  - ❌ 렌더링 FPS에 맞춰 물리를 계산하는 구조 (프레임 드롭 시 물리 오류 발생)
  - ❌ 복잡한 충돌 계산이 메인 스레드를 블로킹

### AC5: 검증자가 외부 질문 없이 완료 판정 가능
- **재설정값(anchor)**: 게임 플레이 흐름이 명확해야 하고, 각 기능(발사, 일시정지, 메뉴 전환, 스테이지 진행)이 실패하면 명확한 오류가 표시되거나 게임이 멈춰야 한다.
- **배제하는 대안**:
  - ❌ "아마 작동할 것 같은" 추측형 검증
  - ❌ 숨겨진 상태 오류로 예기치 않은 동작

## 문제 정의 및 목표

웹 브라우저에서 실행 가능한 앵그리버드 게임을 설계한다. 플레이어는 새총(슬링샷)으로 발사체를 쏘아 구조물을 파괴하고 적(돼지 등)을 제거하여 스테이지를 클리어한다. 10개의 난이도 증가 스테이지를 순서대로 클리어할 수 있어야 하며, 언제든 일시정지하고 게임을 다시하거나 메인으로 돌아갈 수 있어야 한다.

---

## 명시적 가정

- **기술 스택**: 
  - 렌더링: Canvas 2D (WebGL은 고려하지 않음; AC4의 60fps는 2D Canvas로 충분)
  - 물리 엔진: Matter.js v2.0.20+ (AC2의 결정론적 시뮬레이션 보장, 이미 검증된 라이브러리)
  - 기본 번들러: 없음; 바닐라 JavaScript + ES6 모듈
  - **만약 틀렸을 경우**: 물리 엔진 구현이 AC2를 만족하지 못하면 Matter.js로 전환 필요. Canvas 성능 부족 시 Three.js + WebGL 검토.

- **10개 스테이지 구조**:
  - 스테이지 1~3: 기초 메커니즘 (단순 구조물, 1~2개 발사체)
  - 스테이지 4~7: 중급 (복합 구조물, 특수 물체 - 얼음/나무)
  - 스테이지 8~10: 고급 (고정확도 필요, 보너스 요소)
  - **만약 틀렸을 경우**: 스테이지별 플레이 시간이 예상보다 길면 이후 스테이지는 일시적으로 튜토리얼 스테이지로 축약.

- **발사체 메커니즘**: 공 모양 물체 1개가 기본. 스테이지별로 다른 발사체 유형(계란, 폭발물 등)은 도입하지 않음 (복잡도 상한선).

- **플레이어 검증자의 브라우저**는 최신 Chrome/Firefox/Safari (Canvas, AudioContext 지원).

## 접근 & 단계

각 단계는 의존성 순서로 나열한다. 시간 순서가 아니라, 어느 단계의 산출물을 다음 단계가 소비하는지에 따라 정렬.

### Phase 0: 스테이지 데이터 구조 정의 (독립 병렬 가능)

**출력**: `stages.json` 스키마 정의
```javascript
{
  stages: [
    {
      id: 1,
      bodies: [ // 고정된 구조물 및 적
        { type: "wood_block", x: 300, y: 400, width: 50, height: 10, rotation: 0 },
        { type: "pig", x: 350, y: 420, radius: 20 }
      ],
      slingshot: { x: 100, y: 500 }, // 새총 위치
      camera: { x: 0, y: 0, zoom: 1 },
      maxTime: 120 // 스테이지 제한 시간 (초)
    },
    // ... stages 2~10
  ]
}
```

**검증**: JSON 파일이 로드 가능하고, 모든 스테이지의 좌표·물체 수가 기대치(AC1) 내.

---

### Phase 1: Matter.js 초기화 + Fixed Timestep 루프 구현 (Phase 0 완료 후)

**소비**: Phase 0의 스테이지 스키마
**출력**: `physics.js` — Matter.js 엔진 초기화, fixed 60Hz timestep 루프, 게임 월드 상태 관리

**핵심**:
- Matter.Engine을 고정 timestep(1/60초)으로 진행 (AC2의 결정론적 시뮬레이션)
- 렌더링 타이밍과 분리: requestAnimationFrame은 렌더링만 담당, 물리는 독립적으로 진행
- 모든 충돌 이벤트를 중앙 이벤트 버스로 수집

**검증**: 
- 같은 시작 상태에서 2회 실행 시 동일한 궤적 재현 (재현성 테스트)
- 60Hz 타이밍 동안 물리 계산이 frame drop 없이 진행 (성능 로그)

---

### Phase 2: Canvas 렌더링 엔진 (Phase 1 완료 후)

**소비**: Phase 1의 물리 상태 + Phase 0의 스테이지 데이터
**출력**: `renderer.js` — Canvas 2D 렌더링, 카메라, 스프라이트 매핑

**핵심**:
- Canvas를 게임 월드 좌표계에서 화면 좌표계로 변환
- 물리 엔진의 body 객체들(원, 사각형)을 시각화
- 궤적 예측선을 렌더링 (AC2): 드래그 중에 발사체 예상 경로를 선 또는 점 궤적으로 표시

**검증**: 
- 렌더링된 물체가 물리 위치와 정확히 일치 (위치 오차 < 1 픽셀)
- 궤적 예측선이 실제 비행 경로와 일치 (10초 이내 5% 오차 이내)

---

### Phase 3: 슬링샷 입력 & 발사 메커니즘 (Phase 1, 2 완료 후)

**소비**: Phase 1의 물리 엔진 + Phase 2의 렌더링
**출력**: `slingshot.js` — 드래그 입력 처리, 궤적 계산, 발사

**핵심**:
- 마우스 `mousedown` 시 슬링샷 잠금, `mousemove`로 각도/힘 조정
- 궤적 예측: 드래그 중 발사 시뮬레이션을 한 번 더 돌려 경로 미리 표시
- 마우스 `mouseup` 시 발사체 생성 및 물리 적용
- 발사 후 일정 시간(예: 3초)까지만 다음 발사 가능 (한 턴 = 1발사)

**검증**: 드래그 시작~끝까지 궤적 예측이 부드럽게 업데이트, 발사 후 발사체가 예측선을 따라 이동.

---

### Phase 4: 충돌 & 파괴 판정 (Phase 1 완료 후, Phase 3과 병렬 가능)

**소비**: Phase 1의 충돌 이벤트
**출력**: `collision.js` — 충돌 감지, 적 제거, 구조물 파괴 규칙

**핵심**:
- Matter.js 이벤트 버스에서 충돌 감지: `collisionStart`
- 적(pig)이 발사체 또는 높은 충돌력으로 맞으면 제거 (임계값: 충돌력 > 10N)
- 구조물(wood, stone)도 충돌력에 따라 손상도 증가, 임계값 초과 시 제거
- **스테이지 클리어 조건**: 모든 적이 제거 && 안전한 상태 (움직이는 물체 없음) 유지 2초 이상

**검증**: 발사체 충돌 후 적이 제거되고, 남은 적 수가 0이 되면 클리어 화면 표시.

---

### Phase 5: 상태 머신 & 게임 흐름 (Phase 1, 4 완료 후)

**소비**: Phase 1의 물리 상태, Phase 4의 클리어 판정
**출력**: `game-state.js` — 상태 머신 (대기 → 인게임 → 일시정지 → 클리어/재시작/메인)

**상태 다이어그램**:
```
대기 --[시작]--> 인게임 --[일시정지 누름]--> 일시정지
                    ↑                         ↓
                    |<-- [다시하기] ---------|
  
인게임/일시정지 --[클리어]--> 클리어 화면 --[다음]--> 다음 스테이지(인게임)
                                  |
                                  |--[메인]--> 메인 화면

모든 상태 --[메인]--> 메인 화면
```

**핵심**:
- 각 상태 진입 시 필요한 리소스 할당/해제 (AC3의 상태 복원)
- 일시정지 상태: 물리 엔진 `pause()`, 렌더링은 계속, 입력 비활성화
- 메인 화면: 10개 스테이지 목록 표시, 클리어한 스테이지는 표시

**검증**: 일시정지 중 게임 상태(모든 물체 위치)가 정확히 고정되고, "다시하기" 클릭 시 동일한 스테이지 초기 상태로 복원.

---

### Phase 6: UI & 일시정지 오버레이 (Phase 5 완료 후)

**소비**: Phase 5의 상태 머신
**출력**: `ui.js` — HTML 버튼 및 오버레이

**핵심**:
- 게임 화면 우측에 **일시정지 버튼** 고정 (AC3의 요구사항)
- 일시정지 오버레이: "다시하기", "메인으로" 두 버튼 (반투명 배경 위)
- 클리어 화면: "다음 스테이지", "메인으로" 버튼
- 메인 화면: 스테이지 선택 버튼 또는 "시작" 버튼

**검증**: 버튼 클릭이 상태 머신을 올바르게 전환, 모든 경로(일시정지→다시하기→인게임, 일시정지→메인→메인화면) 동작.

---

### Phase 7: 스테이지 로드 & 전환 (모든 Phase 완료 후)

**소비**: Phase 0~6의 모든 산출물
**출력**: `stage-loader.js` — JSON 로드, 현재 스테이지 상태 관리, 스테이지 전환

**핵심**:
- 게임 시작 시 `stages.json` 로드
- 각 스테이지 진입: 이전 상태 정리, 새 스테이지 월드 초기화 (물리 엔진 리셋, 렌더링 카메라 리셋)
- 스테이지 완료 시 다음 스테이지로 자동 전환 (또는 "다음" 버튼 대기)

**검증**: 스테이지 1에서 2로 전환 시 이전 발사체나 물체가 남아있지 않음, 새 스테이지 데이터가 올바르게 로드.

---

### Phase 8: 통합 테스트 & 성능 최적화 (모든 Phase 완료 후)

**출력**: 테스트 케이스 목록, 성능 리포트

**검증 항목**:
- E2E: 메인 → 스테이지 1 시작 → 발사 → 발사 후 클리어 → 다음 스테이지 → ... → 스테이지 10 클리어
- 일시정지 흐름: 게임 중 일시정지 → 다시하기 → 같은 상태로 복원 확인
- 성능: 60 FPS 유지, 메모리 누수 없음 (크롬 DevTools 확인)

## 대안 & 기각 근거

| 대안 | 근거 | 부활 조건 |
|------|------|----------|
| **Canvas 대신 WebGL** | AC4의 60fps는 2D Canvas로 충분; WebGL은 초기 복잡도 증가 | 스테이지 20개 이상 확장 시 |
| **Phaser.js 게임 프레임워크** | 기본 물리는 충분하나, AC2의 결정론적 시뮬레이션 제어 어려움 | 팀이 게임 로직에만 집중할 시간 있을 때 |
| **Babylon.js 3D** | 3D는 요구하지 않음; 오버킬 | 3D 그래픽 요구사항 추가 시 |
| **발사체 다양화** (계란, 폭발물, 독성) | AC1의 10 스테이지 달성이 우선; 복잡도 증가 상한선 | 스테이지 10 클리어 후 추가 콘텐츠 단계 |
| **온라인 멀티플레이** | 시간 제약; 로컬 플레이만 구현 | 베타 검증 후 별도 단계 |

## 위험 & 완화

| 위험 | 확률 × 영향 | 완화 방안 |
|-----|-----------|---------|
| Matter.js 결정론적 시뮬레이션 보장 실패 | 중 × 높음 | Phase 1 검증에서 재현성 테스트 2회 반복; 실패 시 물리 엔진 재설계 |
| Canvas 성능 저하 (프레임 드롭) | 중 × 중간 | Phase 2에서 렌더링 최적화 (배치 처리, 더티 플래그); 필요 시 OffscreenCanvas 도입 |
| 슬링샷 궤적 예측 오차 커짐 | 낮음 × 높음 | Phase 3에서 여러 타이밍 스탭 사용, 오차 < 5% 보증; 게임플레이 느낌 검증 (playtest) |
| 스테이지 10개를 마감까지 구현 못함 | 중간 × 높음 | 스테이지 구조를 데이터 驱動으로 설계 (JSON 기반); 초기 3개만 로직 완성, 나머지는 JSON 추가 |
| 일시정지 상태 복원 오류 | 낮음 × 높음 | Phase 5에서 상태 스냅샷 명시적 저장; 매 전환마다 검증 (unit test) |

## Frame deviations & habit regressions

1. **Timeline regression 위험**: "Phase 0~8"이 숫자로 보이지만, 실제로는 **의존성 순서**이다. Phase 0과 1은 병렬 가능, Phase 3과 4도 병렬 가능. 달력 순서로 읽으면 안 됨. → 섹션 제목에 "(독립 병렬 가능)", "(Phase X 완료 후)"를 명시하여 명확히 했다.

2. **Anchor intersection pass의 약함**: AC1(10 스테이지)과 AC2(결정론적 물리)의 충돌은 없지만, AC2(결정론적 물리)와 AC4(60fps)는 **고정 timestep 사용**이라는 공통 해결책으로 상호지원한다. AC3(상태 복원)도 이 timestep 아키텍처 덕분에 간단해진다. → 이 로직이 Phase 1에서 명시됨.

3. **측정 불가 범주**: "앵그리버드다운 손맛" 은 AC에 없다. 이는 playtest 체크리스트로 별도 관리 (planner의 책임 아님).

4. **숫자 태깅**:
   - 60fps: **(b) lifetime-capped** — 첫 렌더링 성능 측정 후 확정 (Phase 2 검증)
   - fixed 1/60초 timestep: **(a) derived** — Matter.js 기본 권장 + 게임플레이 안정성 (Phaser, Babylon 등 모든 엔진의 관례)
   - 충돌력 임계값 10N: **(c) declared arbitrary** — 초기값; 스테이지별 스탠드 이후 조정

5. **강한 가정**: 
   - Matter.js + Canvas 결정 (✓ 명시)
   - 바닐라 JS (✓ 명시, fallback: 번들러 도입)
   - 브라우저 지원 (✓ 명시)

6. **대안 기각 이유가 아키텍처를 배제했는가**: 
   - Phaser.js 기각 → Matter.js 결정론적 제어 강화로 의사결정 명확 (✓)
   - 발사체 다양화 기각 → 스테이지 10 달성 우선순위 명확 (✓)
   - 온라인 멀티 기각 → 로컬 플레이 단순화 (✓)

## 완료 정의

게임이 "완료"되었다고 판정하는 기준 (검증자가 외부 질문 없이 확인 가능):

1. **스테이지 진행 E2E**: 메인 화면 → 스테이지 1 시작 → 발사 1회 → 적 제거 → 클리어 → 스테이지 2 자동 로드 → ... → 스테이지 10 클리어 **완료**. (일시정지 없이 연속 진행)

2. **일시정지 흐름**: 스테이지 중반에 일시정지 버튼 클릭 → 오버레이 표시, 게임 멈춤, 물체 위치 고정 → "다시하기" 클릭 → 동일 상태로 복원, 다시 발사 가능 → 클리어 (발사 전 상태와 동일).

3. **메인으로 전환**: 스테이지 진행 중 일시정지 → "메인으로" 클릭 → 메인 화면 표시, 스테이지 1 선택 가능 (이전 진행 상태 손실 없음, 다시 선택하면 처음부터).

4. **렌더링 정확성**: 궤적 예측선이 드래그 중 부드럽게 업데이트, 발사 후 발사체가 예측선 궤적을 따라 이동 (육안 검증, 오차 < 1 화면 칸).

5. **성능**: 위 1~4를 수행하는 동안 Chrome DevTools에서 60 FPS 이상, 메모리 누수 없음 (힙 크기 200MB 이상 스파이크 없음).

**완료 불판정 예**:
- ❌ 스테이지 5 이상이 JSON에 없거나 로드 실패
- ❌ 일시정지 후 복원 시 발사체 위치 오차 > 5 픽셀
- ❌ 궤적 예측선이 정지 또는 끊김
- ❌ 메인으로 갔다가 다시 스테이지 1 진입 시 이전 상태 데이터 남음 (예: 발사체 유령 표시)
- ❌ 프레임 드롭으로 발사 궤적이 실제와 다름

## Confessionlog 추가 검토

Phase 8의 통합 테스트 체크리스트가 구체적인 행동 항목이 아니라 다소 추상적 (예: "성능 리포트")인 부분이 있다. 이를 수정하려면 각 Phase의 검증 항목이 더 구체적이고 자동화 가능해야 한다. 예를 들어, Phase 2 검증에서 "궤적 예측 오차 < 5%"를 측정하는 구체적인 알고리즘(예: RMS 거리 계산)을 기술해야 하나, 이는 설계 플랜을 넘어 구현 세부사항이다. 따라서 현재 플랜의 검증은 "코드 리뷰 후 e2e 테스트로 최종 판정"이라는 합의를 전제한다.

또한, 스테이지 10개의 데이터를 "스테이지 로더"에서 로드한다고 했으나, 실제로는 각 스테이지를 누가, 언제 설계하는지 명시되지 않았다. 이는 "플랜 문서 범위" 바깥이지만, 만약 시간 제약이 생기면 초기 3개만 완전 구현하고 나머지는 JSON 스텁으로 두는 것이 현실적이다 (위험 섹션에 이미 반영함).

Backward 프레임을 정직하게 적용했으나, "AC1의 10 스테이지" 그 자체가 해결해야 할 근본적인 아키텍처 선택은 아니고, 오히려 스테이지 데이터 구조(Phase 0)와 로드 메커니즘(Phase 7)의 선택만을 강제한다. 더 강력한 anchor는 AC2(결정론적 물리)와 AC4(60fps)이다. 이들이 고정 timestep + 렌더링 분리를 강제하므로, 이 두 조건이 사실상 아키텍처의 "지붕"이다.
