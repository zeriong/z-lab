# transfer 계열 — 비대칭 전이 실험 (입력·판정 기준, 실행 전 고정)

## 가설 — 이 실험이 존재하는 이유

플랜 문서는 **정보 채널**이다: 가치 = (계획자·구현자 간 능력 격차) × (구현자가 소화할 수 있는 정도).

지금까지 4개 실험(R1~R3, pure-model)은 전부 **같은 모델이 자기 플랜을 자기가 구현**했다.
그 구조에서 강한 모델은 플랜이 잉여이고(격차 0), 약한 모델은 자기 수준의 판단만 담긴 플랜을 받는다.
pure-model의 결과 — arm이 아니라 모델이 성패를 가른다 — 는 이 구조의 필연이다.

**플랜이 실무에서 존재하는 이유는 능력 격차를 건너 판단을 전달하는 것**이다(시니어가 설계하고
주니어가 구현한다 / 비싼 모델이 한 번 계획하고 싼 모델이 구현한다). 이 셀은 한 번도 테스트된 적이 없다.

| 가설 | 내용 | 판정 시 처방 |
|---|---|---|
| **H1** | opus-smith 플랜을 받은 haiku가 opus-baseline 플랜을 받은 haiku보다 높은 사다리 레벨에 도달 | 스킬에 전이 가치 있음 → v1.3은 구현자 인지 라우팅 |
| **H0a** | 두 opus arm이 비슷하고 둘 다 haiku-self보다 높음 | 강한 계획자의 공로이지 스킬의 공로 아님 |
| **H0b** | 세 arm 전부 비슷 | 약한 구현자의 병목은 지식이 아니라 실행 용량 → 스킬 가치를 분산 축소·의도 교정으로 재정의 |

## 설계

- **구현자 고정: `claude-haiku-4-5`** (pure-model에서 두 arm 모두 FAIL한 최약 모델 — 끌어올릴 대상)
- **에이전트: `bare-model`** (역할 0, 도구 `Read`/`Write`만). advisor는 세션 수준에서 비활성
  (같은 세션의 pure-model 재실행 16에이전트에서 0회 실증 — 실행 후 재검증한다)
- **구현 입력: 플랜 단독.** 원 요구사항(`game-prompt.md`)을 주지 않는다 — 플랜이 유일한 채널이어야
  전이력이 측정된다
- **반복 n=3** — 처음으로 실행 변동과 처치를 분리한다. 단 n=3은 방향 신호이지 통계적 유의가 아니다

## arm — 동결된 플랜 3종 (pure-model 무오염 표본에서 복사, 수정 금지)

| arm | 원본 | 단어 | md5(8) |
|---|---|---|---|
| `haiku-self` | pure-model/haiku-4.5/plan/plan.md (haiku 자기 플랜) | 1,720 | 65ee749e |
| `opus-baseline` | pure-model/opus-5/plan/plan.md (opus, 방법론 없음) | 3,537 | 4572e8fb |
| `opus-smith` | pure-model/opus-5/plan-smith/plan.md (opus, plan-smith v1.2.0) | 6,512 | f6a4c8f6 |

**고지 — 이 플랜들은 약한 구현자를 위해 쓰인 것이 아니다.** 셋 다 작성자가 자기가 구현할 것을
전제로 썼다. 그게 이 실험의 조건이다: **현재의 plan-smith 산출물이 그대로** 약한 구현자에게
더 잘 전이되는가를 묻는다. (구현자 인지형 플랜은 이 실험의 결과가 양성일 때의 다음 단계다.)

## 판정 — 사다리 (실행 전 고정, 오케스트레이터가 사후 측정)

이진 판정(발사 여부)은 R2에서 육안 품질 격차를 못 잡았다. 단계별 사다리로 잰다.
각 셀의 점수는 **연속으로 통과한 최고 레벨**이다(L6은 소스 기반이라 별도 보고).

| 레벨 | 기준 | 측정 방법 |
|---|---|---|
| L0 | 설치·빌드 성공 (빌드 불요 구조면 자동 통과) | `npm install` + 셀이 정의한 빌드 |
| L1 | 부팅 — 페이지 로드, 치명 콘솔 에러 없음 | HTTP + 콘솔 |
| L2 | 월드 렌더 — 스테이지 진입 후 캔버스에 게임 장면이 그려짐(메뉴만 있으면 실패) | 스크린샷 |
| L3 | 발사 — 드래그·놓기가 상태를 바꿈 (연속 다프레임 움직임 또는 HUD 변화) | 합성 입력 + 대조 구간 |
| L4 | 턴 진행 — 첫 발사 후 다음 발사체가 장전됨 | 반복 구동 |
| L5 | 종결 도달 — 클리어 또는 실패 오버레이가 실제로 뜸 | 발사체 소진까지 구동 |
| L6 | 콘텐츠 — 10스테이지가 소스에 실재(로더만 있으면 실패) | 소스 검사 |

**계측 규율** (내가 이미 3번 틀린 지점): 리스너 종류(`mousedown` vs `pointerdown`)와 슬링샷 좌표는
**추정하지 않고 소스·스크린샷에서 읽는다.** `setPointerCapture`는 전 셀 동일하게 무력화한다.
0이 나오면 제품보다 계측을 먼저 의심한다.

**arm 비교는 레벨 중앙값 + 분산(r1~r3 흩어짐)**으로 한다. 분산 자체가 지표다 — 플랜의 효과가
평균이 아니라 예측 가능성에 있을 수 있다.

## 측정하지 않는 것

- 게임의 재미·시각 품질·물리 밸런스. 사다리는 기능 골격만 잰다.
- 강한 구현자에서의 전이(격차 0이라 이 설계로는 의미 없음).
- **Stage 1 의도 교정 게이트** — 배치 실행이라 여전히 제거된 상태다. 이 실험도 그 절반은 못 잰다.
- n=3의 한계: 방향만 말할 수 있고 유의성은 주장하지 않는다.
