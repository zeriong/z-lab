# model-bump / pure-model — 발견

## 관측된 것

### P1. 성패 판정은 세대가 바뀌어도 같다 — 4/4 PASS

원 opus-5 · fable-5 네 셀이 전부 발사 PASS였고, Opus 5.5 · Fable 5.1 네 셀도 전부 PASS다(이번엔 네 셀 모두 L5까지).
**이 계열의 1차 지표로는 세대 차이가 보이지 않는다** — 원래 강한 모델은 이 과제를 스킬 없이도 통과했다(원 pure-model 결론).
그래서 이 계열이 새로 말해 주는 것은 성패가 아니라 **산출물의 규모와 형태**다.

### P2. 새 세대는 방법론 없이도 두 배 긴 계획을 쓰고, 더 큰 프로젝트를 짓는다

| 모델 | baseline 플랜 단어 | baseline 구현 파일 |
|---|---|---|
| opus 5 → 5.5 | 3,537 → 7,356 (**+108%**) | 49 → 82 |
| fable 5 → 5.1 | 2,341 → 4,954 (**+112%**) | 10 → 65 |

- 가장 큰 변화는 **fable baseline**이다: 원 fable-5는 빌드 없는 바닐라 JS 10파일이었는데, fable-5.1은 방법론 없이
  TS + Vite 65파일(+550%)을 골랐다. **"작게 짓는 모델"이라는 원 계열의 fable 인상은 5.1에서 사라졌다.**
- 반면 **plan-smith arm의 플랜 길이는 거의 그대로**다(opus +20%, fable −3%). 결과적으로 새 세대에서는
  baseline과 plan-smith의 플랜 길이 격차가 줄었다(opus 3,537 : 6,512 → 7,356 : 7,832 · fable 2,341 : 3,387 → 4,954 : 3,296 — **fable은 역전**).
  → 원 계열의 "plan-smith는 플랜을 길게 만든다"는 관측은 새 세대에서 성립하지 않는다. 모델 자체가 길게 쓰기 시작했다.

### P3. opus-5.5 baseline은 요구사항이 예로 든 엔진을 명시적으로 기각했다

opus-5.5/plan은 요구사항이 예시로 든 Matter.js 대신 Planck.js(Box2D 계열)를 골랐고 그 이유(스택 안정성, CCD, 접촉 충격량)를
플랜에 적었다. 나머지 세 셀은 matter-js 0.20.0. 원 계열 4셀(opus-5 · fable-5)은 모두 matter-js였다(원 표본의 `package.json`/CDN 줄로 확인).
요구사항은 엔진을 지정하지 않고 "직접 구현 vs 라이브러리(Matter.js 등)?"라는 열린 질문으로만 제시한다.
단일 표본(n=1)이며, 선택의 옳고 그름은 측정하지 않았다 — 결과는 둘 다 PASS.

### P4. 셀 정의 빌드(tsc 포함)를 통과한 것은 plan-smith 두 셀뿐이다 — 단, n=2

| | opus-5.5 | fable-5.1 |
|---|---|---|
| plan | tsc 오류 1 (`TS6138` 미사용 속성) | tsc 오류 1 (`TS2345` 리터럴 유니온 불일치) |
| plan-smith | 0 | 0 |

셀이 **스스로 정의한** `build`/`typecheck`가 plan arm에서는 오류 1건씩으로 실패한다. 둘 다 동작에는 무해(vite 단독 빌드 후 PASS)하지만,
사용자가 README대로 `npm run build`를 치면 멈춘다. arm당 2셀이라 처치 효과로 주장하지 않는다 — **다음 실험의 가설 후보**로 둔다
(v1.2.0 스킬 문서의 "완료 판정은 명령 종료 코드로" 계열 조항이 플랜에 tsc 통과를 명시하게 만들었는지는 플랜 원문 대조가 필요하다).

### P5. plan-smith arm의 구현 비용이 더 낮았다 — 특히 fable (n=1, 약한 신호)

| 모델 | 합 (plan → plan-smith) | 비 |
|---|---|---|
| opus-5.5 | 11,222,076 → 8,562,136 | 0.763 |
| fable-5.1 | 9,130,112 → 2,117,315 | **0.232** |

fable-5.1/plan의 구현 토큰(9.05M)은 65파일을 쓰며 긴 대화로 누적된 cache_read가 대부분이다. 셀당 n=1이라 실행 간 분산과
구분할 수 없고, tco 2a(같은 fable-5.1 구현자, 고정 플랜)에서는 반대로 plan-smith 플랜이 output을 더 쓰게 했다 — **두 관측은 조건이 달라 상충이 아니지만, 어느 쪽도 일반화하지 않는다.**
