# 웹 브라우저 앵그리버드 스타일 슬링샷 게임 — 구현 플랜
- Reasoning frame: spec-coverage / Style: opus
- 10개 스테이지, Matter.js 기반 물리 슬링샷 코어 루프, 우측 일시정지→다시하기/메인으로 오버레이까지 요구사항 3항목을 표면 매트릭스로 빠짐없이 판정하고, 발사→충돌→클리어로 이어지는 로드베어링 경로를 5홉 체인으로 배선한다.

### 표면별 완성도 기준(quality floor)
- **메인 메뉴**: 클릭 한 번으로 최근 미해금 스테이지부터 시작할 수 있고, 해금된 모든 스테이지를 개별 선택할 수 있다.
- **인게임 HUD**: 잔여 발사체 수가 항상 보이고, 그 값이 0이 되는 프레임과 실패 판정이 발생하는 프레임 사이에 지연이 없다.
- **궤적 예측**: 드래그 중 실시간 갱신되는 곡선이 실제 발사 궤적과 동일한 물리식을 사용해 오차 없이 일치한다.
- **파괴 피드백**: 구조물이 파괴되면 같은 프레임 내에 해당 body가 화면에서 사라져 "부서졌다"는 상태가 시각적으로 모호하지 않다.
- **일시정지 오버레이**: 클릭 즉시 물리 시뮬레이션이 정지하고, 오버레이 뒤 월드는 전혀 움직이지 않는다.
- **클리어/실패 화면**: 클리어 시 다음 스테이지 해금 여부가 화면에 명시되고, 실패 시 재도전 버튼은 즉시 현재 스테이지를 재로드한다.

### 콘텐츠 축(10 스테이지 난이도 커브)
- 1-2: 튜토리얼 — 목재(wood)만, 돼지 1-2마리, 발사체는 필요 수보다 여유 있게 지급
- 3-5: 재질 확장 — 석재(stone)·유리(glass) 도입, 재질별 파괴 임계값 상이
- 6-8: 복합 구조 — 다중 재질 결합 구조물 + 경사/틈이 있는 지형
- 9-10: 최고난도 — 위 요소를 모두 결합하고 발사체 여유분을 최소화

## 문제 정의 / 목표
`test/game-prompt.md`의 3개 하드 요구사항(10스테이지, 앵그리버드류 물리 슬링샷 게임플레이, 우측 일시정지→다시하기/메인으로)을 모두 충족하는 웹 브라우저 게임을 만들 수 있는 구현 플랜을 제공한다. 완료 판정은 위 매트릭스의 모든 `build` 행이 구현되고, 아래 로드베어링 경로 5홉이 실제로 연결되는 것이다.

## 명시적 가정
- **[로드베어링]** 일시정지 오버레이에는 정확히 "다시하기"/"메인으로" 두 버튼만 존재하고, 별도의 "이어하기(재개)" 버튼은 두지 않는다(스펙 3항을 문자 그대로 해석). **틀렸을 때 영향**: 사용자가 실제로는 재개 기능도 원했다면, 일시정지 중 게임은 반드시 재시작하거나 메뉴로 나가야만 하는 의도치 않은 제약이 된다. **조기 검증**: 첫 플레이테스트에서 사용자가 오버레이에서 재개를 시도하는지 관찰. **폴백**: 상태머신에 `RESUME` 전이 1개 + 버튼 1개 추가(저비용).
- 스테이지는 순차 해금이며 자유 선택이 아니다(이전 스테이지를 클리어해야 다음이 열린다). **틀렸을 때 영향**: 자유 선택이 맞다면 메인 메뉴의 잠금 로직만 제거하면 되는 저비용 변경.
- 발사체는 스테이지당 유한 개수이며 소진 시 실패 판정이 발생한다(장르 관례, 스펙에 명시 없음). **틀렸을 때 영향**: 무제한이라면 "실패" 상태가 사라지고 클리어만 남는 더 단순한 게임이 되며, 클리어 판정 로직은 그대로 재사용하고 실패 판정 로직만 제거하면 된다.
- **[로드베어링]** 물리 엔진으로 Matter.js를 채택한다(자체 구현 대비). **틀렸을 때 영향**: Matter.js가 요구되는 파괴 표현력을 못 준다면, 이미 엔진 API(충돌 이벤트, body 조작)에 결합된 게임 로직의 교체 비용이 크다. **조기 검증**: 스텝 0 직후 블록 3개 쌓기 + 발사체 1개 충돌 스파이크로 API 적합성 확인. **폴백**: Planck.js 등으로 교체, 게임 로직을 엔진 어댑터 인터페이스 뒤에 둔다(스텝 1에서 설계).

## 접근 & 단계
> 의존성 순서로 배열. 각 단계는 전제조건(어느 단계의 산출물을 소비하는지, 또는 "독립/병렬"), 검증 방법, 기여하는 요구사항을 명시한다. 스텝 0-10은 로드베어링 경로가 실제로 닫히는 얇은 엔드투엔드 슬라이스이며, 스텝 11에서 콘텐츠 폭을 확장한다(spec-coverage의 "얇은 슬라이스 먼저, 그다음 폭" 원칙).

1. **스텝 0 — 스택 확정 및 프로젝트 스캐폴딩**. 전제: 독립. 검증: `npm run dev`가 빈 캔버스를 기동. 기여: 전체 매트릭스의 전제조건. 스택은 TypeScript + Vite + Matter.js(아래 구현자 계약 참조) — TypeScript를 택하는 이유는 스테이지 스키마(스텝 2)와 상태머신(스텝 1)의 형태를 컴파일 타임에 강제하기 위함이다.
2. **스텝 1 — 물리 월드 + 상태머신 골격**(MainMenu / Loading / Playing / Paused / Cleared / Failed). 전제: 스텝 0. 검증: 각 상태 진입/이탈 콜백에 대한 단위 테스트. 기여: 매트릭스 14-16, 로드베어링 경로 hop1·hop3의 기반. Matter.js 엔진 접근은 어댑터 모듈 뒤에 둔다(가정 4의 폴백 대비).
3. **스텝 2 — 스테이지 데이터 스키마 + 10개 스테이지 콘텐츠 저작**. 전제: 스텝 0. 검증: `tsc --noEmit` 통과 + 10개 데이터 파일 런타임 파싱 에러 0건. 기여: 매트릭스 2, 19.
4. **스텝 3 — 새총 드래그 입력 + 궤적 예측 렌더**. 전제: 스텝 1(Playing 상태 진입 가능). 검증: 드래그 벡터→각도/파워 변환 함수의 경계값(최대 드래그 거리 클램핑) 단위 테스트. 기여: 매트릭스 4-5.
5. **스텝 4 — 발사(릴리즈 → 물리 속도 적용)**. 전제: 스텝 3. 검증: 릴리즈 이벤트가 `Matter.Body.setVelocity`를 입력 벡터와 일치하는 값으로 호출하는지 단위 테스트. 기여: 매트릭스 6, 로드베어링 경로 hop2.
6. **스텝 5 — 충돌/파괴/제거 규칙**. 전제: 스텝 1(물리 월드), 스텝 2(구조물·돼지 스폰 데이터). 검증: `collisionStart` 핸들러가 body 라벨(destructible/pig)별로 올바르게 분기하는 단위 테스트. 기여: 매트릭스 7-10, 로드베어링 경로 hop3·hop4.
7. **스텝 6 — 클리어/실패 판정 + 결과 화면**. 전제: 스텝 5. 검증: `pigs.length === 0` → cleared 이벤트, 발사체 소진+돼지 잔존 → failed 이벤트에 대한 단위 테스트. 기여: 매트릭스 11-13, 17, 로드베어링 경로 hop5.
8. **스텝 7 — 일시정지 UI(우측 버튼 + 오버레이)**. 전제: 스텝 1. 검증: Paused 상태 진입 시 오버레이 DOM에 정확히 두 버튼(다시하기/메인으로)만 렌더되는지 스냅샷 테스트. Paused 전이는 `Runner`를 정지시키는 부수효과를 반드시 포함한다(리스크 참조). 기여: 매트릭스 14-16.
9. **스텝 8 — 진행도 저장(localStorage)**. 전제: 스텝 6. 검증: cleared 이벤트 후 localStorage의 `unlockedStage` 키 갱신 단위 테스트. 기여: 매트릭스 18.
10. **스텝 9 — 메인 메뉴 / 스테이지 선택 화면**. 전제: 스텝 2(스테이지 목록), 스텝 8(잠금 판단 데이터). 검증: `unlockedStage`보다 큰 인덱스는 잠금 표시되는 단위 테스트. 기여: 매트릭스 1, 로드베어링 경로 hop1(진입점).
11. **스텝 10 — 엔드투엔드 슬라이스 검증(스테이지 1 한정)**. 전제: 스텝 0-9 전부. 검증: 아래 로드베어링 경로 5홉 각각의 "first becomes true at" 열이 가리키는 파일:함수가 실제로 존재하고 서로를 호출하는지 정적 추적. 기여: 로드베어링 경로 전체.
12. **스텝 11 — 나머지 9개 스테이지 콘텐츠 확장 및 난이도 커브 조정**. 전제: 스텝 10 통과 후(폭 확장 전에 얇은 슬라이스가 먼저 닫혀야 함). 검증: 스테이지별 데이터 유효성 검증 스크립트(모든 필수 필드 not-null, exit 0). 기여: 매트릭스 2(콘텐츠 축 전체).

## 로드베어링 경로

핵심 루프(드래그→발사→충돌→클리어)가 끊기면 요구사항 2항 전체가 성립하지 않는다. 5홉 체인:

| hop | 이름 | passes only if | first becomes true at |
|---|---|---|---|
| 1 | 메인메뉴 "시작하기"/스테이지 선택 → 스테이지 로드(Loading→Playing) | 선택된 스테이지 인덱스가 저장된 `unlockedStage` 이하 | 스텝 9의 메뉴 클릭 핸들러 + 스텝 1 상태머신의 `LOAD_STAGE` 전이 |
| 2 | 드래그 릴리즈 → 발사 속도 벡터가 Matter.Body에 적용 | Playing 상태이며 드래그 시작점이 새총 앵커 반경 내 | 스텝 3의 입력 캡처 + 스텝 4의 속도 적용 함수 |
| 3 | 발사체가 포물선 이동 중 구조물/돼지와 `collisionStart` 발생 | 발사체 body와 구조물/돼지 body가 동일 physics world에 존재 | 스텝 2 스테이지 로더의 `World.add` 호출(스텝 1의 world 인스턴스에 대해) |
| 4 | 충돌 임계값 초과 시 구조물 파괴/돼지 제거 실행 | 충돌 라벨이 destructible/pig 태그를 가지고 충격량이 `material.threshold` 초과 | 스텝 5의 `collisionStart` 핸들러 |

## 대안 & 기각 사유
- **물리엔진 자체 구현** — 기각: 강체·충돌·파괴 표현력을 검증된 상태로 확보하는 데 드는 개발 리스크·시간이 크다. **부활 트리거**: 스파이크(가정 4)에서 Matter.js가 요구 표현력을 못 준다고 확인되면 재검토.
- **게임 월드 렌더링에 DOM/React 사용** — 기각: 초당 다수 physics body를 DOM으로 갱신하면 리플로우 비용이 크다(메뉴/오버레이/HUD 등 정적 UI는 DOM으로 구현, 게임 월드만 Canvas). **부활 트리거**: 성능 목표가 낮아지고 PixiJS 등 DOM/WebGL 스프라이트 라이브러리 도입 필요성이 커지면 재검토.
- **점수/별점 시스템을 지금 빌드** — 기각: 스펙에 언급 없고 클리어 판정(돼지 전멸)만으로 요구사항이 충족된다. **부활 트리거**: 사용자가 점수/랭킹을 명시적으로 요구하면 추가.
- **다중 발사체 타입을 지금 빌드** — 기각: 스펙은 단일 슬링샷 메커니즘만 요구하며, 다중 타입은 난이도 곡선 설계 복잡도를 크게 늘린다. **부활 트리거**: 스텝 11에서 스테이지 6-10 난이도 검수 결과 단일 발사체로 곡선을 못 만든다고 판단되면 도입.
- **진행도를 백엔드 서버에 저장** — 기각: 스펙은 순수 프론트엔드 웹 게임이며 서버 언급이 전혀 없다. **부활 트리거**: 멀티 디바이스 진행도 동기화 요구가 생기면 도입.

## 리스크 & 완화
- Matter.js에서 밀도/질량 설정 누락 시 정적 바디가 비정상 질량으로 계산되어 위치값이 `NaN`이 될 수 있다 — 완화: 모든 구조물 블록에 `density`를 명시하고, 개발 중 body 위치의 `NaN` 가드(값 검증 후 즉시 실패)를 추가한다.
- 난이도 커브가 초반엔 너무 쉽고 후반에 급격히 어려워질 위험 — 완화: 재질 임계값·돼지 수·발사체 여유분을 스테이지별 표로 사전 정의하고 단조 증가를 검토한다(스텝 11).
- 드래그-발사 속도 매핑이 과민하거나 둔감해 플레이감을 해칠 위험 — 완화: 최대 드래그 거리 클램핑 + power multiplier 상수 도입(초기값·임의 태그, 첫 플레이테스트 후 조정).
- 일시정지 중 물리 시뮬레이션이 계속 진행되어 오버레이 뒤에서 게임이 흘러가는 위험 — 완화: `Paused` 전이의 필수 부수효과로 Matter.js `Runner` 정지를 명시(스텝 7).

## 커버리지 자가 점검
스펙에 없어 매트릭스에서 `n-a`로 처리한 축: 접근성(키보드 전용 조작 대안), 다국어, 애널리틱스, 수익화. 이 게임의 10스테이지 슬링샷 요구사항은 이들을 요구하지 않는다고 판단해 명시적으로 스코프 밖에 둔다(침묵이 아니라 판정).

## 완료의 정의
- 10개 스테이지 데이터 파일이 모두 존재하고, 각각 최소 1개 이상의 돼지·1개 이상의 파괴 가능 구조물·유효한 새총 앵커 좌표를 갖는다 — 측정: 스키마 검증 스크립트가 exit 0.
- 로드베어링 경로 5홉 전부가 "first becomes true at" 열을 채우고 있으며, 각 홉이 가리키는 함수/파일이 실제로 존재한다 — 측정: 대상 심볼에 대한 `grep` 조회가 결과를 반환.
- 일시정지 오버레이는 정확히 두 개의 버튼(다시하기, 메인으로)만 렌더한다 — 측정: DOM 스냅샷 테스트가 exit 0.
- `npx tsc --noEmit`이 exit 0.

## 구현자 계약
- **대안 부활 트리거**: 위 "대안 & 기각 사유" 절의 4개 항목 각각의 트리거 조건을 그대로 따른다(중복 기재 생략).
- **핀 고정 버전**: `matter-js@0.19.0`, `@types/matter-js@0.19.6`, `typescript@5.6.3`, `vite@5.4.11`. 설치 전 `npm view <pkg>@<version>`으로 해당 버전이 실제로 존재하는지 재확인한다(핀은 계획 시점 기준이며 최신 패치로 조정 가능).
- **스택이 산 것과 그 증명**:
  - TypeScript가 사는 것: 스테이지 스키마(스텝 2)와 상태머신(스텝 1)의 형태를 컴파일 타임에 강제. 증명: `npx tsc --noEmit`이 exit 0.
  - Vite가 사는 것: 개발 서버 + 프로덕션 번들링. 증명: `npm run build`가 exit 0.
  - Matter.js가 사는 것: 검증된 강체 충돌·중력 시뮬레이션(가정 4 참조). 증명: 스텝 0 직후 스파이크(블록 3개 + 발사체 1개 충돌)가 `collisionStart` 이벤트를 발생시키고 콘솔에 로그를 남김(수동 1회 확인, 스파이크 산출물로 코드에 남긴다).

## Frame deviations & habit regressions
- §"접근 & 단계"의 스텝 0을 "스택 확정"으로 먼저 적은 것 자체가 반사적 습관(엔진부터 정하기)이다. spec-coverage 프레임이 요구하는 순서(매트릭스 먼저)는 문서 최상단 절에서는 지켰지만, "접근 & 단계"의 첫 문장이 다시 스택 이야기로 시작하는 것은 완전히 떨쳐내지 못한 흔적이다.
- 가장 약한 절은 "콘텐츠 축(10 스테이지 난이도 커브)"이다. 재질·돼지 수·발사체 수의 구체적 숫자를 스테이지별로 표로 박아 넣지 않고 구간 서술로 남겼다 — 내가 리뷰어라면 이 절을 공격해 "표로 만들지 않으면 스텝 11의 검증 스크립트가 무엇을 검사하는지 불명확하다"고 지적할 것이다.
- 관례(제네릭 슬링샷 게임 관례상 유한 발사체+실패 상태)를 스펙이 요구하지 않았음에도 build로 판정한 곳(매트릭스 12행)은 프레임보다 관례를 택한 지점이다. 가정 절에서 "틀렸을 때 영향"을 명시해 되돌릴 수 있게는 해두었다.
