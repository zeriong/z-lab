# 웹 브라우저 앵그리버드 게임 — 구현 계획서

## 0. 범위와 목표

물리 기반 슬링샷 게임을 웹 브라우저에서 동작하는 단일 페이지 앱(SPA)으로 구현한다.

- 스테이지 10개
- 새총으로 발사체를 당겨 쏘는 조작, 포물선 궤적, 중력, 충돌, 구조물 파괴, 목표(돼지) 제거
- 인게임 우측에 일시정지 버튼 → 클릭 시 "다시하기 / 메인으로" 오버레이

이 문서는 코드를 작성하지 않고, 구현자가 그대로 따라가면 게임이 완성되도록 결정 사항과 순서를 확정한다.

---

## 1. 기술 스택 결정

### 1-1. 물리 엔진: Matter.js (라이브러리 채택, 직접 구현 안 함)

**결정: Matter.js 채택.**

이유:
- 앵그리버드 핵심 재미는 "그럴듯한 물리 반응"(충돌 반응, 토크, 마찰, 구조물이 무게중심을 잃고 무너지는 것)이다. 이를 직접 구현하려면 강체 충돌 해석(SAT/GJK), 임펄스 해석, 안정적인 스태킹(constraint solver)까지 필요해 실질적으로 미니 물리엔진 하나를 새로 만드는 일이 된다. 10 스테이지 분량의 콘텐츠 제작 시간을 확보하려면 여기에 예산을 쓰지 않는다.
- Matter.js는 body(Body), 제약(Constraint — 새총 고무줄 구현에 바로 사용 가능), 충돌 이벤트(`collisionStart`), 카테고리 기반 충돌 필터, sleeping body 최적화를 기본 제공한다.
- 라이선스(MIT), 번들 크기(~90KB min), 유지보수 상태 모두 이 프로젝트 규모에 적합.

트레이드오프로 인지하고 넘어가는 것:
- Matter.js의 안정성 튜닝(터널링, 얇은 판자의 스태킹 흔들림)은 알려진 약점이다. 대응: `engine.positionIterations`/`velocityIterations` 상향, 얇은 구조물 두께 하한선(8px 이상)을 콘텐츠 제작 규칙으로 둔다. 새(발사체)처럼 빠른 물체의 터널링 방지를 위해 `Body.setVelocity` 대신 매 프레임 속도 상한을 두고, CCD 대안으로 발사체 반지름을 충분히 크게(최소 12px) 잡는다.
- 물리 세부값(반발계수, 마찰)의 정성적 튜닝(=재미)은 구현 단계에서 플레이테스트로 조정한다. 본 계획서는 초기값만 제시한다(§6).

### 1-2. 렌더링: Canvas 2D (DOM/SVG/WebGL 배제)

**결정: HTML5 `<canvas>` + 2D Context. Matter.js의 물리 상태를 매 프레임 읽어 커스텀 렌더러가 직접 그린다(Matter의 내장 `Render` 모듈은 디버그용으로만 개발 중 사용, 최종 빌드에서는 미사용).**

이유:
- 오브젝트 수(스테이지당 블록 20~60개 + 파티클)가 DOM 요소로는 리플로우 비용이 크다. Canvas는 즉시모드 렌더링이라 오브젝트 수 증가에 선형적으로만 비용이 늘고 예측 가능하다.
- WebGL(Pixi 등)은 성능 여유는 크지만 이 게임 규모(2D, 오브젝트 수백 개 이하)에서는 과설계다. 셰이더/텍스처 관리 오버헤드를 정당화할 스펙이 없다.
- Canvas 2D는 궤적 예측선, 파괴 파티클, 조준선 등 커스텀 이펙트를 직접 제어하기 쉽다.

렌더-물리 분리 원칙: Matter는 시뮬레이션만 담당(px=물리단위 1:1 매핑, 별도 스케일 없음). 렌더러는 매 프레임 `world.bodies`를 순회해 `position`/`angle`을 읽어 스프라이트 또는 벡터 도형을 그린다. 물리 스텝은 고정 타임스텝(아래 §1-3), 렌더는 `requestAnimationFrame`으로 분리한다.

### 1-3. 게임 루프

- `Engine.update`를 고정 delta 16.667ms(60Hz)로 호출하는 고정 타임스텝 + 누적 오차(accumulator) 패턴 사용. 프레임 드랍 시에도 물리 결과가 기기 성능에 좌우되지 않도록 한다(스테이지 클리어 판정의 재현성 확보 목적).
- 렌더는 `requestAnimationFrame` 콜백에서 누적된 물리 스텝만큼 `Engine.update`를 실행 후 1회 그린다. 탭이 백그라운드로 갈 때(`visibilitychange`) accumulator를 초기화해 "따라잡기 폭주"를 방지하고, 자동 일시정지 처리(§5-3)와 연동한다.

### 1-4. 언어/빌드

- **바닐라 JavaScript(ES2020+ 모듈), TypeScript 미사용.** 이유: 팀 표준이 정해지지 않은 상태에서 이 규모(단일 개발자 기준 2~3주)의 게임에 타입 시스템 도입 비용 대비 이득이 크지 않다고 판단. 단, JSDoc 주석으로 스테이지 데이터 스키마와 핵심 함수 시그니처는 문서화한다(타입 체크는 하지 않되 가독성 확보).
- **번들러: Vite.** 개발 서버 HMR, ES 모듈 네이티브 지원, 정적 자산(스프라이트/사운드) 처리가 설정 최소로 가능. 프레임워크(React 등)는 사용하지 않는다 — 게임 화면 자체는 Canvas 단일 트리이고, UI 오버레이(메인/일시정지/클리어 화면)만 DOM인데 이 정도 상태 전환은 프레임워크 없이 상태 머신 + `classList` 토글로 충분하다(§5).
- 외부 의존성은 `matter-js` 단 하나로 제한한다. 사운드는 Web Audio API를 직접 사용(라이브러리 불필요 규모).

## 2. 상태 머신 (게임 전체 흐름)

```
[MAIN_MENU] --스테이지 선택--> [STAGE_LOADING] --로드 완료--> [PLAYING]
[PLAYING] --일시정지 버튼--> [PAUSED]
[PAUSED] --재개--> [PLAYING]
[PAUSED] --다시하기--> [STAGE_LOADING](같은 스테이지)
[PAUSED] --메인으로--> [MAIN_MENU]
[PLAYING] --클리어 조건 충족--> [STAGE_CLEAR]
[PLAYING] --실패 조건 충족--> [STAGE_FAILED]
[STAGE_CLEAR] --다음 스테이지--> [STAGE_LOADING](n+1) | --메인으로--> [MAIN_MENU]
[STAGE_FAILED] --다시하기--> [STAGE_LOADING](같은 스테이지) | --메인으로--> [MAIN_MENU]
```

- 상태는 단일 `GameState` 열거값(문자열 상수)으로 관리하고, 상태 전이는 하나의 `transition(nextState)` 함수를 통해서만 일어난다(산발적인 `if` 분기로 상태를 바꾸지 않는다 — 버그 재현성을 위해 전이 지점을 한 곳에 모은다).
- 각 상태는 대응하는 DOM 오버레이 또는 없음(PLAYING은 오버레이 없이 canvas만)과 1:1 매핑된다. 상태 전이 시 이전 오버레이 `hidden` 처리, 다음 오버레이 표시라는 단순 규칙만 적용한다.
- `PLAYING` 진입 시에만 물리 시뮬레이션 스텝이 진행된다. `PAUSED`/메뉴류 상태에서는 `Engine.update` 호출 자체를 건너뛴다(Matter world를 정지시키는 것이 아니라 애초에 업데이트를 호출하지 않는 방식 — 재개 시 결과 재현성이 더 단순함).

## 3. 화면 구성

1. **메인 메뉴 (`MAIN_MENU`)**: 타이틀, "시작" 버튼(1스테이지 또는 마지막 플레이 위치부터), 스테이지 선택 그리드(10칸, 클리어 여부/별점 표시).
2. **인게임 (`PLAYING`)**: 풀스크린 canvas. 좌상단 HUD(현재 스테이지, 남은 새 개수 아이콘, 점수), **우측에 일시정지 버튼**(요구사항 명시 위치 — 세로 중앙 정렬, 화면 우측 여백에 고정 배치. 이유: 오른손 조작 시 엄지/마우스 이동 동선이 짧고, 새총 조준 영역(화면 좌측~중앙)과 겹치지 않음).
3. **일시정지 오버레이 (`PAUSED`)**: canvas 위에 반투명 딤 처리 + 중앙 패널. 버튼: "계속하기", "다시하기", "메인으로". (요구사항은 "다시하기/메인으로" 2개를 명시하므로 이 둘은 필수, "계속하기"는 일시정지 버튼 자체의 토글로 대체 가능하나 UX상 명시적 버튼도 함께 제공 — 이 부분은 구현 재량으로 명시.)
4. **스테이지 클리어 오버레이 (`STAGE_CLEAR`)**: 획득 별(1~3), 점수, "다음 스테이지" / "메인으로" 버튼. 마지막(10번째) 스테이지 클리어 시 "다음 스테이지" 대신 "축하 메시지 + 메인으로"만 표시.
5. **스테이지 실패 오버레이 (`STAGE_FAILED`)**: 새를 모두 소진했는데 목표 미달성 시. "다시하기" / "메인으로".

오버레이는 모두 DOM(`<div class="overlay">`)으로 canvas 위에 절대 위치 배치. 게임 자체 렌더링과 UI 오버레이 레이어를 분리해 각각의 관심사를 단순하게 유지한다(캔버스 안에 버튼을 그리고 픽셀 히트테스트를 하는 방식은 배제 — 접근성/구현 복잡도에서 불리).

## 4. 슬링샷 입력 UX

### 4-1. 조작 흐름

1. 새가 새총 발사대(고정 앵커 좌표)에 스폰된 상태로 대기.
2. 사용자가 새 위(또는 근방 히트 영역, 판정 반경은 스프라이트 반지름의 1.6배로 여유를 둠)에서 포인터 다운.
3. 드래그하는 동안 새를 포인터 위치로 이동(단, 앵커로부터 최대 드래그 반경 `MAX_PULL`을 제한 — 무한정 당겨져 비현실적 궤적이 나오는 것 방지). 이 동안 새의 물리 바디는 `isStatic` 유지하거나, Matter Constraint(고무줄)로 앵커에 묶어 두고 포인터 위치를 constraint의 목표점으로 갱신.
4. 드래그 중 실시간으로 **궤적 예측선**을 점선/점 형태로 표시(아래 4-2).
5. 포인터 업(release) 시: 당긴 벡터(앵커 - 놓은 지점)에 발사 계수를 곱해 발사 속도를 계산하고, constraint를 제거해 새를 자유 물체로 전환, 계산된 속도를 즉시 부여.
6. 최소 드래그 거리 미달 시(예: 20px 미만) 발사로 인정하지 않고 새를 앵커로 복귀(오조작 방지).

포인터 이벤트는 마우스/터치를 통합 처리하는 `Pointer Events API`(`pointerdown/pointermove/pointerup`)로 구현해 데스크톱/모바일 브라우저 분기 코드를 최소화한다.

### 4-2. 궤적 예측

- 드래그 중 매 프레임, 현재 계산된 발사 속도로 "만약 지금 쏘면"의 포물선을 순수 수학 공식(등가속도 운동, `y = y0 + v*t + 0.5*g*t^2`)으로 계산해 5~8개의 점을 canvas에 점선으로 미리 그린다.
- Matter 시뮬레이션을 실제로 굴려서 예측하지 않는다(구조물과의 충돌까지 시뮬레이션하면 비용도 크고, 화면에 여러 물체가 튀는 걸 미리 보여주는 것은 오히려 스포일러/부자연스러움). 예측선은 "빈 공간에서의 이상적 탄도"만 보여주는 것으로 범위를 한정한다 — 실제 앵그리버드류 게임들의 통상적 UX와 일치.
- 발사 후에는 예측선을 제거하고, 실제 궤적을 얇은 잔상(옵션, 최소 구현 범위 밖 — "있으면 좋은 것"으로만 명시하고 필수 범위에서 제외)으로 남기지 않는다(범위 확대 방지, MVP 이후 과제로 분리).

### 4-3. 발사 파라미터

- `PULL_TO_VELOCITY_SCALE`: 드래그 거리(px) → 초기 속도(px/s) 변환 계수. 초기값 제안 8~10, 최종은 플레이테스트로 조정(§9에서 조정 가능 파라미터로 명시).
- `MAX_PULL`: 120px (앵커 기준 반경 제한).
- 발사 방향은 항상 "당긴 지점 → 앵커" 벡터의 반대 방향이 아니라 정확히 그 벡터 방향(즉 고무줄이 당겨진 반대 방향으로 날아가는 표준 새총 물리).

## 5. 스테이지 시스템

### 5-1. 데이터 구조

스테이지는 코드와 분리된 **정적 JSON 10개** (`stages/stage-01.json` ~ `stage-10.json`)로 정의한다. 이유: 레벨 디자인(콘텐츠) 변경이 코드 변경 없이 가능해야 하고, 10개 스테이지를 하나의 거대 배열/객체에 몰아넣지 않아 diff/리뷰가 스테이지 단위로 독립된다.

```jsonc
// stages/stage-01.json (스키마 예시)
{
  "id": 1,
  "name": "그린 힐 1",
  "birdCount": 3,
  "birdOrder": ["normal", "normal", "normal"],   // 스테이지별 새 종류/순서 (§5-4)
  "slingshotAnchor": { "x": 150, "y": 400 },
  "groundY": 550,
  "targetScore": { "oneStar": 5000, "twoStar": 12000, "threeStar": 20000 },
  "blocks": [
    { "type": "box", "material": "wood", "x": 600, "y": 500, "w": 40, "h": 120, "angle": 0 },
    { "type": "box", "material": "stone", "x": 700, "y": 500, "w": 200, "h": 20, "angle": 0 }
  ],
  "pigs": [
    { "x": 650, "y": 460, "radius": 18 }
  ],
  "background": "hill"
}
```

- 필드 최소 원칙: 요구사항이 요구하지 않는 필드(예: 배경음악 개별 지정, 날씨 효과)는 넣지 않는다. `background`는 배경 스프라이트 셋 선택용으로만 최소 포함(스테이지가 10개면 시각적 변주가 있어야 "10단계"가 콘텐츠로 체감되므로 — 이는 요구사항 1번의 실질적 충족 조건으로 판단해 포함).
- `blocks[].type`은 `box`(사각) / `circle`(원형, 통나무 등) 두 종류로 시작. 삼각형 등은 필요 시 확장 가능하나 초기 범위는 2종으로 제한(구조물 다양성은 배치 조합으로 확보, 도형 종류를 늘리는 것으로 확보하지 않음 — 콘텐츠 제작 리스크 관리).
- `material`은 `wood`(약함) / `stone`(강함) / `ice`(약하지만 미끄러움, 마찰 낮음) 3종. 재질별 물성값(§6 참조)은 코드 상수 테이블(`MATERIALS`)에 정의하고 JSON은 이름만 참조한다(값 중복 방지).

### 5-2. 로딩/전환

- `loadStage(stageId)`: 기존 Matter `World`를 `Composite.clear`로 완전히 비우고, JSON을 읽어 새 world를 구성한다(스테이지 간 상태 누수 방지 — 이전 스테이지의 부서진 조각이 다음 스테이지로 넘어오는 버그를 원천 차단).
- 로딩은 동기적으로 처리 가능한 수준의 데이터 크기(스테이지당 JSON 수 KB)이므로 별도 로딩 스피너/프로그레스바는 넣지 않는다(과설계 방지). `STAGE_LOADING` 상태는 존재하되 실질적으로는 "다음 프레임 전 완료"로 매우 짧게 지나간다 — 상태 자체는 전이 로직을 명확히 하기 위해 유지.
- 진행도 저장: `localStorage`에 `{ unlockedStage: number, stars: { [stageId]: 0|1|2|3 } }` 저장. 스테이지 클리어 시 다음 스테이지 unlock, 별점은 갱신 시 더 높은 값만 덮어쓴다(재도전으로 점수가 낮아져도 기존 별점 유지).

### 5-3. 자동 일시정지 (탭 전환 대응)

- `visibilitychange`에서 문서가 숨겨지면 `PLAYING` → `PAUSED`로 자동 전이한다(요구사항에 명시되진 않았으나, 고정 타임스텝 물리 루프가 탭 비활성 중 브라우저에 의해 스로틀링된 채로 계속 돈다고 가정할 수 없어 §1-3의 재현성 전제를 지키기 위한 필수 보완 — 별도 버튼 없이 기존 PAUSED 상태/오버레이 재사용).

### 5-4. 새 종류 (범위 결정)

**결정: MVP 범위는 `normal`(단일 새 종류) 1종만 구현한다. 특수 능력(폭탄새, 분열새 등)은 범위에서 제외한다.**

이유: 요구사항 2번은 "앵그리버드와 같은 게임 시스템"을 "새총으로 당겨 쏘고 포물선·중력·충돌·파괴로 목표 제거"로 구체적으로 정의하고 있고, 새 종류별 특수능력은 언급이 없다. 특수능력을 넣으면 입력 UX(탭하여 발동 등)와 밸런싱 범위가 크게 늘어난다. `birdOrder` 필드는 스키마에 남겨 두어(§5-1) 추후 확장 시 스테이지 데이터 변경만으로 대응 가능하게 하되, 이번 구현 범위는 `normal` 고정이다. **(구현자 확인 필요 항목 — §10에 재기재)**

## 6. 충돌 · 파괴 · 점수 · 클리어 판정

### 6-1. 충돌 카테고리

Matter의 `collisionFilter.category`로 4개 그룹 정의: `BIRD`, `PIG`, `BLOCK`, `GROUND`. 모든 그룹은 서로 충돌하되(`mask`는 전체 허용), 이벤트 처리 로직에서 `pair.bodyA/bodyB`의 group 조합으로 분기한다.

### 6-2. 파괴 판정 (블록)

- 각 블록 바디는 커스텀 속성 `hp`(재질별 초기값: wood=30, stone=80, ice=15)를 가진다.
- `Matter.Events.on(engine, 'collisionStart', ...)`에서 각 충돌 쌍의 상대 속도 크기(`Vector.magnitude(pair.collision.normal 방향 relative velocity)`)를 데미지로 환산해 `hp`에서 차감. 데미지 계산식: `damage = relativeSpeed * DAMAGE_SCALE`(재질 무관 공통 계수, 재질별 차이는 hp로만 구현 — 계산식을 재질마다 분기하지 않아 단순함 유지).
- `hp <= 0`이 되면 해당 블록을 world에서 제거하고, 파편 파티클(물리 연산 없는 순수 시각 효과, 짧은 수명의 canvas 도형)을 생성한다. 파편은 물리 바디가 아니라 렌더 전용 객체로 처리한다(물리 바디 수를 늘리면 성능·안정성 리스크가 커지므로 — 파괴 연출과 시뮬레이션 정확도를 분리하는 결정).
- 얼음(`ice`) 재질은 낮은 hp로 "잘 부서짐"을, 낮은 friction(0.02)으로 "미끄러짐"을 동시에 표현.

### 6-3. 돼지 제거 판정

- 돼지는 `hp` 없이 **단일 임계 충격량**으로 판정한다: 충돌 시 상대 속도가 `PIG_KILL_THRESHOLD` 이상이면 즉시 제거, 미만이면 생존(넉백만 발생, Matter의 기본 임펄스 반응에 맡김). 이유: 앵그리버드류 게임에서 돼지는 "때리면 죽는" 즉발 판정이 장르 관습이고, 여기에 hp 시스템을 추가하는 것은 불필요한 상태 추가(요구사항이 요구하지 않은 복잡도).
- 돼지가 무너지는 구조물에 깔려 죽는 경우도 위 조건으로 자연히 처리된다(충돌 상대가 새인지 블록인지 구분하지 않음 — "무엇에 맞았는가"가 아니라 "얼마나 세게 부딪혔는가"만 본다. 이는 실제 앵그리버드의 "구조물 붕괴로 돼지 제거" 재미 요소를 그대로 지원).

### 6-4. 점수

- 돼지 제거: 각 500점(고정값, 콤보/배율 없음 — 범위 최소화).
- 블록 파괴: 재질별 wood=50, stone=100, ice=20.
- 미사용 새 보너스: 스테이지 클리어(모든 돼지 제거) 시, 남은 새 1마리당 +1000점.
- 점수 산정은 `STAGE_CLEAR` 진입 시점에 1회 확정하며, 이후 화면에 남은 발사체가 계속 굴러다니며 추가 파괴를 일으켜도 점수에 반영하지 않는다(판정 시점을 명확히 고정 — "클리어 이후에도 물리가 계속 도는데 점수는 언제 확정인가"라는 모호함을 제거).

### 6-5. 클리어 / 실패 판정

- **클리어 조건**: 스테이지의 모든 `pigs`가 제거됨. 매 물리 스텝 후 `pigs.length === 0`을 체크해 즉시 `STAGE_CLEAR`로 전이(발사 중이던 새의 잔여 움직임을 기다리지 않음 — 마지막 한 마리를 죽인 즉시 클리어되는 것이 장르 관습).
- **실패 조건**: 스테이지의 모든 새를 소진(발사 완료 + 새 바디가 화면 밖으로 벗어나거나 정지)했고, 아직 돼지가 1마리 이상 남아 있음. "소진 완료" 판정은 (a) `birdCount`만큼 발사했고 (b) 마지막 새가 정지(속도 임계값 이하로 0.5초 이상 유지) 또는 화면 경계 밖으로 이탈했을 때로 정의한다 — 새가 아직 굴러다니는 도중에 성급하게 실패 처리하지 않기 위함.
- 별점(1~3)은 `targetScore`의 `oneStar/twoStar/threeStar` 임계값과 최종 점수를 비교해 결정. 클리어에 실패하면 별 0개.

## 8. 구현 순서 (마일스톤)

각 마일스톤은 이전 단계가 동작해야 다음으로 넘어갈 수 있도록 의존성 순서로 배열했다.

1. **뼈대**: Vite 프로젝트, canvas 세팅, 고정 타임스텝 루프, Matter world에 정적 바닥 하나 + 원형 바디 하나 낙하 확인 (물리 파이프라인 자체가 도는지 검증).
2. **상태 머신 + 화면 전환**: 메인 메뉴 ↔ 인게임 ↔ 일시정지 오버레이. 이 시점에는 스테이지 콘텐츠 없이 빈 canvas라도 상태 전이와 우측 일시정지 버튼, "다시하기/메인으로" 버튼 동작을 먼저 완성한다(요구사항 3번을 독립적으로 검증 가능하게 만듦).
3. **슬링샷 입력**: 앵커에 새 스폰, 드래그, 예측선, 발사. 스테이지 없이 빈 지형에서 발사 단독 동작 확인.
4. **충돌/파괴/점수**: 재질별 hp, collisionStart 데미지, 돼지 즉발 판정, 점수 계산. 하드코딩된 테스트 배치(블록 몇 개 + 돼지 1마리) 하나로 클리어까지 1회 완주.
5. **스테이지 데이터화**: 위 테스트 배치를 JSON 스키마로 옮기고 `stage-loader`로 로드. 스테이지 전환(클리어 → 다음 스테이지) 연결.
6. **10개 스테이지 콘텐츠 제작**: 난이도 곡선 설계(§9 참고) 후 1번부터 순서대로 제작, 매 스테이지 실제 플레이로 클리어 가능성 확인.
7. **세이브/별점/스테이지 선택 화면**: localStorage 연동, 메인 메뉴의 스테이지 그리드에 별점 표시.
8. **폴리싱**: 파편 파티클, 사운드(발사/충돌/돼지 제거/클리어), HUD 다듬기.

## 9. 난이도 곡선 (스테이지 10개 콘텐츠 설계 가이드)

- 1~2: 튜토리얼 성격. 단순 구조물 1~2개, 새 3마리, 돼지 1~2마리. 실패하기 어려운 난이도로 조작 학습.
- 3~5: 재질 혼합 시작(wood+stone 조합), 돼지 2~3마리, 새 3마리로 여유 감소.
- 6~8: 얼음 재질 등장(미끄러짐 활용 퍼즐), 다단 구조물(위에 쌓인 구조물이 무너져야 닿는 돼지), 새 2~3마리.
- 9~10: 복합 구조(여러 구조물 + 3종 재질 혼합), 새 2마리로 여유 최소화, 정밀 조준 요구.

이 곡선은 §5-1 스키마의 `blocks`/`pigs`/`birdCount` 조합만으로 표현되므로 코드 변경 없이 콘텐츠 작업만으로 달성 가능하다.

## 10. 완료 판정 기준 (Definition of Done)

다음을 모두 만족하면 "완료"로 판정한다.

1. 메인 메뉴에서 시작 → 1번 스테이지 진입 → 새총으로 발사 → 포물선 궤적으로 발사체가 날아가 구조물에 충돌해 파괴되고, 돼지가 임계 충격 이상으로 맞으면 제거되는 과정이 실제로 동작한다.
2. 10개 스테이지 전부가 로드 가능하고, 각 스테이지가 §9 기준에 따라 최소 1가지 방법으로 클리어 가능함을 실제 플레이로 확인했다(자동 솔버가 아니라 수동 플레이 확인 — 물리 기반 게임은 정적 분석으로 클리어 가능성을 보장할 수 없으므로).
3. 인게임 화면 우측에 일시정지 버튼이 존재하고, 클릭 시 물리 시뮬레이션이 즉시 멈추며(§2 — `Engine.update` 미호출) "다시하기"와 "메인으로" 버튼이 표시된다.
4. "다시하기"는 현재 스테이지를 초기 상태로 재로드하고, "메인으로"는 메인 메뉴로 복귀한다. 두 경우 모두 이전 스테이지의 물리 바디가 잔류하지 않는다(§5-2 `Composite.clear` 확인).
5. 모든 돼지 제거 시 클리어 화면, 새 소진 후 돼지 잔존 시 실패 화면이 정확히 갈라져 표시된다.
6. 진행도(unlock된 스테이지, 별점)가 새로고침 후에도 `localStorage`로 유지된다.
7. 콘솔에 물리/렌더 관련 반복 에러(예: NaN position, 매 프레임 warning)가 없다.

**이 문서가 측정/판정하지 않는 것**: 프레임 성능 수치(FPS) 목표치, 모바일 터치 세부 최적화, 접근성(스크린리더) 대응, 다국어, 사운드 볼륨 밸런싱, 애니메이션(새 표정 변화 등) 디테일. 이들은 요구사항에 명시되지 않았으므로 범위에서 제외했고, 필요 시 별도 요구사항으로 추가되어야 한다.

## 11. 구현자 확인이 필요한 항목 (실행 전 결정 필요)

- **§5-4 새 종류**: 특수 능력 새(폭탄새 등)를 넣을지 여부를 "포함 안 함"으로 가정하고 계획했다. 요구사항에 명시가 없어 이렇게 판단했으나, 만약 "앵그리버드 같은 게임"에 특수 새가 당연히 포함되어야 한다는 기대가 있다면 §5-1 스키마의 `birdOrder`/`type` 필드를 확장하고 §4 입력 UX에 "탭하여 능력 발동" 처리를 추가해야 한다 — 이 경우 마일스톤 3, 4가 커진다.
- **모바일 지원 범위**: 슬링샷 조작을 Pointer Events로 설계해 터치 자체는 동작하지만, 화면 크기별 반응형 레이아웃(HUD 배치, canvas 리사이즈 정책)은 별도 결정이 필요하다. 이 계획서는 데스크톱 우선(고정 해상도 캔버스, 뷰포트에 맞춰 스케일만 조정)으로 가정했다.
- **사운드/스프라이트 자산 출처**: 자체 제작 여부, 무료 에셋 사용 여부가 결정되지 않았다. §8 마일스톤 8(폴리싱)은 자산이 준비된 이후에만 진행 가능하므로 별도 트랙으로 조기에 착수 여부를 정해야 한다.
