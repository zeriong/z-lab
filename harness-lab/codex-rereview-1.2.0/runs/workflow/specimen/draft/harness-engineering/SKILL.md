# Harness engineering

## 적용 경로와 범위

프로젝트 루트를 기준으로 다음 설치 경로를 사용한다.

- 프로젝트 규칙: `.agents/skills/project-rules/SKILL.md`
- 이 워크플로: `.agents/skills/harness-engineering/SKILL.md`
- 결정적 검증 게이트: `.codex/scripts/review-gate.sh`
- 관례 참조: 저장소에 실제로 존재하는 `docs/conventions/` 문서 및 관련 코드

기존 프로젝트 명령을 유지하고 저장소 근거가 있는 규칙만 적용한다. 새 프로젝트 규칙을 추정해 만들지 않는다. 요청 범위와 기존 사용자 답변을 유지하며, 이 워크플로 자체는 설정 변경이나 커밋·게시 권한을 부여하지 않는다.

## 우회

요청이 `!`로 시작하거나 `harness 빼고`, `without harness`, `skip harness`, `no harness`로 우회를 지정하면 아래 워크플로를 건너뛴다. 프롬프트 훅은 프로젝트 규칙을 유지하고 워크플로 본문만 짧은 `BYPASS MODE` 안내로 대체한다. 우회는 이 harness 워크플로에만 적용되며 다른 프로젝트 지침이나 별도 훅은 계속 적용된다.

## 열한 단계

0. **접수:** 원하는 결과, 범위, 제약을 확인하고 기존 답변을 재사용한다. 실제 프로젝트 루트와 기존 테스트·lint·typecheck 명령을 확인해 계획 도구 또는 로컬 기록에 고정한다. 우회 요청이면 여기서 워크플로를 생략한다.
1. **조사:** 영향받는 코드와 사용처를 읽고 주장을 파일과 대조한다. `file:line` 근거를 기록한다. 패치를 적용할 때마다 영향 범위를 다시 조사한다.
2. **규칙:** 적용할 프로젝트 규칙과 관례 참조를 선택한다. 결정적 게이트 규칙과 권고 지침을 구분하고 근거 없는 규칙을 추가하지 않는다.
3. **계획:** 확인된 결과를 만족하는 최소 변경과 성공을 입증할 검사를 정한다. 구현에 영향을 주는 미확정 사항은 구현 전에 해결한다.
4. **구현:** 근거로 확인한 프로젝트 관례에 따라 범위 내 변경을 수행한다.
5. **동작 검사:** 관련 기존 테스트를 실행한다. 동작 변경이나 회귀 방지에 필요한 경우 테스트 범위를 보강한다. 실패와 근거를 기록한다.
6. **정적 검사:** 접수에서 고정한 lint·typecheck 명령을 실행한다. 실행할 수 없는 검사까지 포함해 실제 결과를 기록한다.
7. **문서:** 영향받는 관례 예시와 사용자 동작 문서를 수정한다. 인용과 키워드 색인을 코드와 일치시킨다.
8. **검토 게이트:** 프로젝트 게이트를 `--mode=full`로 먼저 실행한 뒤 아래 절차로 두 독립 일회성 검토를 받는다. 메인 세션이 결과를 종합하고 검토자는 변경을 제안만 한다. 여섯 품질 축으로 패치를 평가한다. 적용한 모든 패치는 1단계로 돌아간다. 검토·회귀 반복은 최대 3회이며 통과하지 못하면 남은 지적과 함께 중단한다.
9. **최종 검증:** 실제 최종 diff, 테스트 결과, 남은 지적을 확인한다. 실패하거나 실행할 수 없는 검사를 통과로 표시하지 않는다.
10. **전달:** 변경된 동작, 근거, 한계를 보고한다. 커밋 또는 게시는 사용자가 해당 행위를 허용한 경우에만 수행한다.

## 검토 게이트

### 결정적 게이트

`PROJECT_ROOT`를 접수에서 확인한 실제 프로젝트 루트의 절대 경로로 지정하고 실행한다.

```bash
bash "$PROJECT_ROOT/.codex/scripts/review-gate.sh" --mode=full
```

- 종료 코드 `0`: 결정적 게이트 통과. 두 독립 검토가 추가로 필요하다.
- 종료 코드 `1`: 규칙 위반. 근거를 기록하고 해결한다.
- 종료 코드 `2`: 설정 또는 실행 오류. 원인을 기록하고 해결한다.
- 명령·스크립트 누락, 기타 비정상 종료: 실행 실패이며 통과가 아니다.

실패한 게이트는 검토자의 긍정 평가로 대체할 수 없다. 수정 후 1단계부터 관련 검증을 다시 수행한다.

### 매 검토 직전 모델과 effort 결정

이 스킬을 실행할 때마다, 그리고 각 검토 호출 직전에 **그 시점의 메인 세션에서 실제 사용 중인 모델과 reasoning effort**를 세션 정보로 확인한다. 이전 세션, 생성 시점, 이전 반복의 값을 기본값으로 저장해 재사용하지 않는다. 모델 이름이나 effort를 상수로 대체하지 않는다.

| 역할 | 명시적 모델 설정 | 명시적 effort 설정 | 각 미지정 값의 기본값 |
|---|---|---|---|
| 아키텍처·규칙 도출 | `HARNESS_CODEX_ARCH_MODEL` | `HARNESS_CODEX_ARCH_EFFORT` | 현재 메인 세션의 실제 모델 / effort |
| 게이트·구현 | `HARNESS_CODEX_GATE_MODEL` | `HARNESS_CODEX_GATE_EFFORT` | 현재 메인 세션의 실제 모델 / effort |

네 override를 각각 독립적으로 적용한다. 비어 있는 설정은 미지정으로 취급한다. 기본값에 필요한 현재 값을 확인할 수 없다면 검토 실행을 멈추고 해당 역할의 명시적 모델·effort 설정을 요청한다. 추정하거나 임의 기본값으로 진행하지 않는다. 완전한 역할별 명시 설정이 있으면 그 설정을 사용한다. override 모델이 선택된 effort를 지원하는지 확인하고, 지원 여부가 불명확하거나 지원하지 않으면 실행 전에 해결한다.

매번 확인한 현재 값을 `CURRENT_MAIN_MODEL`, `CURRENT_MAIN_EFFORT`에 넣는다. 이 변수는 현재 세션에서 확인한 정보를 전달하는 임시 변수이며 자동 탐지 인터페이스나 고정 기본값이 아니다. 확인할 수 없는 값은 비워 두고 이전 값을 제거한다. 아래 코드는 두 쌍의 해석 결과가 모두 있어야 실행을 허용한다.

```bash
ARCH_MODEL="${HARNESS_CODEX_ARCH_MODEL:-${CURRENT_MAIN_MODEL:-}}"
ARCH_EFFORT="${HARNESS_CODEX_ARCH_EFFORT:-${CURRENT_MAIN_EFFORT:-}}"
GATE_MODEL="${HARNESS_CODEX_GATE_MODEL:-${CURRENT_MAIN_MODEL:-}}"
GATE_EFFORT="${HARNESS_CODEX_GATE_EFFORT:-${CURRENT_MAIN_EFFORT:-}}"
: "${ARCH_MODEL:?아키텍처 역할의 명시적 모델 설정 필요}"
: "${ARCH_EFFORT:?아키텍처 역할의 명시적 effort 설정 필요}"
: "${GATE_MODEL:?게이트 역할의 명시적 모델 설정 필요}"
: "${GATE_EFFORT:?게이트 역할의 명시적 effort 설정 필요}"
```

실행 전 각 값의 출처, 최종 두 모델·effort 쌍, 지원 여부 확인 근거를 기록한다. 두 역할이 같은 모델을 상속했다면 그대로 보고하며 서로 다른 모델 계열로 표현하지 않는다.

### 공통 입력과 역할

두 검토자를 각각 새 읽기 전용 CLI 세션으로 실행한다. 이전 검토 대화나 세션을 재개하지 않고, 서로의 검토 결과를 전달하지 않는다. 검토자는 파일 수정이나 추가 검토자 실행 없이 JSON 보고서만 반환한다. 메인 세션이 모든 편집을 맡는다.

쓰기 가능한 임시 위치에 각 역할의 완결된 프롬프트 파일을 준비한다. 두 파일에 동일한 다음 자료를 모두 포함한다.

- 사용자 요청, 확인된 범위·제약, 적용할 프로젝트 지침
- 검토 대상 전체 diff: staged·unstaged 변경과 새 파일 내용까지 포함
- `.agents/skills/project-rules/SKILL.md` 및 적용 규칙의 전체 본문
- 관련 관례의 본문, 코드·사용처 확인 결과와 `file:line` 근거
- 생성된 파일의 전체 내용과 이 워크플로의 검토 계약
- 테스트·정적 검사·full 게이트의 실제 명령, 출력, 종료 코드 및 실행 불가 항목

각 프롬프트를 정확히 `You are reviewing a generated harness` 문장으로 표시하고, 독립적인 위임 검토이며 새 오케스트레이션 작업이 아님을 명시한다. 역할별 초점은 다음과 같다.

- **아키텍처·규칙 도출:** 규칙의 저장소 근거, 설계·책임 분리, 관례 일치, 불필요한 추상화와 중복, 주장과 사실의 일치를 확인한다.
- **게이트·구현:** 구현 정확성, 테스트·정적 검사 근거, 결정적 규칙의 검증 가능성, 게이트 누락·회피 및 회귀를 확인한다.

양쪽 모두 여섯 품질 축 전체를 평가한다. 입력이 누락되었으면 이를 보고하며 근거 없는 통과를 반환하지 않는다.

### 역할별 구체적인 CLI 실행

`ARCH_PROMPT_FILE`, `GATE_PROMPT_FILE`은 위에서 준비한 프롬프트의 절대 경로로, `ARCH_RESULT_FILE`, `GATE_RESULT_FILE`은 쓰기 가능한 임시 결과 파일의 절대 경로로 지정한다. 모델·effort를 위 규칙으로 새로 확인하고 기록한 후 다음 두 명령을 각각 실행한다. `-`는 완결된 프롬프트를 표준 입력에서 읽도록 한다.

```bash
CXC_MODE=off codex exec --ephemeral -s read-only \
  -m "$ARCH_MODEL" \
  -c "model_reasoning_effort=\"$ARCH_EFFORT\"" \
  -C "$PROJECT_ROOT" \
  -o "$ARCH_RESULT_FILE" \
  - < "$ARCH_PROMPT_FILE"
```

```bash
CXC_MODE=off codex exec --ephemeral -s read-only \
  -m "$GATE_MODEL" \
  -c "model_reasoning_effort=\"$GATE_EFFORT\"" \
  -C "$PROJECT_ROOT" \
  -o "$GATE_RESULT_FILE" \
  - < "$GATE_PROMPT_FILE"
```

각 CLI 자식에 `CXC_MODE=off`를 지정해 중첩 실행을 방지한다. 두 호출 모두 완료될 때까지 기다리고 각각의 종료 상태와 최종 JSON을 확인한다. CLI가 없거나 호출이 실패하면 검토 미완료로 기록하고 중단한다. 격리를 완화하거나 검토를 생략하지 않는다.

### 검토 JSON 계약

두 프롬프트에 아래 형태를 포함하고 코드 펜스 없는 JSON 객체 하나를 요구한다. 아래 점수 `0`은 형식 예시이며 실제 평가로 교체해야 한다. `quality_scores`의 값은 각각 **숫자 0–5**여야 한다. 점수와 근거를 객체 하나로 중첩하지 않는다. 근거는 동일한 여섯 키의 `quality_evidence` 문자열로 별도 제공한다.

```json
{
  "findings": [
    {"severity": "high", "file": "path/to/file", "line": 1, "finding": "문제", "evidence": "확인 근거", "suggestion": "개선 제안"}
  ],
  "fact_check_misses": [
    {"claim": "검증되지 않았거나 틀린 주장", "evidence": "file:line 또는 실행 결과"}
  ],
  "gate_evasions": [
    {"rule": "회피된 규칙", "evidence": "file:line 또는 실행 결과"}
  ],
  "quality_scores": {
    "srp": 0,
    "comment_clarity": 0,
    "kiss": 0,
    "dry": 0,
    "yagni": 0,
    "cognitive_ease": 0
  },
  "quality_evidence": {
    "srp": "단일 책임 평가 근거",
    "comment_clarity": "주석 명확성 평가 근거",
    "kiss": "단순성 평가 근거",
    "dry": "중복 평가 근거",
    "yagni": "현재 요구에 필요한 범위인지 평가한 근거",
    "cognitive_ease": "이해하기 쉬운지 평가한 근거"
  },
  "patches_suggested": [
    {"file": "path/to/file", "suggestion": "메인 세션이 검토할 변경 제안", "reason": "근거"}
  ]
}
```

발견 사항이 없는 배열은 `[]`로 반환한다. 실제 파일 위치나 직접 검증 결과로 점수와 지적을 뒷받침한다. 잘못된 JSON, 누락된 키, 문자열 점수, 범위 밖 점수 또는 누락된 근거는 검토 완료로 인정하지 않는다.

### 종합, 통과 및 회귀 제한

메인 세션이 각 지적을 직접 확인하고 채택·기각 이유와 근거를 기록한다. 각 검토자의 여섯 숫자 점수 합계를 6으로 나눠 평균을 따로 계산한다. 두 검토자 점수를 합친 평균으로 통과시키지 않는다.

통과에는 full 게이트 종료 코드 `0`, 두 유효한 독립 검토, **각 검토자 평균 3.5 이상**, 그리고 양쪽 모두 빈 `fact_check_misses`와 `gate_evasions`가 필요하다. 확인된 미해결 차단 지적이 없어야 하며 나머지 지적의 처리와 제한 사항도 종합 기록에 남긴다. 실패·실행 불가 검사는 성공으로 바꾸어 보고하지 않는다.

검토 제안을 포함해 패치를 하나라도 적용하면 1단계로 돌아가 영향 범위를 재조사하고 관련 동작·정적·문서 검증과 full 게이트, 두 새 독립 검토를 다시 수행한다. 이전 검토의 승인은 변경 후 결과에 승계하지 않는다. 한 작업의 검토·회귀 반복은 최대 3회이며 패치나 재접수로 카운터를 초기화하지 않는다. 세 번째에도 통과하지 못하면 추가 반복을 중단하고 남은 지적, 점수, 검사 실패와 한계를 보고한다. 승인을 만들어 내지 않는다.

최종 보고에는 실제 사용한 역할별 모델·effort, 각 평균과 근거, 메인 세션의 종합, 최종 diff와 검증 결과 및 남은 제한을 포함한다.
