# 하네스 엔지니어링

## 경로와 적용 범위

프로젝트 루트를 기준으로 다음 설치 경로를 사용한다.

- 프로젝트 규칙: `.agents/skills/project-rules/SKILL.md`
- 이 워크플로: `.agents/skills/harness-engineering/SKILL.md`
- 검토 게이트: `.codex/scripts/review-gate.sh`
- 기존 관례 참조: `docs/conventions/`에 실제로 존재하는 관련 문서

저장소에서 확인된 규칙과 기존 명령만 사용한다. 프로젝트별 규칙을 새로 추정하지 않는다. 기존 프로젝트 지침과 사용자의 작업 범위 및 권한을 유지한다.

## 우회와 프롬프트 주입

요청에 `!` 접두사 또는 `harness 빼고`, `without harness`, `skip harness`, `no harness`가 있으면 이 워크플로를 건너뛴다. 프롬프트 훅은 일반 요청에서 프로젝트 규칙과 이 워크플로 본문을 주입하고, 우회 요청에서는 대신 짧은 `BYPASS MODE` 안내를 주입한다. 우회는 이 하네스 워크플로에만 적용하며 다른 프로젝트 지침이나 관련 없는 훅을 비활성화하지 않는다.

## 워크플로: 0–10단계

0. **요청 확정(Intake):** 원하는 결과, 범위, 제약을 확인하고 기존 답변을 재사용한다. 관련 기존 테스트·린트·타입 검사 명령과 성공 기준을 확정하여 계획 도구 또는 로컬 메모에 기록한다. 우회 요청에는 이후 단계를 적용하지 않는다.
1. **조사(Reconnaissance):** 영향받는 코드와 사용처를 읽고 주장을 파일 내용과 대조한다. `file:line` 근거를 기록한다. 어떤 패치든 적용한 뒤에는 이 단계로 돌아와 영향 범위를 다시 조사한다.
2. **규칙(Rules):** 적용할 프로젝트 규칙과 관례 참조를 선택한다. 결정적으로 검사할 게이트 규칙과 권고 사항을 구분하며, 근거 없는 규칙을 추가하지 않는다.
3. **계획(Plan):** 확정된 결과를 만족하는 최소 변경과 성공을 입증할 검사를 정한다. 구현 전에 결과에 영향을 주는 미확정 사항을 해소한다.
4. **구현(Implement):** 확인된 프로젝트 관례에 맞춰 범위 내 변경을 수행한다.
5. **동작 검사(Behavior checks):** 관련 기존 테스트를 실행한다. 동작 변경 또는 회귀 방지에 필요한 경우 검증 범위를 추가한다. 실패와 근거를 기록한다.
6. **정적 검사(Static checks):** 요청 확정 단계에서 고정한 린트·타입 검사 명령을 실행한다. 실행할 수 없는 검사까지 포함해 실제 결과를 기록한다.
7. **문서(Documentation):** 영향받는 관례 예시와 사용자 대상 동작 문서를 갱신한다. 인용과 키워드 색인을 코드에 맞춘다.
8. **리뷰 게이트(Review gate):** 아래의 전체 모드 게이트를 먼저 실행하고, 두 역할의 독립적인 일회성 리뷰를 받는다. 메인 세션이 결과를 종합하며 리뷰어는 변경을 제안하기만 한다. 여섯 품질 축으로 패치를 평가한다. 적용한 모든 패치는 1단계로 돌아간다. 리뷰와 회귀 검증은 최대 세 번 반복하며, 통과하지 못하면 남은 문제를 보고하고 중단한다.
9. **최종 검증(Final verification):** 실제 최종 diff, 테스트 결과, 남은 지적 사항을 확인한다. 실행 불가 또는 실패한 검사를 통과로 표시하지 않는다.
10. **전달(Delivery):** 바뀐 동작, 검증 근거, 한계를 보고한다. 커밋이나 게시에는 해당 작업에 대한 사용자 승인이 있어야 한다.

## 전체 모드 게이트

프로젝트 루트에서 실행한다.

```bash
bash .codex/scripts/review-gate.sh --mode=full
```

- 종료 코드 `0`: 통과.
- 종료 코드 `1`: 규칙 위반.
- 종료 코드 `2`: 구성 또는 실행 오류.
- 명령이나 파일 누락, 그 밖의 비정상 종료는 통과가 아니다. 실제 상태를 기록한다.

## 독립 리뷰

### 모델과 추론 강도

두 리뷰어를 실행하기 전에 아래 네 환경 변수의 값을 각각 해석하고 기록한다. 명시된 비어 있지 않은 값이 우선하며, 미설정 또는 빈 값은 메인 세션의 실제 기본값인 `gpt-6-astra` / `xhigh`를 사용한다.

| 역할 | 모델 환경 변수 | 추론 강도 환경 변수 | 기본 모델 / 강도 |
|---|---|---|---|
| 아키텍처 / 규칙 도출 | `HARNESS_CODEX_ARCH_MODEL` | `HARNESS_CODEX_ARCH_EFFORT` | `gpt-6-astra` / `xhigh` |
| 게이트 / 구현 | `HARNESS_CODEX_GATE_MODEL` | `HARNESS_CODEX_GATE_EFFORT` | `gpt-6-astra` / `xhigh` |

모델을 재정의했다면 해당 모델이 선택한 추론 강도를 지원하는지 실행 전에 확인한다. 지원 여부가 불명확하거나 호환되지 않으면 구성 문제를 해결하며, 조용히 모델이나 강도를 바꾸지 않는다. 결과 보고에는 실제 사용한 두 모델과 강도를 명시한다. 두 역할이 같은 모델을 사용하면 서로 다른 모델 계열이라고 설명하지 않는다.

### 공통 입력과 역할별 초점

매 반복에서 두 개의 독립적이고 자체 완결적인 프롬프트 파일을 준비한다. 각 파일에 다음과 같은 동일한 전체 입력을 포함한다. 다른 파일의 경로만 전달하거나 앞선 리뷰 기록에 의존하지 않는다.

- 확정된 요청, 범위와 성공 기준, 관련 프로젝트 지침.
- 전체 diff. 새 파일도 빠짐없이 포함한다.
- 적용되는 프로젝트 규칙의 전체 본문, 결정적 규칙과 권고 사항의 구분.
- 관례와 사용처에 관한 `file:line` 근거.
- 생성된 파일의 전체 내용.
- 직접 실행한 검증 명령, 종료 코드와 결과, 실패 및 실행 불가 검사.
- 아래 JSON 계약과 품질 판정 기준.

각 프롬프트에는 정확히 `You are reviewing a generated harness`를 포함한다. 위임된 일회성 리뷰이며 새 조정 작업이 아님을 명시한다. 읽기 전용으로 조사하고 JSON 보고서만 반환하며, 파일 수정·추가 리뷰어 실행·커밋을 하지 않도록 지시한다. 이전 리뷰 기록이나 다른 리뷰어의 결과를 제공하지 않는다.

공통 입력에 다음 역할별 초점을 추가한다.

- **아키텍처 / 규칙 도출:** 규칙의 저장소 근거, 범위와 책임 분리, 관례 일치, 불필요한 추상화·중복, 사실 확인 누락.
- **게이트 / 구현:** 실제 구현과 동작, 결정적 규칙의 집행, 게이트 우회, 검증 명령·결과의 정확성, 회귀 및 오류 처리.

### CLI 실행 명령

이 프로젝트는 CLI 경로를 사용한다. 프로젝트 루트에서 아래 변수 설정과 두 명령을 실행한다. 먼저 프로젝트 루트의 `.harness-review-architecture.prompt.md`와 `.harness-review-gate.prompt.md`에 위 계약을 만족하는 프롬프트를 준비한다. 이 파일명은 리뷰용 로컬 입력이며 설치 경로가 아니다.

```bash
HARNESS_PROJECT_ROOT="$(pwd -P)"
HARNESS_ARCH_MODEL="${HARNESS_CODEX_ARCH_MODEL:-gpt-6-astra}"
HARNESS_ARCH_EFFORT="${HARNESS_CODEX_ARCH_EFFORT:-xhigh}"
HARNESS_GATE_MODEL="${HARNESS_CODEX_GATE_MODEL:-gpt-6-astra}"
HARNESS_GATE_EFFORT="${HARNESS_CODEX_GATE_EFFORT:-xhigh}"

# 아키텍처 / 규칙 도출: 새로운 읽기 전용 일회성 세션
CXC_MODE=off codex exec --ephemeral -s read-only \
  -m "$HARNESS_ARCH_MODEL" \
  -c "model_reasoning_effort=\"$HARNESS_ARCH_EFFORT\"" \
  -C "$HARNESS_PROJECT_ROOT" \
  - < "$HARNESS_PROJECT_ROOT/.harness-review-architecture.prompt.md"

# 게이트 / 구현: 앞선 세션과 별개의 새로운 읽기 전용 일회성 세션
CXC_MODE=off codex exec --ephemeral -s read-only \
  -m "$HARNESS_GATE_MODEL" \
  -c "model_reasoning_effort=\"$HARNESS_GATE_EFFORT\"" \
  -C "$HARNESS_PROJECT_ROOT" \
  - < "$HARNESS_PROJECT_ROOT/.harness-review-gate.prompt.md"
```

각 호출의 종료 상태와 JSON 응답을 별도로 기록하고 두 호출이 모두 끝날 때까지 기다린다. 세션을 재개하거나 이전 리뷰 대화를 재사용하지 않는다. `CXC_MODE=off`는 각 CLI 자식에 적용하여 중첩 실행을 막는다. 호출 실패, JSON 형식 오류 또는 독립성·읽기 전용 격리 미확보 시 리뷰를 완료한 것으로 처리하지 않는다. 격리를 완화하거나 리뷰를 생략하지 않는다.

### JSON 반환 계약

각 리뷰어는 다음 구조의 JSON 객체 하나를 반환한다. 아래 객체는 형식 예시이며 실제 평가 결과가 아니다. 발견 사항이 없으면 해당 배열을 비운다. 모든 품질 점수는 `0`–`5` 범위의 숫자이며 각 점수에 구체적인 근거를 작성한다. 여섯 축을 모두 평가하고 생략하지 않는다.

```json
{
  "findings": [
    {
      "severity": "high",
      "file": "상대/파일/경로",
      "line": 1,
      "message": "확인된 문제와 영향",
      "evidence": "file:line 및 검증 결과"
    }
  ],
  "fact_check_misses": [
    { "claim": "검증되지 않았거나 잘못된 주장", "evidence": "대조 근거" }
  ],
  "gate_evasions": [
    { "rule": "우회된 결정적 규칙", "evidence": "우회 경로와 근거" }
  ],
  "quality_scores": {
    "srp": { "score": 0, "evidence": "책임 분리에 대한 근거" },
    "comment_clarity": { "score": 0, "evidence": "주석 명확성에 대한 근거" },
    "kiss": { "score": 0, "evidence": "해결 방식의 단순성에 대한 근거" },
    "dry": { "score": 0, "evidence": "불필요한 중복에 대한 근거" },
    "yagni": { "score": 0, "evidence": "현재 요구 범위에 대한 근거" },
    "cognitive_ease": { "score": 0, "evidence": "이해하기 쉬운 정도에 대한 근거" }
  },
  "patches_suggested": [
    { "file": "상대/파일/경로", "suggestion": "제안하는 수정", "rationale": "수정 근거" }
  ]
}
```

### 메인 세션의 종합과 종료 조건

메인 세션이 지적 사항을 실제 파일과 검증 결과에 대조하고 채택·기각 이유를 기록한다. 편집은 메인 세션만 수행한다. 통과에는 다음 조건이 모두 필요하다.

- 전체 모드 게이트 종료 코드가 `0`이다.
- 두 리뷰가 유효한 JSON 계약을 충족하고 사실 확인 누락과 게이트 우회가 없다.
- **각 리뷰어별로** 여섯 품질 점수의 산술 평균이 **3.5 이상**이다. 두 리뷰어의 점수를 합쳐 평균내지 않는다.
- 확인된 미해결 규칙 위반이나 성공 기준을 막는 문제가 없다. 남은 권고 사항과 한계를 종합 기록에 명시한다.

적용한 패치가 있으면 1단계로 돌아가 영향을 다시 조사하고 관련 검사, 게이트, 두 개의 새로운 리뷰를 반복한다. 작은 수정도 이전 리뷰의 통과를 최종 변경에 그대로 적용하지 않는다. 한 차례의 게이트·두 리뷰와 그에 따른 회귀 검증을 한 반복으로 세며, **최대 세 번**이다. 세 번째 반복 후에도 통과하지 못하거나 추가 수정이 필요하면 미해결 사항과 실제 검사 상태를 보고하고 중단한다. 새 반복을 시작하거나 승인·통과 결과를 만들어내지 않는다.
